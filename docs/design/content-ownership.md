# Content ownership

This note describes where LoonFS stores content objects, how a merge keeps the content of the fork it merged, and how garbage collection decides when that content can be deleted. Every namespace stores the content it writes under its own prefix and collects that content from its own roots. A namespace that merges a fork pins the fork's manifest, and every manifest that the fork's folded manifest depends on through the fork's own merge pins, until the namespace no longer depends on them. Maintenance copies the merged content into the merging namespace's prefix so that those pins can be released.

## The problem

This section describes how content is stored and collected today, and what that costs.

A [content reference](../specs/glossary.md#content-reference) contains a content ID, a size, and a checksum, and nothing that says which namespace wrote the bytes. Today every member of a [fork family](../specs/glossary.md#fork-family) writes its content objects and upload records under the prefix of the [family root](../specs/glossary.md#family-root), the namespace that was created without a source. Every manifest records the family root (`family_root_id`), and a reader derives each object's key from the family root and the object's name (see [File contents and ownership](../specs/format.md#15-file-contents-and-ownership) and [Storage layout](../specs/format.md#21-storage-layout)). A fork inherits its source's references and reads the same objects, and a [merge](../specs/glossary.md#merge) brings a fork's references into the namespace it was forked from without copying any bytes.

Because any member can refer to any object under the family root's prefix, one member's roots can't show whether an object is garbage. So the collection on the family root reads the roots of every member (see [Content roots](../specs/format.md#119-content-roots)). It finds the members by walking fork pins, and for each member it discovers the current manifest, lists the pins, and reads the WAL tail. A family with 200 live and recently deleted forks pays 200 manifest discoveries, 200 pin listings, and 200 tail reads on every collection of the family root, and a collection on a fork does none of this work.

The walk also has a time bound. A reference can move from one member to another while the collection runs, and the collection sees that reference through the first member's tombstone only until the first member is retired. So the collection has to read every member's roots within the retirement grace less the clock allowance (38 minutes and 30 seconds), measured from its start, or it skips the family's content. Nothing breaks when that happens, but nothing in the family's content prefix is reclaimed until a collection finishes in time. The family root also has to be the last member retired, because its prefix stores the whole family's content (see [Retirement](../specs/format.md#95-retirement)).

The obvious way out is for each namespace to store its own content and for a merge to copy the fork's content into the destination before the commit. That makes a merge cost one copy request for every object the fork wrote, so a merge of 10,000 new files makes 10,000 copies before it can commit, and every byte that a sandbox wrote is copied whether or not the destination keeps it for long. In the design below, a merge makes no copies. Maintenance makes them later, outside the merge's latency, and each copy is optional.

## The design

This section describes the rules of the design, each with the reason for it and an example. The design adds no clock constant and no new key prefix.

In this note, "main" is a namespace, "sandbox" is a fork of main, and a merge of sandbox into main makes main the "destination". A rebase's destination is the new fork that it creates (see [Rebasing](merge.md#rebasing)).

### Content owners

Every content object is stored under the prefix of the namespace that wrote it, and that namespace is the object's "owner". The keys of a chain's objects are:

```text
namespaces/{owner}/content/{content_id}
namespaces/{owner}/content/{content_id}-{start:020}-{end:020}
```

An upload's object, the objects that a fold writes for WAL pieces, and the extents of new chains are all owned by the namespace that writes them. Upload session records are stored under the uploading namespace's prefix, and the collection on that namespace cleans them up. A [localized copy](#localizing-merged-content) (a namespace's copy of an object that another namespace wrote) has a third key shape, with a random suffix.

Each [extent](../specs/glossary.md#extent) of a [layout](../specs/glossary.md#layout) records its owner (`owner_namespace_id`), and a reader derives the extent's key from the owner and the object's name. A layout row leaves the owner out when the owner is the layout's [creator](../specs/glossary.md#chain-creator), so the extents that the creator wrote (the chain's own extents) don't repeat the creator's ID. The owner appears on shared base extents that another namespace wrote, and on extents that a namespace copied into its own prefix. Leaving it out matters because a namespace ID can be 128 bytes long and a layout can have 32 own extents, so writing the owner on every extent would add up to 4 KiB to a layout row.

For example, main creates `/model.bin`, and its fold writes the chain's whole object at `namespaces/main/content/c_7f2a`. Sandbox, a fork of main, appends to the file. Sandbox isn't the chain's creator, so the append starts a new chain whose layout lists main's object as a shared base extent with owner main, followed by an own extent that sandbox's fold writes at `namespaces/sandbox/content/c_91be-...`.

A read already locates a chain's objects through the chain's longest layout row whenever any of its bytes have been folded (see [Content verification](../specs/format.md#45-content-verification)), so the read path reads nothing new. The change is in how the reader derives a key. The reader puts each extent under the prefix of the extent's owner instead of the family root's prefix. The keys that LoonFS derives from a reference alone, without a layout row, all refer to the reading namespace's own content: an upload's object before the commit that publishes it, and the whole object that a fold writes for a chain that the namespace's own WAL started. Those keys use the reading namespace's prefix. A download of a zero-byte reference writes the chain's empty whole object if it doesn't exist (see [Download transport](../specs/api.md#610-download-transport)), and that key uses the reading namespace's prefix too, so a fork that inherited an empty file writes its own empty object on the first download.

The [chain creator](../specs/glossary.md#chain-creator) rule doesn't change. Only the creator extends a chain in place, and any other namespace's append starts a new chain. Separate prefixes would keep two namespaces' span objects at different keys, but the rule is still needed because a merge brings the fork's layout rows into the destination. If main and sandbox both extended one chain, the merge would bring a second layout for the same content ID with different bytes, and the longest layout rule would pick one namespace's bytes for a reference that the other namespace wrote.

The [extent filter](../specs/format.md#extent-filter) doesn't change. The filter stores object names without a prefix, and a [localized copy](#localizing-merged-content) has a name of its own, so no name refers to objects under two owners.

### The basis chain

A fork's source pin keeps the source's manifest at the fork point (the fork's basis), the source's own source pin keeps the source's basis, and so on up to the namespace that was created without a source. This sequence of pinned manifests is the namespace's "basis chain", and it protects the objects that the namespace inherited. The namespaces whose manifests the chain pins are the namespace's ancestors. The manifest doesn't list them, and no rule needs to, because each fork basis records its source's manifest reference and source pin ID (`fork_basis`).

For example, if sandbox is a fork of main and trial is a fork of sandbox, trial's basis chain is sandbox's manifest at trial's fork point, followed by main's manifest at sandbox's fork point. A rebase's new fork is a fork of main, so its basis chain starts with main's manifest at main's head when the rebase created it.

### Owners and retained views

A namespace's rows can refer to objects of three kinds of owner:

- The namespace itself, for content it wrote or copied into its own prefix.
- A namespace that it has a merge pin on (see [Pinning a merged fork](#pinning-a-merged-fork)), for content that a merge or a rebase brought in.
- A namespace reached through its basis chain, for content that it inherited from a manifest of its source.

The second case is the one the rules below test. Every merge pin that a namespace has is on a namespace below the namespace's own source in the fork tree (a fork of the namespace, a sibling fork that a rebase replayed, or a fork of either), and never on the namespace itself or an ancestor. So the rules test the pins that the namespace has, and they never need to tell an ancestor from any other owner. For example, after main merges sandbox, main's rows refer to objects owned by sandbox, and main has a merge pin on sandbox. If trial forks main before main copies those objects into its own prefix, trial's inherited rows refer to sandbox's objects too, and trial reaches sandbox through its basis chain, because the manifest of main that trial's fork pin keeps depends on main's pin.

A namespace's "retained views" are its current manifest (active or deleted), every manifest that a pin on the namespace keeps, every manifest whose immediate successor is younger than the "view window", and its unfolded WAL tail. The length of the view window depends on what the collection is checking. When a collection protects content, the window is the ordinary grace `T`, and the views are the reference roots of [Reference roots](../specs/format.md#112-reference-roots) together with the tail. When a collection checks whether to release a merge pin (see [Releasing a merge pin](#releasing-a-merge-pin)), the window is the default grace window (`GC_DEFAULT_GRACE_WINDOW_MS`, 60 minutes), whatever `T` is configured to.

Why does the release rule use a longer window? A superseded manifest stays a view so that a reader that confirmed it just before its successor was published can keep using it. The configured `T` can be as short as its minimum, 22 minutes 15 seconds, which is the revalidation bound plus the clock allowance, so it covers a cached reader. It doesn't cover a download URL that the reader issues at the end of its revalidation bound, which can still be in use 19 minutes 15 seconds plus 15 minutes after the successor was published. The default window covers both. The retention advance already uses the same default window to keep a replaced revision readable for a URL's whole lifetime (see [Advancing the retention floor](../specs/format.md#101-advancing-the-retention-floor) and [Content roots](../specs/format.md#119-content-roots)), so the design adds no constant for it.

### Pinning a merged fork

A merge reads the fork through a pin on the fork's folded manifest, and the destination's rows then refer to the fork's objects. The fork's collection keeps an object while one of the fork's retained views refers to it, so the pin has to stay for as long as the destination refers to the fork's content.

Every pin record is stored at:

```text
namespaces/{namespace_id}/pins/{pinned_namespace_id}/{pin_id}.json
```

For a pin stored under the pinned namespace, the middle segment is the pinned namespace's own ID, so the pins on a namespace (its user pins, the fork pins of its forks, and the merge pins of its destinations) are the entries under `pins/{namespace_id}/`. A namespace ID never contains `/`, so LoonFS can parse the key. The pin record's body is the one that [Records and owners](../specs/format.md#81-records-and-owners) defines: the pinned namespace's ID, the pin ID, the pinned head sequence, the manifest's payload checksum, the creation time (`created_at_ms`), and the owner.

A "merge pin" is a pin on a merged fork's manifest whose pin owner (the record's owner field, not a [content owner](#content-owners)) is `merge`, with the destination's namespace ID (`destination_namespace_id`). It keeps the fork's objects for as long as the destination refers to them. A merge pin is stored twice, byte for byte the same record, at the same relative key. The record under the pinned namespace protects the manifest. The record under the destination is "the destination's copy" of the pin, and it records that the destination has the pin. So the entries under a namespace's `pins/` prefix with another namespace's ID are the namespace's copies of the merge pins it has on other namespaces.

For example, main's merge pin on sandbox is stored at `namespaces/sandbox/pins/sandbox/pin_00000000000000000042-3f....json`, and main's copy is stored at `namespaces/main/pins/sandbox/pin_00000000000000000042-3f....json`.

Why does a fork pin have no copy under the fork? A fork's ownership of its source pin has to be atomic with the fork's creation, and the fork's first manifest is the only record whose write creates the fork. So the fork records its pin in that manifest (`fork_basis.source_pin_id`), and the source's [pin cleanup](../specs/format.md#117-pin-cleanup) reads it there. A merge's destination already exists, so a copy that the merge writes before its commit is safe. If the commit never happens, the release rule removes the pin and the copy.

The fork's rows can also refer to objects that the fork itself merged from another namespace and hasn't copied into its own prefix yet. The fork keeps those objects through its own merge pins. A destination never relies on the fork's merge pins. Instead, the destination creates a merge pin of its own on every manifest that the fork's folded manifest depends on through one of the fork's merge pins, so every dependency is "first order". A namespace depends on pins that it created itself, and never on another namespace keeping a pin.

To merge sandbox into main, LoonFS:

1. Reads the request clock as the call's start (`created_at_ms`). The prepared content of every plan in the call expires `DIRECT_TRANSFER_URL_TTL_MS` after this time.
2. Folds sandbox and selects its folded manifest, as [Merging](merge.md#merging) step 7 does.
3. Creates a merge pin on that manifest, with `created_at_ms` from step 1, and verifies it as any pin from the current head is verified (see [Creating and verifying a pin](../specs/format.md#82-creating-and-verifying-a-pin)). If the verification fails, LoonFS deletes the pin, best effort, and starts again from a fresh basis.
4. Collects the distinct pairs `{W, p}` (an owner W and the ID p of a merge pin that sandbox has on W) in the pin dependencies of the segment descriptors that sandbox wrote and that the folded manifest lists (see [Recording which pins a segment depends on](#recording-which-pins-a-segment-depends-on)). For each pair, it reads pin `p` under W and creates a merge pin of main's own, with the same `created_at_ms`, on the manifest that `p` keeps.
5. Writes main's copy of each pin from steps 3 and 4, with put-if-absent.
6. Lists main's `pins/` prefix, for main's copies of the merge pins it already has.
7. Plans and publishes the merge commit, reading sandbox through the pin from step 3. The merge record lists, as pin dependencies (`pin_dependencies`), main's merge pins on the owners of the extents that the commit admits: the pins that steps 3 and 4 created, and main's existing pins (found in step 6) on those owners. Each entry is a pair of an owner and a pin ID, the same shape that a segment descriptor uses.

The merge commit is published only after steps 5 and 6 succeed, and the route call has to start its WAL put within `METADATA_PUBLICATION_BUDGET_MS` of `created_at_ms`. A merge also admits each of the fork's references with a proof that expires `DIRECT_TRANSFER_URL_TTL_MS` after `created_at_ms` (the same length today), and the writer checks the proofs again just before the numbered WAL put. The writer refuses the batch once either deadline has passed. A merge that admits no reference (one that only moves or deletes) has no proof, but it admits no extent either, so its merge record lists no pin. LoonFS doesn't delete the pins or the destination's copies after the commit.

A route call creates one set of pins. A plan made again after a stale commit reads the same folded manifest through the same pin, so it reuses the first plan's pins, copies, `created_at_ms`, and deadline. A retry of the same commit ID in a new call, after an unknown outcome, creates a new set. A rebase creates merge pins in the same way, with the rebase's new fork as the destination, for each call. A merge creates no user pin on the fork.

For example, main merges sandbox at main's sequence 300. Sandbox has no merge pins of its own, so its folded manifest lists no pin dependencies, and step 4 creates nothing. Sandbox's prefix contains `pins/sandbox/pin_00000000000000000042-3f....json` with owner `merge {destination_namespace_id: main}`, main's prefix contains the same record at `pins/sandbox/pin_00000000000000000042-3f....json`, and the merge record at sequence 300 lists the pair `{sandbox, pin_00000000000000000042-3f...}`.

Why doesn't main read `p` again after it creates its own pin? The folded manifest is one of sandbox's retained views (its current manifest, or a manifest superseded less than the default grace window ago, which is the window for a release decision) for longer than a route call can run, and that manifest lists the pair `{W, p}`. So sandbox's collection keeps its copy of `p` until the route is done, and W's collection keeps `p` while sandbox's copy exists. Pin `p` keeps the same manifest that main's new pin protects. A pin of sandbox's that no pair in the folded manifest lists is one that sandbox's current rows don't depend on, so main doesn't depend on it either.

Why does the destination create its own pins instead of depending on the fork's pins? If main depended on sandbox's pins, main's release of its pin on sandbox would have to wait until no namespace that sandbox pins was still referenced by main. That rule would track owners, and an owner can reach main both through main's own earlier merge and through the fork. For example, main merges a fork called scratch, and before main copies scratch's objects into its own prefix, sandbox forks main. Sandbox's fork pin keeps a manifest of main that refers to scratch, and sandbox's own manifest inherits that segment. Main later merges sandbox and copies every object its current rows refer to. A rule that tracked owners would see scratch in the manifest that sandbox's fork pin keeps and in sandbox's manifest, so main would never release its pin on sandbox. Sandbox could then never be retired, and its fork pin on main would never be deleted, even after all three namespaces were deleted. Narrower versions of that rule fail in the merge loop, where one owner can reach a namespace through two different manifests (see the second example in [Releasing a merge pin](#releasing-a-merge-pin)). First-order pins avoid the problem, because each destination releases its own pins on the evidence of its own views alone.

Why does the merge record list main's existing pins as well as the new ones? A fold attributes each extent that a merge admits to the merge record's pairs on the extent's owner (see [Recording which pins a segment depends on](#recording-which-pins-a-segment-depends-on)), and only the route has the information to tell which of main's pins protect an extent that came back through the fork. For example, main merges scratch with pin `p_ms`, sandbox forks main, and then main localizes scratch's objects. Main's current manifest no longer depends on `p_ms`, but main keeps it, because the manifest that sandbox's fork pin keeps depends on it. Sandbox's rows still refer to scratch's objects, and sandbox has no pin on scratch, so when main merges sandbox, those extents come back into main's rows. If the fold left them unattributed, sandbox could be retired, its fork pin's manifest would leave main's retained views, main would release `p_ms`, scratch could be retired, and main's current rows would refer to deleted objects. With `{scratch, p_ms}` in the merge record, the new segment depends on `p_ms` until main localizes those extents again. An extent whose owner has no pair in the record is main's own or came from main's basis chain, and the basis chain protects it.

Why does a refused merge keep its pins and copies? A commit whose outcome is unknown might still be applied, and deleting a pin would leave the destination referring to objects that the pinned namespace's collection can delete. The release rule deletes the pins and the copies once `T` has passed and the destination doesn't depend on them.

A merge pin and its copy are kept for at least the ordinary grace `T` after their `created_at_ms`, as a fork pin is (see [Pin cleanup](../specs/format.md#117-pin-cleanup)). The route call starts its WAL put within `METADATA_PUBLICATION_BUDGET_MS` of `created_at_ms`, and the provider applies it within the provider publication bound. `T` is at least `GC_MIN_GRACE_WINDOW_MS`, which is the longer of the WAL and metadata publication budgets (`METADATA_PUBLICATION_BUDGET_MS`), plus the provider publication bound, plus the clock allowance. So once `T` has passed by the collector's clock, every WAL put that the call could make has been applied, and a collection that reads the destination's tail finds the merge record if the merge committed. The design adds no clock constant.

### Recording which pins a segment depends on

A collection has to find out, without reading rows, which of its namespace's merge pins its retained views still depend on. So each `content_layouts` segment descriptor records the segment's "pin dependencies" (`pin_dependencies`). Each entry is a pair of an owner (`owner_namespace_id`) and the ID of a merge pin that the namespace that wrote the segment created on that owner (`pin_id`). A pair always identifies a pin of the segment's writer, and a namespace acts only on the pairs of segments it wrote. The pin dependencies list the merge pins whose manifests keep objects that the segment's rows refer to. The list is usually empty, and it rarely has more than a few entries.

A pin ID contains a manifest number and a random suffix, and no namespace ID, so a list of pin IDs alone couldn't show which owner each pin protects. A merge record lists its pin dependencies in the same shape, so one schema records a pin dependency from the commit until a compaction drops it. The pair is in the merge record while the record is in the tail, and on a segment descriptor after the fold.

A fold computes a segment's pin dependencies from the merge records in the WAL objects it folds. It copies onto the descriptor the merge record's pairs on the owner of each extent in the merge's rows. An extent whose owner has no pair in the merge record is the destination's own or came from the destination's basis chain, and it stays unattributed, because the basis chain protects it. A fold records every pair that a merge record it folds lists, even when the fold localizes every extent of that pair's owner (see [Localizing merged content](#localizing-merged-content)). A compaction records, for its output, the union of the pin dependencies of its input segments that the compacting namespace wrote, less the pairs whose owner has no extent left in the output rows. It drops the pairs of inherited input segments. So a pair leaves a namespace's views only through a compaction, and the manifest before that compaction stays a retained view of the release rule for the default grace window after the compaction (see [Owners and retained views](#owners-and-retained-views)).

A segment that a fork inherits keeps the pin dependencies that its writer recorded, and those pairs identify the writer's pins, not the fork's. So a pair in an inherited segment never causes the fork to keep or release a pin of its own. The pair still matters to the writer, because the fork's pin on the writer keeps a manifest that lists the segment, and that manifest is one of the writer's retained views.

A namespace "depends on" one of its merge pins when a pair with the pin's ID appears in the pin dependencies of a `content_layouts` segment that one of its retained views lists, or in the pin dependencies of a merge record in its unfolded WAL tail. A collection finds both in the manifests it already loads and the tail it already reads, so it reads no rows and sends no extra request.

For example, main merges sandbox with pin `pin_...42-3f...`, and the fold after the merge writes a segment whose pin dependencies are `{sandbox, pin_...42-3f...}`. Trial forks main before main copies sandbox's objects. Trial's manifest lists that segment, but the pair identifies main's pin, so trial has nothing to release. Main depends on the pin while its current manifest or the manifest that trial's fork pin keeps lists the segment.

Why does a fold keep the pair of a pin whose extents it localized? A reader that confirmed the destination's view just before the fold trusts that view, including the merge record in the tail, until its revalidation bound, and it reads the pinned namespace's objects through that record. The fold moves the merge record out of the tail. If it also left the pin out of the new segment's pairs, the next collection would find nothing that depends on the pin and release it, and the pinned namespace could be retired inside the reader's bound. With the pair, the pin stays until a compaction drops it, and the manifest before that compaction then stays a retained view for the default grace window, which covers the reader's bound and any download URL that the reader issued (see [Owners and retained views](#owners-and-retained-views)).

Why does a compaction drop an inherited segment's pairs? The pairs identify the writer's pins, so they're no use to the fork, and the writer loses nothing, because the writer's retained views still list the writer's original segments. Dropping them also means that every pair on a namespace's own segments identifies one of its own pins, so a publication can tell which owners it may localize from its own inputs, without a request (see [Localizing merged content](#localizing-merged-content)).

### Replaying content in a rebase

A rebase's new fork starts from main's current head, not from the replayed fork's fork point, so the replayed fork's rows can refer to objects that the new fork's view doesn't protect. To keep every object that the new fork refers to protected, a replay commit checks each extent of each row it replays, in this order (the "replay rule"):

1. If the new fork's own view (its basis plus its own history) has a layout row for the extent's chain that covers the extent's byte range, the replay writes that view's extents for the range in place of the replayed extent. The extent's chain and range come from its object's name (the content ID, and for a span or a localized copy the start offset) together with the extent's offset and length. The view's extents can be a localized copy that main made. The new fork's own content and its basis chain protect them.
2. Otherwise, if one of the replay commit's merge pins (the pin on the replayed fork and the pins that step 4 of the merge created) is on the extent's owner, and the manifest that pin keeps has a layout row that refers to the same object (the same owner and the same name), the replay writes the extent as it is, and the fold attributes it to the merge record's pairs on its owner, which include that pin.
3. Otherwise the replay commit doesn't apply that change, and the conflict report lists it as a `visibility` conflict, the kind that a rebase already reports for a file that main deleted after the fork point (see [Rebasing](merge.md#rebasing)).

The planner already has the replayed row from the replayed fork, and it sends one row lookup for each chain and each manifest it consults. The pin on the replayed fork is open already, because the merge reads the fork through it, and the planner loads the manifests that the copied pins keep only when a lookup needs one, which is rare. Attribution in the fold stays at the owner level. The fold attributes an extent to every pair that the merge record lists on its owner, and not just to the pin whose manifest step 2 found, because an extra pair delays a release and does no other harm.

Step 1 also removes most visibility conflicts for a fork that appended to a file it inherited from main, once main has localized the file's base. The new fork's view covers the base with main's localized copy, so the resolver doesn't upload bytes that main already has.

A merge into the fork's source needs no such check, because every extent in the fork's rows is owned by the fork, is protected by one of the fork's own merge pins (whose pairs the fork's folded manifest lists, so the merge creates its own pin on the same manifest), or came from the source's rows at the fork point, which the source's basis chain and the source's own merge pins protect for as long as the fork's pin keeps that manifest.

For example, main has `/data.bin`, whose object main owns. Sandbox forks main at sequence 100 and copies `/data.bin` to `/copy.bin`, which reuses main's chain. Main then deletes `/data.bin`, its retention floor passes the deletion, and a compaction drops the rows. Main's collection still keeps the object, because sandbox's fork pin keeps main's manifest at sequence 100. Sandbox's merge conflicts on another file, so the merge loop rebases sandbox into sandbox-2, a fork of main's current head. Sandbox-2's view has no layout row for the chain, so step 1 doesn't apply, and sandbox-2 has no merge pin on main, so step 2 doesn't apply either. Without the replay rule, the replay commit would create `/copy.bin` in sandbox-2 with an extent owned by main, which sandbox-2's basis doesn't list. Sandbox-2 would release its merge pin on sandbox once it stopped depending on it, the merge loop would delete sandbox, sandbox's retirement would delete its fork pin on main, and main's next collection would delete the object that `/copy.bin` refers to. With the replay rule, step 3 lists `/copy.bin` in the conflict report, and the resolver recreates it from sandbox's bytes, as it does for any file whose base main no longer has.

The replay rule covers objects that a third namespace owns in the same way. Main merges scratch, with main's pin on scratch's manifest, and sandbox forks main before main localizes scratch's objects, so sandbox's inherited rows refer to scratch's objects. Main then localizes them, and main keeps its pin on scratch because the manifest that sandbox's fork pin keeps depends on it. Sandbox's replay into sandbox-2 has no pin on scratch, because sandbox has no merge pin of its own. If main's current head still has the rows of those chains, step 1 writes main's localized copies in place of scratch's objects. If main has since deleted those files and compacted, step 2 finds no pin on scratch, and step 3 lists the files as conflicts. Without the replay rule, sandbox-2 would refer to scratch's objects, and once sandbox was retired, its fork pin on main would be deleted, main would release its pin on scratch, and scratch's retirement would delete the objects.

Why does the second step check the object rather than the owner? Main merges part of sandbox through pin `P1` on sandbox's manifest `M1`, which lists object X, and main copies the file that contains X to a second path. Sandbox deletes its own copy of the file and compacts, so sandbox's later manifest `M2` doesn't list X. The merge loop rebases sandbox into sandbox-2, which has a pin on `M2`. Sandbox-2 inherits the second path through its basis and appends to it, which starts a new chain with X as a shared base extent owned by sandbox. That merge conflicts, so the loop rebases sandbox-2 into sandbox-3, which creates its own pin on `M2`. A rule that asked only whether sandbox-3 has a pin on sandbox would admit X and attribute it to the pin on `M2`. Once sandbox-2 is retired, main releases `P1`, and sandbox's collection deletes X, because `M2` never listed it, while sandbox-3 still refers to it. Step 2 refuses X because `M2` doesn't list it, and step 1 admits it through main's localized copy when main's view still covers the chain.

### Localizing merged content

A merge pin keeps the whole pinned manifest, so the pinned namespace can't be retired while the destination depends on the pin. So that the pinned namespace can be retired, maintenance copies the pinned namespace's objects that the destination refers to into the destination's own prefix.

A publication that writes layout rows (a fold, a compaction, or a commit's validation when it writes pending pieces) can "localize" an extent. The publication copies the extent's object to a new object under the publishing namespace's prefix, a "localized copy", and writes the row with the copy as the extent's object and the publishing namespace as its owner (left out when the publishing namespace is the chain's creator). The copy's key is:

```text
namespaces/{owner}/content/{content_id}-{start:020}-{end:020}-{copy_id}
```

The `content_id` is the chain, `start` and `end` are the chain offsets of the bytes that the copied object stores, and `copy_id` is a new random value of 16 lowercase hex digits, the same shape as a pin ID's suffix. The publication writes the copy with put-if-absent, and it never adopts an occupied key, so a copy whose put fails or has an unknown outcome is made again under a new copy ID. The copy is a single-source copy (the store operation that this design adds to [Required operations](../specs/format.md#31-required-operations)), which preserves the provider's stored checksum, and the publication checks that checksum as it does for every chain extent that a fold writes (see [Publishing a manifest](../specs/format.md#72-publishing-a-manifest)). A copy that a crashed publication didn't publish is an unreferenced object under the namespace's own prefix, and the namespace's collection deletes it once it's older than `T`, as it deletes any other orphan.

For example, main's rows refer to sandbox's span object `namespaces/sandbox/content/c_91be-00000000000000000000-00000000000004194304`. Main's fold after the merge copies it to `namespaces/main/content/c_91be-00000000000000000000-00000000000004194304-8e01d4c7a9b3f625` and writes the chain's row with that extent's owner set to main.

Why does a localized copy get a new name instead of the copied object's name? Deletes are by key, and a collector captures its roots once per collection. If copies reused names, a key that was deleted and later written again could be deleted by a collection that listed the old object before the new one was written, and no provider offers a conditional delete that tells two objects with identical bytes apart. With a new name, every content key is written once, which is the property that the format's collection already relies on for every other object. Keeping the chain ID and the range in the name is what lets a replay put main's localized copy in place of the original (see [Replaying content in a rebase](#replaying-content-in-a-rebase)).

A publication localizes only extents whose owner it has a merge pin on, which is never itself or an ancestor. It finds those owners in the pin dependencies of its own input segments (the ones it wrote) and, for a fold, in the merge records it folds, so it sends no listing. An object whose owner it has no merge pin on reached the namespace through its basis chain (it was inherited), and copying it would copy the data that the fork was created to share. For example, trial, forked from main before main localized sandbox's objects, has no merge pin on sandbox, so trial's compactions don't copy sandbox's objects. When a compaction rewrites inherited rows together with merged rows that have the same owner, and the namespace has a merge pin on that owner, it localizes both. The inherited objects are the few that the source hadn't localized when the fork was taken.

Once a compaction leaves no extent with a given owner in its output, the output's pin dependencies drop every pair on that owner. The pin is released once no retained view depends on it, which is at least the default grace window after that compaction, because the manifest that the compaction superseded stays a retained view for that long.

The copies happen before the publication writes its segments, within the publication's budget. A publication plans at most `max_localized_objects_per_publication` copies (a maintenance setting, 1,000 by default, which is about a second of copies at 64 in flight). A publication that doesn't localize an extent writes it with its owner and keeps its pairs, and a later publication continues the work. Each row records which of its extents are already local (the ones whose owner is the publishing namespace), so the work resumes after a crash without a progress record.

Which publications localize is maintenance policy, not format. The reference implementation localizes first in the fold that follows a merge (see [Merging](merge.md#merging) step 12), so a small merge is local after one fold. Compaction localizes the rest. A segment whose pin dependencies identify one of the namespace's own merge pins counts as a compaction candidate, so a manifest's oldest run (the `base` run of [Compaction windows](../specs/format.md#102-compaction-windows)) that nothing else would compact doesn't keep a merged fork from being retired.

Localization is optional for correctness. Without it, nothing is copied, and a merged fork stays unretired while any retained view of the destination depends on its pin. The release rule, the pin dependencies, and the owners on extents are required either way.

### Releasing a merge pin

A destination's collection releases each of the destination's merge pins once the destination no longer needs it, because the destination's views are the ones that depend on the pins.

A merge pin goes through these stages:

1. A merge creates it. The pin under the fork and the destination's copy both record the merge call's `created_at_ms`.
2. From the commit, the merge record in the destination's tail lists a pair with the pin's ID.
3. From the fold, the pin dependencies of a segment descriptor that the destination wrote list the pair.
4. A compaction that leaves no extent of the pin's owner drops the pair, and the manifest that the compaction superseded stays a retained view for the default grace window.
5. The destination's collection releases the pin. The collection deletes the pin under the fork, and then the destination's copy.

A merge that never commits leaves a pin and a copy that the release rule removes once `T` has passed. If the destination's copy is absent once `T` has passed, the pinned namespace's collection deletes the pin (see [Cleaning up a merge pin](#cleaning-up-a-merge-pin)).

A collection on main releases merge pin P on sandbox when both of these conditions hold by the collection's clock:

1. P is older than `T`, measured from its `created_at_ms`.
2. Main doesn't depend on P, which means that no pair with P's ID appears in the pin dependencies of a `content_layouts` segment that one of main's retained views lists, or of a merge record in main's unfolded WAL tail.

To release P, the collection deletes P under sandbox first and then deletes main's copy. Deleting a pin that's already gone succeeds, so a collection that stopped between the two deletes finishes the release on the next collection.

The rule has no transitive condition. Every object that main's rows refer to is main's own, covered by main's basis chain, or kept by one of main's own merge pins, so main's own views determine every release.

Why is the default grace window after the compaction enough for a reader? A reader that confirmed a view trusts it for at most the revalidation bound (19 minutes 15 seconds), and a download URL issued from that view lasts the URL lifetime (15 minutes). A pair leaves a namespace's views only through a compaction, and for the release rule the manifest that the compaction superseded stays a retained view for the default grace window (60 minutes). So the pin is released no earlier than 60 minutes after the last view that referred to the old location was superseded, and the pinned namespace's retirement comes after the release. That's longer than the revalidation bound, the URL lifetime, the provider bound, and the clock allowance together (41 minutes 30 seconds), so every read and every URL that could point at the pinned namespace's object has ended before the object can be deleted.

The first example shows a case that a rule tracking owners couldn't release. Main merges scratch with pin `p_ms`, and sandbox forks main while main's rows still refer to scratch. Main localizes scratch's objects and then merges sandbox with pin `p_mb`. The manifest of main that sandbox's fork pin keeps lists the pair `{scratch, p_ms}` and not `p_mb`. So main releases `p_mb` once its current manifest, its tail, and its other pinned manifests stop depending on it. Sandbox can then be retired, its retirement deletes its fork pin on main, that manifest leaves main's retained views, main releases `p_ms`, and scratch can be retired.

The second example is the merge loop, in which one owner reaches a namespace through two manifests. Sandbox merges part of its range into main, with main's pin `p_ms1` on sandbox's manifest `M1`. Its next merge conflicts, so the loop rebases sandbox into sandbox-2, which pins sandbox's later manifest `M2` with `p_s2`. When main merges sandbox-2, step 4 finds the pair `{sandbox, p_s2}` in sandbox-2's folded manifest and creates main's own pin `p_ms2` on `M2`, next to main's pin `p_ms2b` on sandbox-2 from step 3. Main's rows then record the pairs `{sandbox-2, p_ms2b}` and `{sandbox, p_ms2}`, in addition to the older `{sandbox, p_ms1}`. Main localizes sandbox-2's and sandbox's objects and releases each of its three pins once main no longer depends on that pin. Sandbox-2's retirement deletes `p_s2` and its copy, and sandbox can be retired. A fork of main taken in between inherits `{sandbox, p_ms1}`, but the pair identifies main's pin, so the fork never acts on it, and main keeps `p_ms1` while the manifest that the fork's pin keeps is retained, which is exactly as long as a read through that fork pin could need sandbox's objects.

A deleted namespace's current manifest stops counting as a retained view for the release rule once the collection's clock has passed the tombstone's retirement deadline (see [Retirement](../specs/format.md#95-retirement)). Until then it counts, so a cached reader within the revalidation bound still finds the objects it refers to. After the deadline, the manifests that pins on the deleted namespace keep still count.

Why does a tombstone stop counting at its deadline? Without that, a deleted destination and the deleted fork it merged would never be retired. Suppose main merges sandbox, and then both are deleted. Sandbox's fork pin on main blocks main's retirement, and main's merge pin on sandbox blocks sandbox's retirement. Main's tombstone depends on the merge pin, and a tombstone has no successor, so nothing ever localizes sandbox's objects in main. Once main's retirement deadline passes, main's tombstone stops counting, the only manifest left in main's views is the one sandbox's fork pin keeps, and that manifest was published before the merge. So main releases its merge pin, sandbox is retired, sandbox's retirement deletes its fork pin on main, and main is retired.

A merged fork can also stay pinned through a fork of the destination. If trial forks main while main still depends on its pin on sandbox, trial's fork pin keeps a manifest of main that depends on it, and trial reads sandbox's objects through that manifest. Main keeps its merge pin on sandbox until trial is retired. Localizing in the fold right after a merge makes this rare, because few forks are taken in the time between a merge and its fold.

### Cleaning up a merge pin

A pinned namespace's collection checks whether to keep each merge pin on the namespace, in the same way that it checks a fork pin (see [Pin cleanup](../specs/format.md#117-pin-cleanup)). Releasing a merge pin is the destination's job, so the pinned namespace's collection deletes a merge pin only when the destination has finished with it or never needed it.

| Condition | Decision |
| --- | --- |
| Less than `T` has passed since the pin's `created_at_ms` | Keep the pin. |
| A read of the destination's copy at the same relative key finds a record equal to the pin | Keep the pin. |
| The read of the destination's copy fails | Keep the pin. |
| The copy is absent | Delete the pin. The destination released the pin, never wrote the copy, or was retired. |
| The copy exists and differs from the pin | Fail with `namespace_corrupt`. |

Checking a merge pin this way costs one GET for each merge pin, compared with two for a fork pin (the target's hint and its manifest), and it reads no rows and no WAL tail of the destination.

### Collecting a namespace's content

A collection on a namespace establishes its roots as [One complete collection](../specs/format.md#111-one-complete-collection) does, without the fork family steps. It discovers the current manifest, lists the namespace's upload sessions, reads the WAL tail, and lists `pins/` once. That listing returns both the pins on the namespace (the entries under its own ID, which are its reference roots) and its copies of the merge pins it has on other namespaces (the entries under other IDs, which the release rule checks). A content object under the namespace's own prefix is kept while the extent filter of a `content_layouts` segment in one of its retained views may contain the object's name, or the tail or an upload session refers to its chain, as [Content roots](../specs/format.md#119-content-roots) describes for one member of a fork family. The collection then cleans up the pins on the namespace, including merge pins, releases the merge pins it no longer depends on, and retires the namespace if it's eligible.

For example, a collection on sandbox lists `namespaces/sandbox/content/` and reads the extent filters of the layout segments that sandbox's retained views list: its current manifest, the manifests superseded less than `T` ago, and the manifests that its snapshots, its forks' fork pins, and main's merge pins keep. It deletes every object older than `T` that none of those filters may contain and that no chain in sandbox's tail or upload sessions refers to.

Why is that safe without reading any other namespace's roots? Every other namespace that reads an object under sandbox's prefix reads it through a manifest of sandbox that a pin keeps. A fork of sandbox reads through its fork pin, and a fork of that fork reads through the same pinned manifest, which the chain of fork pins keeps. A namespace whose rows refer to sandbox's objects through a merge has its own merge pin on sandbox, because a merge creates its own pin on the manifest of every pin that the fork's folded manifest depends on, and a fork of that namespace reads through a manifest that depends on that pin. Sandbox's own pin listing includes every one of those pins, so sandbox's collection sees every manifest that anyone reads sandbox's objects through. A rebase is the one way a namespace could refer to an object without such a pin or its basis chain, and the replay rule (see [Replaying content in a rebase](#replaying-content-in-a-rebase)) refuses that case.

### Retiring a namespace

A deleted namespace is eligible for retirement when its deadline has passed and its complete pin listing contains no pin on it, which means no entry under its own ID (see [Retirement](../specs/format.md#95-retirement)). Merge pins are pins, so a namespace whose content a destination still reads can't be retired. To retire an eligible namespace, garbage collection:

1. Lists the namespace's content prefix and deletes every key.
2. For each merge pin that the namespace has on another namespace (each entry under another ID), deletes the pin under the pinned namespace, and then the namespace's own copy.
3. Deletes the source pin that the tombstone's fork basis refers to, if there is one.

Step 2 doesn't apply the release rule, because nothing that the namespace refers to is read any more. Every step is idempotent, so a retirement that stops can start over. Retirement doesn't delete the namespace's hint or its tombstone.

Every namespace's retirement deletes its own content, so no namespace waits for another namespace's retirement before its own content can be deleted, and no namespace collects another namespace's content.

### Invariants

The design keeps these properties, and a bounded model checks them:

- Every content object exists while a view that counts refers to it, including an object that the view reaches through a chain of pins. The views that count are an active namespace's retained views, a deleted namespace's retained views until its retirement deadline, and after the deadline the manifests that pins on it keep.
- If every namespace in a set that refers to each other's content is deleted, every one of them is eventually retired. In particular, a deleted destination and the deleted fork it merged are both retired.
- A merge pin is deleted only by its destination's collection once the destination no longer depends on it, by the pinned namespace's collection when the destination's copy is absent once `T` has passed, or by the destination's retirement.
- A content object is deleted only by its owner's collection or its owner's retirement.
- Every extent that a namespace refers to and that an ancestor owns is covered by its basis chain, which means that the pinned basis manifest of its source refers to the same object, directly or through the source's own basis.
- Every object that a namespace's rows refer to is owned by the namespace, is covered by its basis chain, or is listed by a manifest that one of the namespace's own merge pins keeps.
- No content key is written twice, so a collection's decision about a key is never invalidated by a later write to that key.

## Costs

This section lists what the design costs, compared with one content prefix per fork family.

- A merge reads the fork's folded manifest, which it does anyway, and for each pair in that manifest's pin dependencies it sends one GET (the fork's pin), one PUT (main's own pin), and one write of main's copy. A sandbox usually has no merge pins of its own, so that's usually none. A merge also lists main's `pins/` prefix once per route call, writes one copy for each pin it creates, and deletes nothing after the commit (with one prefix per fork family, a merge deletes its merge snapshot). So a merge usually creates one pin and one copy. A rebase does the same for each replay commit.
- The merge loop increases the number of pins that a merge creates. Each rebase leaves the new fork with merge pins on the forks it replayed, so a merge of that new fork creates one more pin and copy for each pair in its folded manifest.
- A collection on a namespace sends no extra LIST, because one listing of `pins/` returns both the pins on the namespace and the namespace's copies. It sends one GET for each merge pin on the namespace (the destination's copy). A collection on a fork also lists the fork's own content prefix, which is empty with one prefix per fork family.
- A collection sends no per-member manifest discovery, pin listing, or tail read, and it has no time bound. A template with many forks still lists and judges one fork pin for each fork, at two GETs each, as it does with one prefix per fork family.
- Localization sends no listing, and each localized object costs one single-source copy request. The implementation adds a single-source copy operation to the store contract, which every supported provider offers with the stored checksum preserved. (The existing assembly path streams objects below 8 MiB through the server, so a copy costs one server-side request only with that operation.) A publication localizes within its publication budget, and `max_localized_objects_per_publication` is the planning bound on how many copies it attempts.
- A merge pin stays until a compaction drops its pair and the default grace window (60 minutes) passes, so a merged fork is retired at least one compaction and 60 minutes after its content is copied, whatever `T` is configured to.
- A merged fork's bytes are stored twice from the time they're localized until the fork is retired. Without localization, they're stored once, and the fork stays unretired while the destination depends on its pin.
- A merged fork stays unretired while a fork of the destination, taken before localization, keeps a manifest of the destination that depends on its pin, and while a snapshot of the destination does.
- A replay commit refuses a change when the new fork's view doesn't cover an extent's range and no manifest that one of the replay commit's merge pins on the extent's owner keeps refers to the object, so the resolver re-uploads that file's bytes. Step 1 of the replay rule makes this rare for a fork that appended to a file it inherited from main after main localized the base. The check costs one row lookup for each chain and each manifest consulted.
- Each layout segment descriptor stores its pin dependencies, and each pair is an owner (up to 128 bytes) and a pin ID (41 bytes). Each merge record lists its pin dependencies in the same shape. Each merge pin is stored twice.
- Each namespace's writes go to its own prefix from the first request, so a busy fork family doesn't concentrate its writes in one prefix that the provider has to partition.

## Other systems

Several storage systems share data between a clone and its source, and each one handles the source's collection differently. A Delta Lake shallow clone refers to the source table's data files in place, and running VACUUM on the source can delete files that the clone still reads. A merge pin exists to prevent that case. Ceph RBD layering lets a clone refer to a protected snapshot of its parent, and its `flatten` operation copies the snapshot's data into the clone so that the parent can be unprotected and deleted. Localization is a flatten that runs inside ordinary maintenance, bounded per publication, and only for content that the namespace's own merges brought in. Neon's `detach_ancestor` copies an ancestor's layers below a branch point into the child's own prefix with server-side copies and then re-parents the child, which keeps the parent free to collect and compact. ZFS `promote` swaps the roles of a clone and its origin so that the origin can be destroyed without copying anything. Apache Iceberg removes the data files that no retained branch or tag reaches when it expires snapshots, and it computes that from metadata rather than from a scan of the data, which is the shape of the release rule here.

## Alternatives considered

- **One content prefix per fork family.** Every member writes under the family root's prefix, and the family root's collection reads every member's roots. A merge copies nothing and needs no second kind of pin. But every collection of the family root pays a manifest discovery, a pin listing, and a tail read for each member, it has to finish within the retirement grace less the clock allowance, the family's writes all go to one prefix, and the family root is retired last.
- **Copying at merge time.** The destination copies every object the merge refers to before the commit. There are no merge pins, no localization, and no release rule, but a merge of 10,000 new files makes 10,000 copies before it commits, and every byte a sandbox wrote is copied, including bytes that the destination replaces soon after.
- **Tracking dependencies by owner, with a transitive release condition.** Each segment would record the owners of its rows that the namespace has merge pins on, and a destination would release its pin on a fork only when none of the owners that the fork's manifest lists was still referenced. One owner can reach a namespace through its fork basis and through a merge, through two different pinned manifests, and an owner set can't tell them apart. The rule then never releases in the case described in [Pinning a merged fork](#pinning-a-merged-fork), and the narrower versions that do release are unsafe in the merge loop.
- **An owner on every content reference.** A reference would locate its own bytes, so a read could find an object without a layout row. Every reference in every row and every delta would grow by a namespace ID, and a reference would become a locator that a client could point at any namespace's prefix.
- **Recording the ancestor list in the manifest.** Each manifest would list its source, its source's source, and so on, so that a rule could tell an ancestor's object from any other namespace's object without a request. No rule needs that distinction once the rules test the pins that the namespace has, and the API already exposes the source through the fork basis.
- **Listing the fork's merge pins.** A merge would list the fork's copies of its merge pins and create its own pin on the manifest of every one. The fork's own segment descriptors already record which pins its view depends on, and a pin that the folded manifest doesn't list is one that the merge doesn't need.
- **Copying to the same name under the destination.** A localized copy would keep the copied object's name under the destination's prefix. A key that was deleted and later written again could then be deleted by a collection that listed the old object before the new one was written, because deletes are by key and no provider offers a conditional delete that tells two objects with identical bytes apart.
- **Recording merge pins in the manifest.** A fold would add an entry for each merge record in the tail, and the destination would need a manifest publication to remove an entry, or every later publication would check each entry's pin, which costs a request for each unreleased pin on every fold.
- **No localization.** Nothing is ever copied, which is correct and the simplest design, but a long-lived destination that still depends on a merge pin never lets the pinned namespace be retired.
- **Localizing inherited merged content.** A publication would also copy objects whose owner it reaches through its basis chain. A fork of the destination taken before localization would then copy the merged content it inherited, which is the data the fork was created to share, and the copies wouldn't let any pin be released, because the pair in the inherited segment identifies the destination's pin.
- **Copying uncovered objects during a rebase.** A replay commit could copy an object that the new fork's view doesn't cover into the new fork's prefix before the commit, bounded by the replay commit's size. The replay already reports the changes that depend on state main no longer has, and the resolver already recreates such files from the fork's bytes, so the copy would be a second path for the same case.
- **Adopting the fork's prefix.** The destination could take over the merged fork's content prefix instead of copying from it. A prefix is part of a namespace's identity, and the fork can stay in use after the merge, so the destination can't take it over.
