# Time bounds

This note lists every time bound in the LoonFS format, sorts the bounds into three kinds by what each bound limits, and says what happens when each bound is broken. It ends with a rule for new designs.

## The problem

This section describes why LoonFS compares ages with constants, and why the constants are hard to read as a set.

Object storage has no transaction across objects, and a process can't tell a crashed operation from a slow one except by waiting. So for several questions, such as whether an unreferenced object is safe to delete, LoonFS compares an age with a constant. For example, a [collection](../specs/glossary.md#collection) can't ask whether some writer is about to write WAL object 31. Instead, the collector waits until an unreferenced object is older than the [grace window](../specs/glossary.md#grace-window), which is long enough for every write planned against an older state to have finished or failed.

The constants are defined as sums of each other. The minimum grace window (`GC_MIN_GRACE_WINDOW_MS`) is the longest publication budget, plus the provider request bound, plus the clock allowance. Four more bounds are built on that minimum, and the minimum commit age of a retention advance is checked against two more:

```text
provider request bound    = 2 min (retry budget) + 15 s (final backoff) + 2 min (payload request)
                          = 4 min 15 s
minimum grace window      = 15 min (metadata publication budget) + 4 min 15 s + 3 min (clock allowance)
                          = 22 min 15 s
read revalidation bound   = 15 min + 4 min 15 s = 19 min 15 s
compaction budget         = 24 h (segment minimum age) - 22 min 15 s = 23 h 37 min 45 s
retirement grace          = 15 min + 4 min 15 s + 22 min 15 s = 41 min 30 s
family roots read budget  = 41 min 30 s - 3 min = 38 min 30 s
completed-content grace   = 7 d (receipt window) + 1 h (token lifetime) + 22 min 15 s
minimum commit age (1 h) >= 19 min 15 s + 15 min (presigned URL lifetime) + 3 min = 37 min 15 s
minimum commit age (1 h) >  38 min 30 s (family roots read budget)
```

[Appendix C](../specs/format.md#appendix-c-timing-and-size-reference) shows this arithmetic, but it doesn't show which of these bounds an acknowledged commit depends on, and which bounds protect a request in progress and nothing more.

## The assumptions

This section lists the three assumptions that every bound depends on. The format spec states each assumption once.

- **The provider applies a request within a bound.** [Required operations](../specs/format.md#31-required-operations) says "A provider MUST also apply each request, if it applies it at all, within `PROVIDER_PUBLICATION_REQUEST_BOUND_MS` of when the client started the operation that sent it", and "An implementation can't check this assumption."
- **Clock error stays inside one allowance.** [Clock and operation assumptions](../specs/format.md#114-clock-and-operation-assumptions) defines the combined allowance (`GC_SAFETY_MARGIN_MS`, 3 minutes) as "one allowance for relative clock error, timestamp precision, and scheduling together". For an age measured from a stored time instead of a provider timestamp, the same section says "Ages based on recorded times (creation, expiry, or completion) use the corresponding bound between the collector and the host that recorded the time."
- **Each process's monotonic clock counts time asleep.** The same section says "Publication budgets use monotonic elapsed time, on a clock that keeps running while the host sleeps."

A bound that a process checks on its own clock depends on the third assumption. If a host's monotonic clock stopped while the host slept, a writer could wake after 30 minutes, find that one minute of its budget had passed, and send a put that the grace window no longer covers.

Why can't LoonFS check the provider assumption? A client sees when a response arrives, but not when the provider applied the request. A request whose response never arrives can still be applied later, and the client has no way to learn when.

## Three kinds of bound

This section defines three kinds of time bound by what the bound limits and which process checks the bound.

- A "budget" limits how long a process may take between an observation and the write it planned against that observation. The format spec already uses this word for the [publication budgets](../specs/glossary.md#publication-budget), the compaction budget, and the family roots read budget, and the provider request bound is the same kind of limit on the provider's side. A process checks its own budgets on its monotonic clock. When a budget runs out, the process stops, so the operation ends with an unknown outcome or abandons its output. For example, a writer that observed WAL tip 30 at 12:00 has to start its put at 31 by 12:05.
- A "collection age" is how old an unreferenced or replaced object has to be before the collector deletes the object. The grace window `T`, the segment minimum age, the retirement grace, the completed-content grace, the upload cleanup ages, and a fork pin's creation grace are collection ages. The collector compares the provider's timestamp, or a stored time, with its own clock. For example, with the default grace window of one hour, a folded WAL object whose provider timestamp is 11:58 can be deleted by a collection that starts at 12:58 or later.
- A "reader bound" limits how long a process may keep using what it loaded or was handed. The [revalidation bound](../specs/glossary.md#revalidation-bound), the [minimum commit age](../specs/glossary.md#minimum-commit-age), the presigned URL lifetime, a user pin's expiry, the upload session lease, and the admission evidence windows are reader bounds. For example, a reader whose last successor probe was sent at 12:00 runs discovery again if a probe's answer arrives at 12:19:15 or later.

Two bounds fit none of the three kinds, and the table says so in their rows. The clock allowance is a term inside several collection ages, and a namespace's [retention window](../specs/glossary.md#retention-window) is a policy setting for how much history to keep.

## The bounds

This section lists every format constant and every setting that affects what LoonFS keeps or deletes, and what happens when each bound is broken.

A budget or a reader bound is broken when the work, or the use, runs past the bound. A collection age is broken when the collector deletes an object that is younger, in real time, than the age, for example because the collector's clock runs ahead of the provider's. The last column of the table uses one of three outcomes:

- **Data loss.** Acknowledged data can be lost. A commit that a caller was told succeeded, or content that a committed file references, becomes unreadable.
- **Error.** A request fails with an error, and the caller retries or rediscovers.
- **Repeated work.** Work is repeated.

Each row says whether the format spec states the outcome, or whether the outcome follows from the rules, with the steps. A row whose outcome neither the spec nor the code establishes says "The format spec doesn't state this."

Implementation defaults that pace work (the fold triggers, the write-stop wait, the revalidation interval, and the sweep, collection, and backoff intervals) are scheduling settings, so the table leaves them out, and [Appendix C.4](../specs/format.md#c4-reference-implementation-sizing-and-admission-defaults) lists the ones that the format spec records.

Why does the table list a broken publication budget as an error, when a put that returns late can still have succeeded? The check after the put reports the late success as an unknown outcome, so the writer doesn't acknowledge the commit. A retry with the same commit ID runs discovery and returns the original result from the commit receipt if the put is visible.

### What the table shows

An acknowledged commit, or content that a committed file references, depends on eight bounds: the clock allowance, the grace window and its minimum, the segment minimum age, the retirement grace, the completed-content grace, the upload cleanup ages, a fork pin's creation grace, and the minimum commit age. Seven of the eight are collection ages, or the clock allowance, which is a term inside the collection ages. The minimum commit age is a reader bound, but the family root's content walk also depends on the minimum commit age. The provider request bound is a term in the minimum grace window, so each of these ages also depends on the provider meeting that bound.

The budgets and the revalidation bound are inputs to those ages. A process checks each of these bounds itself, so a process that runs past a budget or the revalidation bound stops, and the cost is a retry or repeated work. The other reader bounds protect a request in progress, and breaking a reader bound returns an error.

[Timing assumptions](../specs/format.md#33-timing-assumptions) says "Writer fencing and commit order don't depend on clocks." That sentence describes the history that readers see. A put-if-absent at the next WAL number orders every commit, and a writer whose put collides with a fence stops, whatever the clocks read. But a fence stops an old writer only while the fence is still at its WAL number. A writer's put at the next WAL number is safe because the put collides with any object at that number, and an object that another writer created there after the writer's observation is still there, because the collector waits a grace window before it deletes the object ([Publication and group commit](../specs/format.md#63-publication-and-group-commit), [Clock and operation assumptions](../specs/format.md#114-clock-and-operation-assumptions)). So the order of the visible history depends on conditional writes alone, but stopping a fenced writer before it acknowledges a commit also depends on the collector's clock, as the example shows.

For example, suppose a collection runs with the minimum grace window, 22 minutes 15 seconds, on a host whose clock runs 20 minutes ahead of the provider's clock. The times below are provider times.

1. At 12:00:00, writer session A confirms that the WAL tip is 30 and that the current manifest has no successor.
2. At 12:00:05, writer session B publishes its claim manifest, and at 12:00:10, B writes its fence as WAL object 31.
3. At 12:00:30, a fold publishes a manifest whose `folded_wal_no` is 31.
4. At 12:02:30, a collection starts. Its clock reads 12:22:30, so WAL object 31 looks 22 minutes 20 seconds old, and the collection deletes WAL object 31, which is at or below `folded_wal_no`.
5. At 12:04:00, A creates WAL object 31 with put-if-absent. The number is free, so the put succeeds, and the put returns within A's 5-minute budget, so A acknowledges the commit.

Each kind of process sees something different:

- Writer session A reports success to its caller. If A later runs discovery, it finds B's higher writer epoch and is fenced, as after any takeover, and A has no way to learn that the commit is gone.
- A reader that runs discovery replays the WAL from `folded_wal_no + 1`, which is 32, so no read returns A's commit, and no read returns an error.
- The collector finds an unreferenced WAL object at 31 again, and deletes the object once it looks a grace window old.

With an accurate clock, the collection at 12:02:30 finds that WAL object 31 is 2 minutes 20 seconds old and keeps the object, so A's put collides, and A runs discovery and is fenced without acknowledging anything. In this sequence, the commit can be lost when the clock error is more than `T` less the WAL publication budget, because an acknowledged put returns within that budget of the writer's observation, and the object that the put would collide with was created after that observation. With the minimum grace window, that's an error of more than 17 minutes 15 seconds. With the default grace window of one hour, it's an error of more than 55 minutes.

## A rule for new designs

This section states how a new design handles time.

- **No new time bound.** A dependency that outlasts one publication takes a [pin](../specs/glossary.md#snapshot), which keeps a manifest and its segments until the pin is deleted or expires and a collection removes the pin. A fork pins its source ([Forking a namespace](../specs/format.md#92-forking-a-namespace)), a merge or a rebase pins the fork while it plans ([Cross-namespace copies and moves](../specs/format.md#97-cross-namespace-copies-and-moves)), and grep's backfill reads through a user pin on the head ([Index lifecycle](../specs/format.md#d2-index-lifecycle)).
- **Order, not age, for acknowledged data.** A decision that acknowledged data depends on is made by a write that the WAL or the manifest sequence orders. [Retention advance in the WAL](retention-advance-in-the-wal.md) is the example. In that design, the retention floor moves when a floor object is written at the next WAL number, and a writer learns of the new floor by reading the log, so no writer can commit a restore against the old floor after the floor object exists. The design adds no constant.
- **A new bound has a kind and a derivation.** If a new bound is unavoidable, it's defined as a budget, a collection age, or a reader bound. Its derivation goes in [Appendix C](../specs/format.md#appendix-c-timing-and-size-reference), and a const assertion beside the constant checks the derivation at compile time, as the assertions in `crates/loonfs-core/src/limits.rs` do for the revalidation bound and the minimum commit age.

Why does a decision that acknowledged data depends on need an ordered write instead of an age? An age is safe only while all three assumptions are true, and LoonFS can't check the provider assumption. A put-if-absent at the next number is ordered against every other put at that number, whatever the clocks read. The retention window note describes a design that removes a deletion's rows once the floor has been above the deletion for a fixed time, and rejects the design because a restore validated against the old floor can stay unfolded in the WAL for any length of time (see [Alternatives considered](retention-window.md#alternatives-considered)).

Why can a pin's expiry be a time bound when the rule says a new feature doesn't add one? A pin's expiry is a reader bound that the caller chooses. When the expiry passes, a read through the pin returns `snapshot_not_found`, and a caller that still needs a manifest takes a new pin, as grep's backfill does when its pin no longer reaches the index's position.
