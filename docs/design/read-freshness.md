# Read freshness

This note describes where a process keeps a namespace's current [head](../specs/glossary.md#head), how a read uses it, and how recent the state that a read sees is. Each process keeps one view of a namespace, one procedure refreshes that view, and a read uses the view as it is unless the read asks for a confirmed head. A read sends no store request if it's `eventual` and its view was confirmed within the maximum staleness. Otherwise, it costs one refresh, or one HEAD and one conditional read of the manifest boundary in the writer's process. (In this note, a process means one LoonFS runtime. Two runtimes in one process keep separate views, even when they share a metadata cache.)

## The problem

A read starts from a head, and the head moves each time a writer commits. Confirming that a head is current costs store requests. In a process without the writer session, a GET of the next WAL number finds new commits, and a HEAD of the next manifest number finds a newer manifest (a fold, a compaction, or another writer's claim). In the writer's process, the writer position includes every commit that the session made, so only the HEAD and a read of the manifest boundary are needed, to find another writer's claim.

If each read confirmed its own head, every warm read in a reader process would send a GET, so a reader that walks thousands of files would send a GET per file to confirm a head that moves a few times during the walk. Each read would also send its probes at a different time, so LoonFS would need rules for which response confirms what, for a response that arrives too late, for concurrent reads that share one probe, and for a successor manifest that the process published itself.

LoonFS avoids those rules by keeping one view per process, confirming the view with one procedure, and letting most reads use the view as it is.

## One view per process

A process keeps one view of a namespace. In a process with the namespace's open writer session, once the session has published, the view is the session's [writer position](../specs/glossary.md#writer-position): the head that the session plans its next commit against, the manifest that head was read against, and the projected WAL tail above that manifest. Otherwise (in a process without the writer session, or before the session publishes, or after it's fenced or closed), the view is the read cache's cached view: a manifest and the head replayed from the WAL above it, with the projected tail cached under that head's key. This note calls either one the process's "view". It's the state that the process's reads start from, not a [read view](../specs/glossary.md#read-view), the state that one read sees.

A cached view records two times:

- The "confirmation time" is when a store observation last confirmed the head. That's the discovery that loaded the head, or the last refresh, which applies any new WAL objects that it finds.
- The "check time" is when a store observation last confirmed that the view's manifest has no successor.

A position records its check time, which is also its confirmation time. The session's check sets it, when the check finds no successor. A new position takes its check time from the last check of its manifest, which is the check of the discovery that loaded the position or the check after the session's fence put (see [Writer ownership](../specs/format.md#61-writer-ownership)), or from a later check by the session. A publish doesn't confirm the position's head, because a successful put confirms the WAL tip and nothing about the manifest, and another writer has to publish a claim manifest before it can commit, so for a position the check is what confirms the head.

Every check of a view's manifest sends the successor probe and then reads the [manifest boundary](../specs/glossary.md#manifest-boundary), because a successor published after the previous check might already have been deleted. Garbage collection raises the boundary before it deletes a manifest, so if the view's manifest is at or below the boundary, LoonFS reloads the view by discovery, however long ago the view was last checked (see [Replaying the visible WAL](../specs/format.md#42-replaying-the-visible-wal)). In the writer's process, the session settles its position instead (see [The writer's session and its position](#the-writers-session-and-its-position)). An `eventual` read doesn't use a cached view without a request once the view's check time is [`READ_REVALIDATION_BOUND_MS`](../specs/glossary.md#revalidation-bound) old, so the content that the view refers to stays until a download URL that the read issues expires. A view's manifest can also be replaced while the view is fresh, and garbage collection keeps only the segments of the current manifest and of manifests that snapshots keep. So a read on a replaced manifest can find a segment missing. The load that finds the segment missing checks whether a newer manifest replaced the manifest, so every operation that reads the manifest's rows makes the same check. When a newer manifest replaced the view's manifest, an ordinary read runs again from the current manifest, confirmed as a `strong` read confirms it, up to eight attempts in all, and a read view returns `store_contention`, so the caller captures a new view and reads again from current state.

While a session has a position, LoonFS doesn't copy the position into the read cache. When the session closes, the position becomes the read cache's view, with both of the view's times set to the position's check time, so the next read starts from a head at least as new as any head that a read from the position returned. When the session drops its position, or is fenced, the position's WAL tail goes into the read cache and the cached view is dropped, so the next read loads the namespace by discovery.

## One refresh procedure

A "refresh" confirms the view in a process without the writer session. A refresh:

1. Takes its observation time before it sends anything.
2. Sends the "WAL probe", a GET of the WAL number after the view's tip, and applies each WAL object it finds until a number is missing.
3. If the view's check time is older than the manifest check interval (`manifest_revalidation_interval_ms`, 1,000 ms by default), sends the "successor probe", a HEAD of the manifest number after the view's manifest, after the WAL probe's responses arrive.
4. If the successor probe found nothing, reads the manifest boundary, with a conditional read when the view keeps the boundary's version. If the read fails, the refresh returns the error to the read.
5. Runs discovery instead if it finds a successor, a missing WAL number below a present one, a WAL object with another writer epoch, or a boundary at or above the view's manifest. Discovery finds the newest manifest from the manifest boundary (see [Resolving the metadata basis](../specs/format.md#41-resolving-the-metadata-basis)) and replays the WAL above it.
6. Otherwise, moves the confirmation time to its observation time, with the head at the last WAL object it applied, and moves the check time there too if it sent the successor probe.

The WAL probe comes first because a fold can move a WAL object above the view's tip into a newer manifest, and garbage collection can then delete that WAL object. A successor probe sent after the WAL probe finds that newer manifest, or the boundary read finds that garbage collection deleted that manifest too. If the successor probe came first, the WAL probe could find nothing where the deleted WAL object was, and the view would miss the commits in that WAL object.

One refresh runs per namespace per process at a time. A read that needs a refresh while one is in flight waits for that refresh, because it might have sent its probes before the read started. After that, an `eventual` read takes the view if the refresh confirmed it within the maximum staleness, and any other read shares the next refresh, which every read that arrives during the first refresh shares. A refresh that finished before a `strong` read started doesn't serve that read, and a wave of concurrent `strong` reads costs at most two refreshes.

Why one procedure and not a probe per question? Both probes ask one question (whether the view is current), and the rules about which response confirms what are needed when the probes are sent from different places at different times. A refresh sends both probes from one place, with one observation time, so one rule covers both responses.

## What a read promises

A live read is either `eventual` or `strong` (its [consistency](../specs/glossary.md#consistency)):

- `eventual` (the default): the read uses the view as it is while the view's confirmation time is younger than the runtime's maximum staleness, and otherwise it confirms the view first (with a refresh, or for a position, with the session's check). The maximum staleness is 1,000 ms by default, and a host can set it per runtime, up to the revalidation bound.
- `strong`: the read confirms the view first, so it sees every commit acknowledged before the read started.

An `eventual` read sees every commit acknowledged before the view's confirmation time, and can miss commits acknowledged since. Both consistencies see every commit that this process acknowledged, because the writer position moves before the acknowledgement. Neither consistency returns an older head than a read that completed earlier in the same process, because a refresh replaces the view only with a newer one.

In the writer's process, an `eventual` read starts from the position and sends no request while the position was confirmed within the maximum staleness. The position includes this process's own commits, and all a request could add is another writer's claim, which the session's check finds once the maximum staleness has passed. A `strong` read waits for the session's check, so it sees another writer's claim before it reads (see the next section).

A process drops its view when it deletes the namespace, when a mutation's outcome is unknown, and when it finds its writer session fenced, because it can't tell how those events moved the head. The next read loads the namespace by discovery, with either consistency, so a read that follows one of those events in the same process sees the result. A refresh that started before the drop doesn't install its view when it finishes, because it might have read the namespace before the event. A manifest that a publication of the session's lane publishes moves the writer position onto the manifest, with the publication's check of the manifest, whose check time is the publication's start, because no manifest followed the manifest then. A check of an earlier manifest counts too: if no manifest followed manifest 7 when a check began, then none followed manifest 9 either, because manifest 9 was published after that check began. The same manifest drops the cached view, unless the cached view is already on that manifest or a later one, in which case it takes the publication's check. A fold in a process whose session has no position, which finds the newest manifest current without publishing, confirms the cached view in the same way, so it costs the next read no request. A read from a checked writer position doesn't change. A read from the cached view runs one discovery: in a process without the writer session, and in the writer's process while the session has no checked position, which is before the session's first commit stores a position, after the session drops its position (after an unknown outcome, for example), and after the session is fenced. The session's claim builds on the cached view's manifest when no writer has claimed the namespace at that head, so after the drop the claim finds the newest manifest from the store first. A fork that has to fold an aged source tail folds it through the process's fold path, so the fold's publication moves the source's position and drops the source's cached view, as any fold does. The snapshot records that the fork then writes aren't part of a view, so the fork moves neither the position nor the cached view. The process's view of the new namespace is the active manifest that the fork published, with an empty WAL tail, and a create makes its published manifest 2 the process's view in the same way. So the first read in the process doesn't run discovery, and the session's first commit builds its claim on that manifest without a request first. A create or a fork that finds the namespace already active, because another call published the active manifest first, installs no view of the namespace, so the process's first read of the namespace runs discovery. In a process without the writer session, a read that checks authorization or a receipt before a write confirms the head whatever the caller asked for, because the check is part of the write. In the writer's process, a check before a commit reads the position as it is, because the position includes every access change and receipt that the session committed, and another writer's takeover fences the session at the commit's own publish. A check before a snapshot change or a fork, which the session doesn't publish, confirms the head in either process.

A pinned read (through a snapshot) has no consistency, because the snapshot selects its state. In Rust, a read takes its consistency from the handle it goes through. A new `Namespace` handle reads `eventual`, `Namespace::strong` returns a copy that reads `strong`, and a read view captures the head at the consistency of the handle that captured it.

Why is `eventual` the default? A read that follows a write in the same process already sees the write. A read that follows a write in another process is the case that needs a request, so that read asks for `strong`. A client that changes a permission through one server and reads through another passes `strong` on that read. A request whose cursor, `after_seq`, or `to_seq` is ahead of the head that an `eventual` read would read makes LoonFS confirm the head, so a poller that learned its `after_seq` from a fresher read doesn't have to pass `strong`. A process that opens a namespace for the first time loads it by discovery, which is as fresh as `strong`. Other reads send no request within the maximum staleness. A deployment whose readers always follow writes in other processes sets the server's maximum staleness to zero, and pays a request on every read.

Why a maximum staleness and not an interval alone? The staleness is the promise that an `eventual` read makes. A view that nothing has read for a minute isn't refreshed every second in the background, and the first read after that minute refreshes it, so an idle process sends nothing.

## The writer's session and its position

The position belongs to the writer session, and only the session's queues (the commit queue and the publication lane) change it. A commit moves it onto the commit. A publication of the lane (a fold, a compaction, an extension's publication, or a change of the retention window) moves it onto the manifest that the publication published. The "writer's load" (a discovery of the namespace from the store under the session's writer epoch, which returns `writer_fenced` after another writer's claim) loads it again. The session also drops the position when it's fenced or closed. A read never moves the position onto a manifest that the read found, and never drops it. The copy of the position that reads start from follows the session's newest published manifest, as described below.

Why can't a read move the position itself? Only the namespace's current writer publishes its manifests, one at a time through its lane. So a manifest after the position's is either the session's own publication between its put and the moment the session records it, or another writer's claim. In the first case the session is about to move the position, and in the second the session has to find the claim, so a read that found the manifest asks the session to "settle" its position:

1. If the position follows a manifest above the one that the read found replaced, the newer manifest was the session's own, and the session is done.
2. Otherwise, the session waits for its publication lane, so a publication in flight records its manifest, and tests the position again. The session hasn't locked the engine at either test, so no commit waits.
3. Otherwise, the session locks the engine, and while the session keeps its writer epoch and a position on the replaced manifest or an earlier one, it drops the position and runs the writer's load, which fences the session after another writer's claim. The session never claims here, so a read never causes a claim.

A manifest that this process publishes doesn't wait for a commit whose WAL put is in flight. The session keeps the newest manifest that the process published for the namespace, and records each one as soon as its put and its boundary read succeed. The engine's position still changes on the engine's turn: both copies of the position (the engine's, and the one that reads start from) move up to that manifest at once when no commit has the engine, and when the commit in flight releases the engine otherwise. Until then, a read moves its own copy up when it starts. So a commit that planned from the older manifest doesn't undo the newer one when it puts the position back, and a read in the process never starts from a manifest below one that the process published. (Only the manifest under the position changes this way. A commit appends above the position's tip and a fold cuts the tail below it, so the order in which the two arrive doesn't change the result.)

The position is a view like any other, and the same two rules cover it, with the session's check in place of a refresh. So an `eventual` read past the maximum staleness, and every `strong` read, runs the session's check and waits for it. As with a refresh, one check runs at a time per session, and a read that needs one waits for the check in flight and then shares the next one, so a wave of concurrent `strong` reads costs at most two checks. The manifest check interval doesn't apply to the position. A read waits for a check once the maximum staleness has passed since the position's check time.

The session's check:

1. Takes its observation time, and sends one HEAD for the next manifest number.
2. If the HEAD finds no successor, reads the manifest boundary, with a conditional read when the position keeps the boundary's version. If the boundary read fails, the check returns the error to the read that started it.
3. If the HEAD found a successor, or the position's manifest is at or below the boundary, the session settles its position and the check runs again on the position that the session then has. A settle that fences the session leaves it without a position, and the read starts from the read cache's view, as a read in a process without the session does.
4. Otherwise, records the check and the boundary, so the position's check time becomes the check's observation time, and the read starts from the position.

The session settles the position after every check that finds it replaced. For example, if the position is on manifest 10, the session's fold has put manifest 11 and hasn't recorded it, and another writer then claims manifest 12, the first check finds 11, and the settle waits for the fold, so the position follows 11. The second check finds 12, and the second settle finds no newer manifest of the session, so the writer's load finds the other writer's claim and fences the session. The check runs at most eight times (`MAX_CONTENTION_ATTEMPTS`). A read whose last check still doesn't confirm the session's position loads the namespace's head as a `strong` read does, and never takes the read cache's view inside its staleness, because that view can be older than commits that the session acknowledged. The check runs on a position of any age, and it doesn't drop a position because of the position's age.

So in the writer's process, a check costs one HEAD and one conditional boundary read. A check that coincides with the session's own publication waits for that publication's boundary read and costs one more HEAD and boundary read, and no commit waits for it. The first check after another writer's claim fences the session with one writer's load, and later reads cost what they cost in a process without the session. A session with no reads sends no check, and a session under `eventual` reads sends one check per maximum staleness. No timer is involved, because a read runs the check.

For `eventual` reads in the old writer's process, the takeover window is the maximum staleness. For example, after another writer takes over, an `eventual` read there that starts within the maximum staleness of the position's last check returns the old writer's head. The first `eventual` read past that staleness waits for the check, finds the new writer's claim, fences the session, and reads the new writer's head from the store, and a `strong` read does so on that read.

Why does an `eventual` read in the writer's process wait for the check only past the maximum staleness, and not on every read? A check there can find only a takeover, and the staleness bounds how late the read finds it. Running the HEAD as the session's check keeps it off the other reads' latency, and keeps the ordering rules between reads, checks, and publications off the read.

In the writer's process, `eventual` reads cost one check (a HEAD and a conditional boundary read) per maximum staleness. With the default maximum staleness of 1,000 ms, the first `eventual` read after an idle second waits for one check. The session runs one check at a time, so the reads that need a check share it.

## What the format and API specs say

The format's requirements cover discovery, the WAL checks, the boundary read after each successor probe, the revalidation bound, and the check after a fence put. [Replaying the visible WAL](../specs/format.md#42-replaying-the-visible-wal) describes how the reference runtime applies them:

- The two warm-read probes and the boundary read, which the runtime sends in that order as one refresh.
- `eventual` warm reads, which send no probe while the tip's confirmation is younger than the maximum staleness.
- Reads from the writer position, which the session checks with the successor probe and the boundary read, with the maximum staleness in place of the manifest check interval, and which the session settles when the check finds the position's manifest replaced.
- The takeover example, in which a `strong` read finds the new writer's claim before it reads.

[Reference-implementation sizing and admission defaults](../specs/format.md#c4-reference-implementation-sizing-and-admission-defaults) lists `max_staleness_ms` next to the manifest check interval, and says that the maximum staleness applies to the last successor check of a writer position.

In the API specification, [Read consistency](../specs/api.md#read-consistency) makes `eventual` the default in the Rust API, the HTTP API's `consistency` parameter, and the reference server. It explains `strong` as a setting of the handle that a read goes through (a request parameter over HTTP) with the three cases above, and describes how the session's check confirms the position. The reference server's `max_staleness_ms` defaults to 1,000 ms, and a setting of zero makes every read confirm the head. The glossary's entries for [consistency](../specs/glossary.md#consistency) and the [writer position](../specs/glossary.md#writer-position) describe the same rules, and the [architecture overview](../specs/architecture.md) describes the probes that confirm a cached view.

## Alternatives considered

Make `strong` the default, and send each read's probes from the read. Every reader process then pays a request per read to confirm a head that rarely moves, so a walk over many files, or a burst of concurrent stats, sends one GET per read.

Poll every open namespace on a timer (for example, every second in the writer's process and every ten seconds in a reader process). A timer keeps a view fresh with no read in flight, but it costs a request per interval per namespace whether anything reads or not, so a process with a thousand open namespaces sends a thousand requests per interval.

Poll only, with no `strong` reads, so a reader lags by up to its poll interval, and a read can't see a write made in another process until the next poll. It's simpler by one setting, but it can't serve the one case that needs a request, a read that follows a write in another process. The `strong` setting keeps that case at one request, on the reads that ask for it.

Share one probe between concurrent reads, so that the read that starts the probe waits for it and later reads start without it. It keeps the probe on the read's path and needs a rule for every overlap of a read, a probe, and a publication. Under that design, a read's probe that overlaps a fold can drop the writer position.

Send a notification from the writer to readers in other processes, through an object that the writer writes on every commit. This adds a PUT to every commit to save a GET on every read, and it helps only when reads outnumber writes.
