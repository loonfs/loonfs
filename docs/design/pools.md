# Pools

This note describes where LoonFS stores content objects and upload records, and how they're collected. A "pool" is a set of namespaces that share one set of content objects, together with the key prefix that stores those objects. Every namespace belongs to exactly one pool, and every manifest records that pool's ID. A fork joins its source's pool, so a fork and a merge share content without copying bytes. A pool's content is stored under the pool's own prefix, and a collection of the pool, which is a job of its own, deletes the pool's unreferenced content. So no namespace's prefix stores another namespace's content, and no namespace's retirement deletes content.

## The problem

This section describes the problem that pools solve.

A [content reference](../specs/glossary.md#content-reference) contains a content ID, a size, and a checksum, and a reader builds the keys of a [chain](../specs/glossary.md#chain)'s objects from the reference. Nothing in the reference says which namespace wrote the bytes, and a read doesn't need that information. A [fork](../specs/glossary.md#fork) inherits its source's references, and a [merge](../specs/glossary.md#merge) adds a fork's references to another namespace, so namespaces that fork and merge refer to the same content objects. Some prefix has to store those objects, and some [collection](../specs/glossary.md#collection) has to delete them once no namespace refers to those objects.

If each namespace stored the content it wrote under its own prefix, an object that two namespaces reference would be read by both, but the writer's collection alone would protect the object. A fork snapshot makes that sharing safe in one direction, from a fork to its source. Every other case, such as a merge into the source of content that the fork wrote, would need a snapshot in that direction too, or a copy of the bytes under a new content ID. A copy stores the same data twice, and every reader that already had the first object misses its cache.

If one namespace's prefix stored the shared content instead (for example, the prefix of the namespace that was created without a source), that namespace's lifecycle would depend on data that other namespaces wrote. Each fork keeps a fork snapshot on its source, and a tombstone can't be [retired](../specs/glossary.md#namespace-retirement) while a snapshot is on it, so that namespace would be retired after every fork of it and every fork of those forks. Its collections would have to keep running after it's deleted, because no other collection would delete the shared content, and its retirement would delete the content of every namespace that shares the prefix. The shared content would have no ID of its own, so a collection of that namespace would report the content of every namespace that shares the prefix together with the namespace's own metadata.

## The design

This section describes pools and pool records, the creator of a chain, how a namespace is created, the pool's collection, and the API.

### Pools and pool records

A pool's ID (`pool_id`) is `pool_` followed by the 26-character body that every generated LoonFS ID has (see [Numbered objects and generated IDs](../specs/format.md#23-numbered-objects-and-generated-ids)), for example `pool_3s0drmj8em84yb4mnetqkz2j0x`. Every manifest records the namespace's pool (`pool_id`). A [namespace](../specs/glossary.md#namespace) created without a source records a pool ID that its create call generates, and a [fork](../specs/glossary.md#fork) copies the value from the source manifest that the fork snapshot keeps. The value can't change. A "member" of a pool is a namespace whose manifest records that pool, until the namespace is [retired](../specs/glossary.md#namespace-retirement).

A pool stores these objects under its own prefix:

```text
pools/{pool_id}/pool.json
pools/{pool_id}/content/{content_id}
pools/{pool_id}/content/{content_id}-{start:020}-{end:020}
pools/{pool_id}/uploads/{upload_id}.json
pools/{pool_id}/uploads/{upload_id}.outcome.json
pools/{pool_id}/temporary/{temporary_id}
```

A "pool record" (`pool.json`) is written once, when the pool is created. It records the pool's ID, the namespace that was created with the pool (`first_member_namespace_id`), and the creation time (`created_at_ms`), which the create call takes from its request clock. That namespace is the pool's first member. The rest of the prefix stores the pool's [content objects](../specs/glossary.md#content-object) and span objects, the session records and outcome records of its [upload sessions](../specs/glossary.md#upload-session), and [temporary objects](../specs/glossary.md#temporary-object). Every assembly writes a content object, so every temporary object is stored under a pool's prefix. Everything else stays under the namespace's own prefix: WAL objects, manifests, the manifest boundary, snapshots, metadata segments, and extension segments.

So LoonFS stores two kinds of data in two ways. Data keyed by content identity is stored once for each pool and collected by reachability from the members' roots. Data keyed by namespace state is stored under each namespace's prefix and protected by snapshots. A fork reads its inherited segments through its fork snapshot, and a compaction writes its output under the compacting namespace's prefix.

A content reference contains a content ID, a size, and a checksum, and no pool, namespace, or path. A reader builds the object key from its own manifest's `pool_id` and the content ID, so one reference identifies the same object in every member of a pool. An [extent filter](../specs/format.md#extent-filter) records object keys with the pool's content prefix removed, so a segment that any member wrote matches the keys in the pool's content listing.

Inside a pool, a fork and a [merge](../specs/glossary.md#merge) use references and copy no file bytes. No operation adds a reference to another pool's content, and content moves between pools by an upload (see [Cross-namespace copies and moves](../specs/format.md#97-cross-namespace-copies-and-moves)).

For example, creating `main` generates `pool_3s0drmj8em84yb4mnetqkz2j0x`. Forking `main` into `sandbox`, and `sandbox` into `trial`, writes no pool key, and all three manifests record that pool ID. A file that `sandbox` uploads is stored at `pools/pool_3s0drmj8em84yb4mnetqkz2j0x/content/con_014d2pf2dbsqqg28t5cy4tqkff`, and after `sandbox` is merged into `main`, a revision in `main` refers to the same object.

Why does a pool have its own ID and prefix instead of using a namespace's? If one namespace's prefix stored the content of every member, that namespace would have to be retired last for a reason that has nothing to do with its own data. Its collections would have to keep running after it's deleted, and its retirement would delete every member's content. With a pool prefix, no namespace stores another namespace's content, and no namespace's collection or retirement acts on that content.

### One creator per chain

A chain's [creator](../specs/glossary.md#chain-creator) is the namespace whose commit started the chain, and the creator's commits are the commits that append to the chain in place. The chain's layout records the creator next to its extents. A copy or a restore of a chain that another member created includes the chain's layout in its WAL delta, so the layout row that replay writes from the delta records the same creator. The creator is a fact about the chain, like its extents, so the layout describes the whole chain. When any other member of the pool appends to the chain, LoonFS starts a new chain whose layout lists the first chain's extents as [shared base extents](../specs/glossary.md#extent), followed by the appended bytes. The new chain's creator is the appending namespace, so that namespace's later appends extend the new chain in place.

For example, `main` creates `/build.log` and appends to it three times, which extends one chain under the pool's prefix. `sandbox`, a fork of `main`, appends to the file. `sandbox` isn't the chain's creator, so its append starts a new chain whose layout lists the first chain's extents and the appended bytes, under the same prefix. The next append in `sandbox` extends the new chain. Later appends in `main` extend the first chain, and neither namespace writes a key that the other could write.

Why can't every member append to a chain in place? Every member writes under the same prefix. Two members that appended to one chain from the same length would write a span object at the same key with different bytes, and their layout rows would describe one content ID as two different byte sequences. The longest layout rule, which picks the newest row among the longest layouts of a chain, depends on every layout of a chain being a prefix of the longest one. One creator per chain keeps every layout a prefix of the longest one. The rule costs a content ID and a layout row for each other member that appends to a chain, and no bytes, because the new chain shares the first chain's extents.

### Creating a namespace

To create a namespace without a source, LoonFS:

1. Generates a pool ID and builds the first manifest, which records that pool ID (see [Publishing a manifest](../specs/format.md#72-publishing-a-manifest)).
2. Finds the newest manifest for the new ID (see [Creating a namespace](../specs/format.md#91-creating-a-namespace)). If it finds one, or finds that the namespace is retired, the call writes nothing. An active namespace returns `namespace_exists`, and a tombstone or a retired namespace returns `namespace_deleted`.
3. Writes the pool record with put-if-absent.
4. Writes manifest 1 with put-if-absent, and reads the manifest boundary after a put that succeeds.
5. If another call's manifest 1 exists, or the put succeeded at or below the boundary, returns `namespace_exists` or `namespace_deleted`, and deletes its own pool record when the namespace's current manifest records another pool. That deletion is best effort.

The pool record is written before manifest 1, so every pool that a manifest records has a pool record. The pool record is written after the lookup, so a create call for a namespace that already exists ends at step 2 and writes no pool record. After a put with an unknown outcome, the call reads the pool record back and sends the put again if the record isn't stored (see [Immutable writes and retries](../specs/format.md#32-immutable-writes-and-retries)). If the record still isn't stored, the call ends with the error and doesn't write manifest 1. The pool's collection deletes a pool record that the put left behind. A pool ID is generated by one create call, so no other call writes that pool's record. A namespace writes under a pool's prefix after a manifest records the pool, so if the create call fails, its pool record is the only object under the pool's prefix.

A call whose manifest put has an unknown outcome leaves its pool record in place, because the manifest might have been written. If the manifest wasn't written, the pool's collection deletes the pool record after its creation grace (see [The pool's collection](#the-pools-collection)). The call reads its request clock once, when it starts. That reading is the pool record's `created_at_ms`, and the call's metadata publication budget starts at that reading. So a create call ends inside the pool record's creation grace.

A fork writes nothing under the pool's prefix when it's created. Its first manifest copies the source's `pool_id`, and its installation makes the requests in [Forking a namespace](../specs/format.md#92-forking-a-namespace). Outside the fork's own prefix, the fork snapshot on the fork's source is the only record of the fork.

Why does a pool ID change how a create resolves an unknown outcome? After a manifest put with an unknown transport outcome, the publisher reads the manifest at that number. Identical bytes confirm the attempt's own success when the manifest refers to an object that's unique to that attempt. A first manifest without a pool ID wouldn't refer to such an object, because two plain creates with the same request would build the same bytes (see [Conflicting and unknown installations](../specs/format.md#93-conflicting-and-unknown-installations)). A plain create's first manifest contains a pool ID that this attempt alone generated, so identical bytes confirm the create, in the same way that a generated fork snapshot ID confirms a fork's first manifest.

Why isn't the pool record written by a fork? The fork snapshot already records the fork, and its ID is set by the fork's manifest 1, so every call that finishes the fork writes the same snapshot. A second record for each fork would have to be kept in step with the snapshot by every fork call and every retirement.

### The pool's collection

A collection of a pool deletes the pool's unreferenced content objects, upload records, and temporary objects. It's a job of its own, separate from the collection of any namespace. The collection reads its clock once, when it starts, and every age and deadline check uses that reading. The pool's collection:

1. Reads the pool record. If the pool has no pool record, the collection returns `pool_not_found` and deletes nothing.
2. Reads the current manifest of the pool's first member (found from its manifest boundary, see [Resolving the metadata basis](../specs/format.md#41-resolving-the-metadata-basis)). If that namespace is retired, the pool has no members, and the collection continues without member roots. If the namespace has no current manifest and isn't retired, or its current manifest records another pool, the pool has no members because its create call failed. The collection then follows the rules below for a pool whose create call failed, and lists nothing.
3. Lists the pool's upload sessions.
4. Reads the first member's roots: the layout segments of its current manifest, the content IDs of its WAL tail, and its snapshot listing with the manifests that its snapshots keep.
5. Finds the other members by walking fork snapshots, and reads the same roots for each member. Each fork snapshot in a member's snapshot listing adds the snapshot's target as a member.
6. Reads the extent filter of each distinct layout segment that the members' manifests list, and lists the pool's content prefix once. It deletes each content object that no root protects, once the object's provider age is at least the [grace window](../specs/glossary.md#grace-window).
7. Deletes the pool's temporary objects that are older than the grace window, and applies the rules in [Upload-session cleanup](../specs/format.md#116-upload-session-cleanup) to the pool's session records.

These rules are the same as in [Content roots](../specs/format.md#119-content-roots), applied to the members of a pool:

- The sessions are listed before any member's WAL tail is read, for the reason in [Content collection](content-collection.md#why-the-roots-are-enough).
- The collection reads each member once, and it has to read every member's roots within 12 hours (`POOL_ROOTS_READ_BUDGET_MS`), or it deletes no content objects in step 6. It reports `content_deletion_pool_budget` in `skipped`, and it still lists the content prefix once to measure the pool's stored bytes.
- If one member's roots can't be read (for example, its manifest fails verification, or it records another pool), the collection deletes no content objects in step 6 and reports `content_deletion_unreadable_member` in `skipped`. Other pools are unaffected.
- A member's content references are roots until the member is [retired](../specs/glossary.md#namespace-retirement), which is when the member's own collection raises the member's [manifest boundary](../specs/glossary.md#manifest-boundary) to retired. The pool's collection reads a deleted member like any other member, and the tombstone's layout segments are roots. A member that the walk finds through a fork snapshot stays a member until its own collection retires it, which deletes that fork snapshot first.
- A member whose boundary is retired has no roots and no forks.
- A [fork snapshot](../specs/glossary.md#snapshot) whose target has no manifest, whose target is retired, or whose target is initializing, is skipped.

The pool's first member has no fork snapshot, so its retirement raises its boundary to retired and deletes nothing. The first member is eligible for retirement when its tombstone's retirement deadline has passed and no snapshot is on it (see [Retirement](../specs/format.md#95-retirement)). The pool's collection doesn't decide this for itself. The first member's own collection retires it, and the pool's collection finds the retired boundary when it looks for the first member's newest manifest. A retired first member contributes no roots. Each fork keeps a fork snapshot on its source, so the first member can be retired after every other member is retired. From then on the pool has no members, and no root protects any of its content. The ordinary age rule deletes every content object and every temporary object, and the rules in [Upload-session cleanup](../specs/format.md#116-upload-session-cleanup) delete every upload record. A completed session's record protects its content in the collection that deletes the record, so a later collection deletes that content. No rule deletes a pool's content in one step.

A pool also has no members when its create call failed, or when another create call for the same namespace ID succeeded first. The collection finds this case in step 2, when the namespace that the pool record identifies has no current manifest, or has a current manifest that records another pool. The "creation grace" is the grace window after the record's `created_at_ms`, and it covers a create call that's still running. While the pool record is inside its creation grace, the collection can't tell a failed create from a create call that's still running, so it deletes nothing, and it reports the end of the creation grace in `next_reclamation_at_ms`. After the creation grace, the collection deletes the pool record, lists nothing, and ends. After a failed create, the pool record is the only object under the pool's prefix, so nothing else is left to delete.

The collection deletes the pool record of a failed create, but not the record of a pool whose first member is retired. That pool keeps its pool record, and each later collection of the pool finds no member roots and applies the same rules.

For example, suppose that `main`, `sandbox`, and `trial` are all deleted. `trial` is retired first, which deletes its fork snapshot on `sandbox`, and then `sandbox` is retired, which deletes its fork snapshot on `main`. Once `main`'s own collection retires `main`, a collection of `pool_3s0drmj8em84yb4mnetqkz2j0x` finds no member roots. It deletes every content object and temporary object whose provider age is at least the grace window, it deletes the pool's upload records under the rules in [Upload-session cleanup](../specs/format.md#116-upload-session-cleanup), and it keeps the pool record. If that collection deletes the record of a completed session, the session's content is deleted by a later collection of the pool.

A namespace's own collection covers its manifests, WAL objects, metadata and extension segments, and snapshots. It reads the namespace's current manifest, lists its snapshots, reads each snapshot record, and loads the manifests that the snapshots keep, and it makes no request under `pools/`. Retiring a fork deletes the fork snapshot on its source, and every retirement raises the namespace's boundary to retired. Later collections of a retired namespace delete every object under its prefix except the boundary object, and no namespace's collection deletes content.

Why does the collection delete nothing when the pool record is missing? The pool record is how the collection finds the members. Without it, the collection can't tell a pool with no members from a pool whose members it can't find, and deleting content in the second case would lose data.

Why doesn't retirement delete the pool's content in one step? Once the pool has no members, the ordinary rules already delete the pool's content, upload records, and temporary objects, so a separate rule would be a second way to delete content.

Why does a pool keep its pool record after its first member is retired? A delayed abort or completion can create an outcome record after garbage collection deleted the session's records (see [Upload-session cleanup](../specs/format.md#116-upload-session-cleanup)), and by then every other object under the pool's prefix might be deleted. A later collection deletes that outcome record under its age rule, and that collection reads the pool record to find that the pool has no members.

### The API

`NamespaceMetadata` includes the namespace's `pool_id` (see [`GET /v0/namespaces/{ns}`](../specs/api.md#62-get-v0namespacesns)). The create and fork requests have no pool field.

A maintenance job can run on a pool as well as on a namespace. `POST /v0/maintenance/pools/{pool_id}/jobs` (operation `run_pool_maintenance_job`) with `kind` `gc` runs one collection of the pool, as `POST /v0/maintenance/namespaces/{ns}/jobs` runs a job on a namespace. The route has the same retry class and deadline exemption as the namespace route. A pool with no pool record returns `pool_not_found` (404).

A pool's result includes `pool_id`, the `deleted` counts (`content_objects`, `upload_sessions`, and `temporary_objects`), the `retained` counts, `listed_bytes` for the objects under the pool's prefix that the collection listed, `next_reclamation_at_ms`, and `skipped`. The result doesn't report the deletion of a pool record. A pool's collection reports `content_deletion_pool_budget` in `skipped` when it couldn't read every member's roots in time, and `content_deletion_unreadable_member` when it couldn't read one member's roots. A namespace's `gc` job reports no content objects, upload sessions, or temporary objects, its result has no `skipped` list, and its `listed_bytes` covers the namespace's own prefix.

The reference server's [sweep](../specs/glossary.md#sweep) collects pools. A sweep runs every listed namespace's steps, and then runs a collection of every pool that it lists under `pools/`, with the same concurrency. A session's collection step collects the namespace and nothing else, so a pool's content, upload records, and temporary objects are collected by sweeps. The server records a failed collection of a pool under the call name `pool_gc`, and the next sweep tries the collection again. A listed pool that returns `pool_not_found` isn't a failure, because a create call can delete its pool record between the listing and the collection.

An application that meters storage reads a pool's stored bytes from the pool job's `listed_bytes`, and a namespace's metadata bytes from the namespace job's `listed_bytes`.

Why doesn't a create request include a pool? A pool ID is generated by one create call, so the pool record identifies the pool's one member without a source, and the collection finds every other member through fork snapshots. If a create request could add a namespace to an existing pool, each namespace created that way would need its own record (see [Alternatives considered](#alternatives-considered)).

## Costs

This section lists what the design costs, compared with a pool stored under its first member's prefix (the first item in [Alternatives considered](#alternatives-considered)).

- Creating a namespace without a source makes one more PUT request, for the pool record. A fork makes no more requests, and neither does a create call for a namespace that already exists.
- There are two kinds of collection. An operator who runs `gc` jobs by hand runs one for each namespace and one for each pool. A namespace without forks is read by both collections: the pool's collection discovers the namespace's manifest, reads its WAL tail, and lists its snapshots, as the namespace's own collection does.
- The pool's collection makes one manifest discovery, one snapshot listing, and one WAL tail read for each member, including each deleted member until it's retired. A deleted member's content is deleted up to one collection of the member later than its tombstone's retirement deadline, because the member's own collection retires it first. A collection of the first member's prefix would make the same requests, with the same time limit, and one unreadable member would stop content reclamation for the whole pool in both designs until the member is repaired or deleted.
- A pool's content is deleted under the ordinary age rule by the collections of the pool after its first member is retired, and the content of a completed session is deleted by a later collection than the one that deletes the session's record. With the content under the first member's prefix, that namespace's retirement could delete all of it at once.
- Storage is measured for a pool, and a member's share of a pool's content isn't visible from object keys. Upload admission limits apply to each member, and nothing else limits a pool's content.
- A namespace can't move to another pool, because `pool_id` is set when the namespace is created.
- A failed create can leave a pool record, which stays until a collection of that pool finds the record older than its creation grace. The sweep finds such a pool by listing the pools.
- A pool whose first member is retired keeps its pool record, and a sweep still runs a collection of that pool, in the same way that a retired namespace's boundary object keeps the namespace in the sweep's listing.
- A pool's content is collected by sweeps (once a day by default), and not by a session's collection step.

## Alternatives considered

- **A pool stored under its first member's prefix.** The content of every member is stored under the prefix of the namespace that was created without a source, and every manifest records that namespace. So that namespace is retired last because of other members' data, its collections keep running after it's deleted, its retirement deletes every member's content, and the pool has no ID of its own. Another member can't take over the content when that namespace is deleted, unless a durable record says which member collects the content and the members have a way to agree on a change to that record.
- **A member record for every member.** Every namespace writes a record under its pool, and the collection lists the records once instead of walking fork snapshots. A fork then has two records of its creation, the fork snapshot and the member record. A member record's key isn't unique to one installation attempt, so the collection can't delete the record of a failed installation without risking the record of a later attempt for the same namespace ID, unless the manifest records which member record is its own, as a fork basis does for a fork snapshot.
- **Every snapshot of a pool stored under the pool's prefix.** One listing finds every member and every snapshot, which saves one snapshot listing for each member in each collection. But a snapshot protects a namespace's manifest and segments, so a namespace's own collection would list keys outside its prefix, and looking up a fork snapshot by its ID needs a listing.
- **Content stored under the namespace that writes it.** Each namespace stores its uploads and folded pieces under its own prefix. Content that one namespace wrote can be used by another namespace by copying the bytes, or by a snapshot from the reader onto the writer for as long as the reference exists. A merge then makes the destination depend on the fork, which is usually the shorter-lived of the two, so the dependency has to be ended while the destination is still in use, by copying the merged bytes and proving that no reference to the fork's objects remains.
- **Copying at retirement.** A namespace references another namespace's objects without a copy, under a snapshot from the reader onto the writer. When the writer is retired, the bytes are copied into the reader's prefix, and the reader's layouts are rewritten to point at the copies. That design needs snapshots in both directions and a publication in one namespace that another namespace's retirement triggers, and it still copies every shared byte eventually.
- **An owner namespace on every content reference.** Each reference records the namespace whose prefix stores its bytes. The reader's manifest already records the pool, so the field would repeat one value in every reference and every extent. It would also make a reference into another pool's prefix representable, and such a reference is never safe, because that pool's collection doesn't read the reader's roots.
- **Any member extends a chain in place.** Two members that appended to one chain from the same length would write span objects at one key with different bytes, and a chain would stop being one sequence of bytes. Adding a unique component to span keys avoids the key collision but not the second problem, because the longest layout rule would then pick one member's bytes for a reference that the other member wrote.
- **The first member alone extends chains in place.** A fork would start a new chain on every append, and each new chain's layout would list every earlier extent as a shared base extent. Shared base extents are never combined and don't count toward the extent limit, so a file that a fork appended to 1,000 times would have 1,000 extents.
- **One pool for every namespace in a store.** Unrelated namespaces share one collection and one content listing. One unreadable namespace stops content collection for all of them, and the collection has to read every namespace in the store within its time limit. A pool is the smallest set of namespaces that can share a reference, so it's the smallest collection domain that works.
- **A pool that the caller chooses when it creates a namespace.** A create request identifies an existing pool, so that namespaces created separately share content. A pool ID is then not generated by one create call, so the pool record alone doesn't identify every member that has no source, and each such member needs its own record with a key that's unique to one creation attempt. The design also needs a rule for which callers may add a namespace to a pool.
- **A pool that the caller creates before its first namespace.** Every create request identifies a pool, and a caller with one namespace manages a second resource that it never uses.
- **Content keyed by a hash of its bytes.** Identical uploads share one object. But a direct multipart upload has no SHA-256 of the whole object, so the key needs a second pass over the bytes or a copy after the upload. A chain's content ID stays the same while appends extend the chain, which a hash of the bytes can't do. The collection's safety also depends on each content ID being written once, and with a hash key, an upload can write a key again while a collection is deleting the object at that key.
