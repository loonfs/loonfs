# Publishing a merge through the manifest

This note proposes a second way to plan and publish a [merge](../specs/glossary.md#merge) or a replay commit of a [rebase](../specs/glossary.md#rebase), for a merge that is too large to be one WAL commit. LoonFS then has two paths for a merge:

- On the "WAL path", a merge within the bounds in [Which merges take the manifest path](#which-merges-take-the-manifest-path) is planned and committed as one WAL commit, as [Merging a fork](merge.md) and the [format spec](../specs/format.md) describe. Every merge takes this path today.
- On the "manifest path", which this note describes, a merge that the WAL path refuses as too large is planned by a second planner. That planner turns the fork's net change into the merge's deltas (the same kinds of delta that a WAL commit record contains), with placeholders for the merge's sequence and time. It derives the merge's rows from those deltas with the function that the fold uses, and writes them as metadata segments, off to the side and in bounded memory. Main's writer then publishes the segments with one manifest put that folds main's [WAL tail](../specs/glossary.md#wal-tail) and adds one [run](../specs/glossary.md#run) at the next sequence.

A merge on the manifest path is bounded by the time that its plan is allowed to take and by the memory that its plan keeps for its name changes, not by one WAL object and a memory allowance, so no merge or rebase is split into pieces. Nothing in this note is implemented.

In this note, "main" is the namespace that a merge commits into, "the fork" is the namespace whose commits the merge applies, and "the plan" is the work that turns the fork's net change into the merge's rows.

## The problem

This section describes the limits of a merge on the WAL path and what a merge at the largest allowed size does to main.

On the WAL path, a merge is one commit in one WAL object. The planner turns the fork's net change into an ordered list of operations, and main's writer plans every operation again when it publishes. The writer assigns the sequence, each delta's `delta_index`, the binding positions and versions, and the revision numbers, and it checks each operation's preconditions against main's current rows. Four limits follow.

The first limit is size. A merge has to fit in one WAL object (512 MiB) and in the "merge allowance" (`max_merge_bytes`, 512 MiB by default). The allowance charges five times the merge's planned WAL bytes, because publication builds the deltas and the WAL object while the operations are still in memory. A file create with a one-extent layout plans 5,418 bytes, so the allowance charges about 27 KB for each create, the default allowance admits about 19,800 file creates, and one WAL object fits about 99,100. The planner also refuses a range whose commits touched more than about 290,000 inodes. Each bound returns `merge_too_large` with a split hint, and the caller merges the fork in pieces.

The second limit is the writer. A merge is alone in its batch, and one worker per namespace publishes one batch at a time, so main's other commits wait while the writer plans the merge again. A merge with a subject goes through the writer's planning twice, because the planner runs the writer's planning once to check rights.

The third limit is the commit row. After a fold, a `commits` row stores the whole commit with every delta, so every reader that needs one field of a merge commit (the planner's ownership check, a retry's receipt lookup, a retention advance) decodes all of it.

The fourth limit is the tail. Until main folds, every reader of main replays the merge's WAL object. The fold then keeps the whole tail in memory with a sorted copy of each family, and no allowance charges for it.

Only the first limit returns an error. A user meets the other three as latency, memory, and read cost. For example, a merge of 99,000 file creates on a server whose allowance was raised to 2.5 GiB has a WAL object whose planned bound is about 536 MB. Main's other commits wait behind it, and every reader without that tail cached replays it until the next fold. A fork of 200,000 files can't merge as one commit, and its rebase replays in pieces, which [Merging a fork](merge.md#rebasing) says can report conflicts on names that the fork passed through.

Well within those bounds, the WAL path costs little. A small merge is one WAL put and one snapshot record put, and the lab measured it at 163 to 206 ms on S3 (see [What a small merge would cost on the manifest path](#what-a-small-merge-would-cost-on-the-manifest-path)). One namespace can commit up to about 39 such merges a second (estimated from measured commits of one file). A fold covers a small merge together with the commits around it, so the merge adds no manifest and no run of its own. So the WAL path stays for every merge within its bounds, and this design is for the merges that it refuses.

## The design

This section describes which merges take the manifest path, what the two planners have to agree on, and one merge on the manifest path, from the request to the manifest that makes it visible.

A commit goes through the log. A fold or a compaction builds immutable segments off to the side, with bounded memory, and makes them visible with one manifest publication, and a segment that never gets published is collected once it's old enough. A large merge is the same kind of work, so the manifest path builds the merge's rows as segments and publishes them the same way. A small merge stays a WAL commit, because through the manifest it would cost about 11 to 29 puts where the WAL path costs 2, and a manifest and a run of its own, as [What a small merge would cost on the manifest path](#what-a-small-merge-would-cost-on-the-manifest-path) estimates.

### Which merges take the manifest path

The WAL path refuses a merge as too large at three bounds, and each refusal returns `merge_too_large` today:

- **Touched inodes.** The planner reads the range's commits in pages of 64 and collects the inodes that they touched. It refuses the range once the set passes the number of inodes that one WAL object could change, which is 512 MiB divided by the planned size of the smallest operation that a merge can have (about 290,000 inodes). The set includes inodes that later drop out of the net change.
- **The merge allowance.** The planner estimates the merge's memory as the larger of two figures: five times the merge's planned WAL bytes, and its working memory (the touched set at 32 bytes per inode, the page of commits that it last read, and the paths that its state readers keep). It refuses the merge when that estimate is above the whole allowance (`max_merge_bytes`, 512 MiB by default). It checks after each page of commits, after each inode's plan, each time the path caches grow by 1 MiB, and for the ordered commit with its temporary moves and a replay commit's conflict report. When the publisher admits the merge's commit, it checks the WAL object and five times the planned WAL bytes again.
- **One WAL object.** The same checks refuse a merge whose planned WAL bytes, with the WAL object's overhead, are above 512 MiB (`MAX_WAL_OBJECT_BYTES`). The writer refuses the merge too when its own estimate of the WAL object, after it plans the merge's operations again, is above 512 MiB.

With the default allowance, the allowance refuses a merge before the WAL object does, at about 102 MiB of planned bytes, which is about 19,800 file creates with a one-extent layout. The WAL object refuses first only on a server whose allowance is at least 2.5 GiB. (A merge whose estimate fits the allowance, but not beside the reservations of other merges, gets `server_busy`. That error is transient, and the merge stays on the WAL path.)

The boundary between the two paths is that refusal. A merge takes the manifest path when the WAL path refuses it at one of the three bounds, at any of the checks above, and every other merge is planned and committed on the WAL path. A threshold of its own below the refusal would send merges that the WAL path commits to the manifest path, with the costs of small merges there, and a threshold above it would leave merges that neither path takes. Because the allowance is a server setting, the boundary depends on the server: a server with a smaller allowance sends more merges to the manifest path, and one with a larger allowance accepts larger merges on the WAL path, with the costs in [The problem](#the-problem) that no error reports. That's safe because the two planners produce the same result for every merge that both can take (see [Two planners](#two-planners)), so the setting changes what a merge costs and not what it does.

The WAL path's planner stops at the first bound that the merge crosses and publishes nothing, so a merge that changes paths has first spent part of one plan, bounded by the allowance. That attempt's reservation of the allowance can be close to the whole allowance, so the route releases it when the attempt returns `merge_too_large`, before the job reserves its plan memory bound. (The WAL path releases it then today, because the reservation is dropped when the plan or the publisher's admission returns the error.) The route then starts the manifest path's job for the same request, with the range that the WAL path's attempt planned (see [The request](#the-request)), and the change of path doesn't count toward the four plans that a merge can make. On the manifest path, a merge that would pass the plan memory bound or the plan budget returns `merge_too_large`, and those are the only size refusals that a caller sees.

### Two planners

LoonFS has two planners: the WAL path's planner, which [Merging a fork](merge.md#merging) describes, and the manifest path's planner, which [Planning](#planning) describes. Either one could plan a merge within the WAL path's bounds. If the two applied different rules, the same merge could commit on one path and conflict on the other, and which rules applied would depend on the merge's size and the server's allowance. So for every merge that both paths can take, the design requires that the two planners accept and refuse the same merges, with the same error and, for a replay commit, the same conflict report, and that they produce the same visible result: the same state of main at the merge's sequence through every reader, and the same events in the change feed, in the same order. (The layouts of the merged content can differ, as the table below describes, but a file's content reference and bytes can't.)

A differential test checks the requirement, and the manifest path is enabled only in a build that passes it. The test makes forks and mains with generated histories (creates, edits, moves, cycles of moves, deletes, restores, and access changes, with conflicts and with subjects whose rights differ), plans each merge and replay commit on both paths from the same inputs, and compares the outcomes. It also checks the manifest path's check against the WAL path's preconditions. For a commit to main between the plan and the publication, it runs both paths with that commit and compares the outcomes after each path's plans again (the WAL path plans again when a precondition fails, and the manifest path when the check finds an intersection). The test covers the outcome of each single merge from its inputs. The interleavings of a merge with main's commits are covered only for the orders that the test scripts, because the two paths read main at different times.

Three parts differ by intent:

- **The limits.** The WAL path has the three bounds above, and the manifest path has the plan memory bound and the plan budget.
- **The response.** The WAL path commits inside the request. The manifest path runs as a job, and its request can return a response that says the merge is running (see [The request](#the-request)).
- **The form of the commit record.** A merge on the WAL path is a WAL commit record with its merge record and conflict report, and its `commits` row stores the whole record after a fold. A merge on the manifest path stores its deltas in `commit_deltas` and its conflict report in `merge_conflicts` (see [A merge's commit record as rows](#a-merges-commit-record-as-rows)).

The two planners' rules differ in these places, and the last column says what the requirement needs in each:

| Rule | WAL path | Manifest path | What the requirement needs |
| --- | --- | --- | --- |
| The temporary name | The inode's ID, with a numeric suffix up to 8 if the name is taken at main's head or by an earlier change in the merge's order. With no free suffix, the merge fails with `invalid_request`, as it does when no order of the changes works. | The inode's ID, with a numeric suffix if the name is taken at `P`. | The manifest path takes the same limit of 8 suffixes and returns `invalid_request` when no order works, as [Planning](#planning) states. |
| The rights check | The planner plans the merge's commit as the writer does and returns the writer's error. The writer checks each operation against the state that the earlier operations leave, exempts a temporary move from `create` and `remove` on the directory that has the temporary name, and returns `inode_not_found` where the subject has no rights. | Each change that passes the conflict rule is checked against main's access rows at `P`, and against the merge's own access row for a directory that the merge creates. | The same refusals with the same error code. The test includes subjects without rights on created directories, on moves through a temporary name, and on deletes. |
| The rights of a move | For a move, the writer checks the `remove` right on the directory that the inode leaves, the `read` right on the inode, and the `create` right on the directory that it enters. It also checks the move's change of the inode's inherited rights: unless the inode's own access row is a boundary, the move fails when the access rows of the new directory would grant a principal a right on the inode that the subject doesn't have there. A move through a temporary name is checked as one move, from the directory before the first leg to the directory after the second. | The same checks for each move, read at `P`, as [Planning](#planning) states. | The same refusals. The test includes moves into directories whose access rows grant more than the subject has. |
| The conflict response | The planner classifies every inode, counts each conflicting inode once, and returns `merge_conflict` with that count and the conflict of the inode with the smallest ID, including a `subtree` conflict found after classification. | The same count and the same conflict, because classification doesn't stop at the first conflict (see [Planning](#planning)). | The same response. |
| The range of a re-plan | A later plan applies the first plan's range, so it never merges a longer range. | The job plans the range of the WAL path's attempt, and every re-plan keeps it. | The same range, so the same fingerprint. |
| Commits to main during the plan | The commit's preconditions are main's current values of the rows that it replaces, plus main's head when the merge deletes or moves a directory or moves an inode through a temporary name, so any commit to main fails such a merge. The second leg unbinds the merge's own temporary binding. | The same outcome after each path's plans again. Under a steady stream of commits, the WAL path can use its four plans and return `store_contention` where the manifest path commits, and the test allows that difference only when each of the WAL path's plans failed a precondition. |
| The fork's tail | A snapshot of the fork's manifest without a fold (unless a tail commit is more than 11 hours and 45 minutes old), and the tail's pieces written under the pool's prefix as an extent of the merge's layouts. | The fork is folded first, and the layouts come from the fork's folded rows. | The layouts of content that was in the fork's tail differ, which the requirement allows, because the content references and their bytes are the same. The test compares content by its bytes. |
| The temporary snapshots | One of the fork, for 5 minutes | One of the fork and one of main, each for the plan's budget | Nothing, because the snapshots aren't part of the merge's result. | Size and conflicts | The size bounds are checked while the merge is classified, so a range that is too large is refused for its size before its conflicts are all found. | The plan memory bound is checked as the plan runs. | Nothing, because a merge that both paths can take passes the WAL path's bounds. |

To merge a fork on the manifest path, LoonFS:

1. Starts the merge as a job in the process that received the request, once the WAL path has refused it, reserves the plan memory bound from the merge allowance, looks up the receipt for the request's commit ID, and checks the range and both retention floors, as the WAL path does. The plan needs no writer epoch.
2. Folds the fork and main, and takes a snapshot of each manifest that the folds published, which lasts the plan's budget. The head of main's snapshot is the "basis" `P`.
3. Classifies the fork's net change in inode order against main at `P`, and produces each inode's deltas. A merge that finds a conflict classifies the rest of its inodes to count the conflicts, and then returns `merge_conflict` and publishes nothing.
4. Orders the merge's name changes, assigns each delta its position, derives the rows, and writes them into segments.
5. Checks what main committed after `P` against what the plan touched, first without pausing anything. It then folds main's tail, pauses main's queue, and checks the commits that are left, up to the WAL tip. `H` is the head at that tip.
6. Puts the next manifest, which folds what's left of main's tail, adds one run at `H + 1` that lists the merge's segments, and sets the head to `H + 1`.
7. Resumes the queue. The writer's next WAL object starts at `H + 2`.

If step 5 finds a commit that changed what the plan read or replaces, LoonFS plans the merge again.

### The plan's deltas and markers

[Row families](../specs/format.md#19-row-families) says that every row is derived from a single WAL delta or commit record without reading other rows. The fold derives a delta's rows in one function (`apply_committed_wal_delta_mut` in `loonfs-core`), whose inputs are the delta and its commit's sequence, commit ID, actor, and time. So the planner's output is deltas, the eight kinds in [WAL delta kinds](../specs/format.md#wal-delta-kinds), and the merge's rows are what that function produces from them. The commit ID and the actor come from the request. Revision, attributes revision, and access revision numbers continue main's from its rows at `P`. Unbinds, revokes, and summary rows point at main's existing events where they undo or extend them.

The merge's sequence and time aren't known while the plan runs, so the plan writes a "marker" in their place. The sequence enters the rows as every row's `committed_seq`, as a bind row's `bind_position`, and as a `trash` row's `deletion_seq` for the merge's own deletions and `removed_seq` for its restores. The time enters as every history row's `committed_at_ms` and a `trash` row's `deleted_at_ms`. Some delta fields contain the merge's own sequence or time as well. A file that the merge creates, or moves and also changes, has a revision delta whose `bind_position` is the merge's own bind, and the second leg of a move through a temporary name unbinds the merge's own temporary binding. A create's `child_created_at_ms` and its revision summary's `revision_committed_at_ms` are the commit's time. The plan writes the markers in those fields too.

The marker is per field, because some sequences in a merge's rows are main's. A summary row's `bind_position` can be main's existing binding, an unbind or a revoke points at main's event, and a restore's `trash` row is keyed by the deletion's original sequence.

| Families | The merge's sequence in the key | In a merge run |
| --- | --- | --- |
| `inodes` | Not in the key | Marker in `committed_seq` |
| `direntry_binds`, `direntry_child_binds`, `revisions`, `tombstones`, `attributes`, `access`, `content_layouts` | Inverted, after the entity's ID | Marker in every row, so the stored order is the decoded order |
| `trash` | First, as the deletion sequence | Marker for the merge's own deletions. It sorts above every real sequence, and every other `trash` row in the run removes a deletion at or below `P`, so the stored order is the decoded order. |
| `commit_deltas`, `merge_conflicts` (new) | First | Marker in every row |
| `commits`, `commit_receipts`, `merges` | First or last | Written by the publication with the real sequence |

The manifest's activity counters for the merge come from the deltas, as a fold's come from each commit record.

### Planning

The fork is folded first, so the fork snapshot's manifest contains every commit in the range, the plan reads no WAL tail of the fork, and the merge writes no pending pieces. The fork's snapshot is the temporary snapshot that a merge on the WAL path takes of its fork, with a lifetime of the plan's budget (see [Budgets and collection](#budgets-and-collection)) instead of 5 minutes.

The plan also folds main and takes a temporary snapshot of the manifest that the fold published, with the same lifetime, and reads main through that snapshot for the whole plan. `P` is that manifest's head. A merge on the WAL path takes no snapshot of main, because it plans against one loaded view inside one request, and a rebase reads main's history up to the new fork's fork point through the new fork's [fork point snapshot](../specs/format.md#fork-snapshots-and-fork-point-snapshots), which is a snapshot of main. A plan that runs for hours can't use one loaded view, because a collection can delete the segments of a replaced manifest soon after it's replaced. A snapshot keeps its manifest and every segment that the manifest lists until the snapshot's record is cleaned up ([Snapshot cleanup](../specs/format.md#117-snapshot-cleanup)), whatever compaction or the retention floor does in main after `P`, so every read through it returns what it returned at the start of the plan. The plan's view of main doesn't move, and a floor advance during the plan doesn't stop it. (Main is folded first because a snapshot keeps no WAL tail, so `P` has to be a manifest's head.)

The snapshot of main is a temporary snapshot of the same kind as the fork's, an unnamed user snapshot, under the same rules. A namespace's snapshot listing shows each of the two snapshots until it expires, so for up to the plan's budget. A caller who reads one in a listing can extend it, which keeps its manifest and segments for longer and doesn't change the plan, because the plan reads it only within its budget. A caller can also fork from it, which makes a fork at that manifest, with a fork snapshot of its own. A caller can also delete it. The plan's next read through a deleted snapshot returns `snapshot_not_found`, so the merge publishes nothing and returns that error, and a retry plans again with new snapshots.

Every read that the plan makes of main is one of these, and a read through a snapshot returns each of them today:

| Read of main at `P` | What the plan uses it for |
| --- | --- |
| The newest `merges` row of the fork, and the receipt of the request's commit ID | The range rule and a retry |
| An inode's row | Whether an inode that the fork changed exists on main |
| An inode's parent binding, and the binding of a slot (a parent and a name) | Main's edges in an ordering entry, whether a name is free, and the choice of a temporary name |
| An inode's newest revision, attributes revision, and access revision | The conflict rule, and the numbers that the merge's revisions continue |
| An inode's tombstone events, compared with the view's floor | Whether a deletion hides an inode and is still in the trash |
| The walk from an inode up to the root | Visibility, the subtree check, and the access rows of the rights walk |
| A diff over the root from the fork point to `P` | The subtree check of a directory that the merge deletes or moves |
| The `commits` row at a row's `committed_seq` | Whether a row is the fork's own |

The snapshot's manifest records main's floor at `P`. Once the snapshot exists, the plan checks the fork point against that floor again and returns `below_retention_floor` if the fork point is below it, as rebase checks the fork point against the floor of its snapshot's manifest. So the snapshot keeps the newest row of each edge and inode at or below the fork point and the `commits` row at the sequence of every main row above the fork point. Every read of commit rows that the plan and the check make finds its rows, or fails at that read:

- The plan reads main's `commits` row at the sequence of each main row above the fork point, for the ownership check, through main's snapshot, and a missing row returns `namespace_corrupt`.
- The plan reads the fork's commits in the range through the fork's snapshot, and a replay reads the parent's commits at or below the new fork's fork point through the fork point snapshot. A snapshot keeps its manifest's segments, so no compaction or floor advance removes these rows during the plan.
- The first stage of the check reads main's `commits` and `commit_deltas` rows above `P` through main's current manifest, because those commits came after the snapshot. A base compaction removes commit rows only strictly below the floor, and main's floor can't pass `P` during the plan, because a retention advance can't pass a commit that is younger than the grace window of 24 hours ([Targets and the grace-window bound](../specs/format.md#targets-and-the-grace-window-bound)) and every commit after `P` is younger than the plan's budget of 6 hours. So these rows stay until the check has read them, and a missing row returns `namespace_corrupt`. A floor advance doesn't stop the first stage, because it reads no row below `P`, and condition 5 compares the floor at the end of each interval.
- The second stage reads the WAL above the tip of its fold, and no row below `P`.

A floor advance after the plan's last read is what condition 5 covers: the deletions that the plan relies on, and the merge floor rule.

The plan has two steps.

Step one classifies. The planner reads the fork's commits in pages, as today, and collects the "touched inodes", which are the inodes that the range's commits touched. It keeps them at an estimated 32 bytes each (about 32 MB per million inodes), and above a bound it writes the set as sorted chunks and merges them. Classification then runs in inode order and produces each inode's deltas, grouped by event. A "group" is the deltas of one change that the [change feed](../specs/format.md#67-change-feed) reports as one event: a create (create, bind, and first revision), a content change, a move (unbind and bind), a delete (unbind and tombstone), a restore (revoke and bind), an attributes change, or an access change. A group has no position yet. Step one keeps the groups in memory up to 16 MiB of deltas and writes the rest to temporary chunks, objects under segment keys that the age rule for unlisted segments collects. A merge whose groups fit in that buffer writes no chunk, and a merge whose groups don't fit writes them once more than a single pass would. (16 MiB is a choice, not a measurement.)

For each inode with a name change (a create, a move, a delete, or a restore), step one also keeps an "ordering entry" in memory. The entry contains the change's parent and name, the binding version that a move or a delete replaces, the inode's kind, main's edge of the inode and of the parents that the change uses, and the inode's place in the ordering's maps (which inode has the name on main, which directories that the merge creates the change needs, and whether the change still waits). An entry takes about 300 bytes plus about twice the name's length, so about 330 bytes with 13-byte names and 800 bytes with 255-byte names (estimated from the field sizes). Main's edges of the ancestors add one entry per distinct directory.

Step two orders and writes. It orders the name changes with the rules that the WAL path's planner uses ([Merging a fork](merge.md#merging)):

- A create, restore, or move into a directory comes after the create or restore of that directory.
- A change that takes a name comes after the change that frees it on main.
- A directory's delete comes after the moves of the inodes that leave it.
- A directory never moves under its own descendant.
- A delete below a directory that the merge deletes, with no moved inode between them, is left out, because the directory's recursive delete covers it.
- When moves wait on each other in a cycle, one of them first moves to a temporary name.

Step two chooses the temporary name by reading main at `P` (the inode's ID, with a numeric suffix up to 8 if the name is taken, and `invalid_request` when no suffix is free, as on the WAL path), and adds the temporary name's slot to the touched set (see [Checking what main committed during the plan](#checking-what-main-committed-during-the-plan)).

Step two then assigns positions. The groups of the name changes come first, in that order, and every other group (content, attributes, and access) follows in inode order. Each delta gets its `delta_index` from its place in that sequence. Each group gets one `semantic_operation_index`, numbered 0, 1, 2, and so on, and the change feed, diff, and the activity counters group a commit's deltas into events by this index. Two orders matter here. A slot's state is the newest row across its edges ([Directory bindings](../specs/format.md#13-directory-bindings)), so a delta that frees a name has to come before the delta that takes it. And a consumer of the change feed applies a commit's events in order, so each event has to be valid after the ones before it. The ordering keeps both.

Step two reads the groups back in inode order (from memory, and from the chunks if step one wrote any), derives each group's rows, and writes them into one segment writer per family. These are the writers that the fold and compaction use, with at most 32 puts and 32 MiB in flight. The families keyed by inode come out in key order. The slot index (`direntry_binds`), `content_layouts`, `trash`, and `commit_deltas` aren't keyed by inode, so the planner writes them as sorted chunks under segment keys and merges the chunks with the compaction's sorted iterators.

Three more parts of the plan keep sets in memory, which grow with the number of name changes or conflicts: the names that the merge's own inodes take or free, the subtree check, and a replay's skip of dependent changes.

One setting bounds the ordering entries, main's edges of the ancestors, these three sets, and the check's path set together. The "plan memory bound" (`max_merge_plan_bytes`) is 128 MiB by default (a choice, not a measurement). The plan charges each entry and each member of a set at its estimated size when the plan adds the entry or member, and a plan that would pass the bound publishes nothing and returns `merge_too_large` with the bound `plan_memory`. The rest of a plan's memory has bounds of its own: the 16 MiB buffer of step one, 32 MiB of puts in flight, the sorts' decoded input, and the touched set, which spills. A plan reserves the bound from the merge allowance (`max_merge_bytes`, 512 MiB by default) before it starts, after the route has released the reservation of the WAL path's attempt, and keeps that reservation until it publishes or stops, as a merge on the WAL path keeps its own reservation, so the allowance is the one budget for merge memory in a process. With the defaults, the allowance fits four plans at once, or fewer beside merges on the WAL path. When the allowance has no room for the reservation, the plan starts nothing and the request returns `server_busy`, which is transient, as the WAL path does when its first reservation or a growth of it doesn't fit. A server refuses to start with a plan memory bound above its allowance, because no plan could ever reserve it. An ordering entry takes about 330 bytes with 13-byte names, so 128 MiB fits about 400,000 name changes, and about 800 bytes with 255-byte names, so about 165,000, less one entry for each distinct directory on the changes' paths (estimated from the field sizes). A content, attributes, or access change takes no ordering entry. A user whose merge reaches the bound merges a shorter range of the fork, or raises the setting, and the allowance with it, on a server that has the memory.

Classification applies the conflict rule first, and then checks the subject's rights for each change that passes it, with the rules in [Merging a fork](merge.md#merging). The rights walk reads main's access rows at `P`, except for a directory that the merge creates. For that directory, it reads the access row that the merge writes, and then continues with main's rows from the first ancestor that exists at `P`, as the WAL path's writer sees the rows of earlier operations in the same commit. A move is also checked as the writer checks it: the `remove` right on the directory that the inode leaves, the `read` right on the inode, the `create` right on the directory that it enters, and, unless the inode's own access row is a boundary, that the access rows of the new directory grant no principal a right on the inode that the subject doesn't have there. A move through a temporary name is checked as one move, from the directory before its first leg to the directory after its second. So a merge with a conflict returns `merge_conflict` and no rights error, as on the WAL path, and a replay checks rights on the parts it applies.

A conflict doesn't stop classification, because `merge_conflict` reports the number of conflicting inodes and the conflict of the inode with the smallest ID, as on the WAL path. Once the plan finds a conflict, it writes no more segments, but it classifies the rest of the inodes in inode order and counts each conflicting inode once, keeping the first conflict it finds. It then runs the subtree check, which can add a `subtree` conflict for a directory that had no other conflict, and keeps that conflict instead when its inode has a smaller ID. Classification in inode order sees each inode once, so the count needs no set of its own.

A re-plan is a new plan, with a new basis, new snapshots of the fork and of main, and a new budget, but with the first plan's range, as on the WAL path. The job's first plan also keeps the range that the WAL path's attempt planned, so no plan of a merge applies a longer range than its first, and a merge of the fork that committed in between returns `merge_range_conflict`. LoonFS makes at most four plans, as on the WAL path, and then returns `store_contention` with the cause `lost_race`. A plan that doesn't finish within its budget publishes nothing and returns `merge_too_large` with a new bound, `plan_budget`. So on the manifest path, `merge_too_large` has two bounds, `plan_budget` for time and `plan_memory` for memory, and neither has a split hint. The caller can still merge a shorter range of the fork.

### Reading a merge run

A segment of a merge run is opened only through its run entry, which records the commit's sequence and time. One place in the block decoder replaces each marker with the run entry's sequence or time. A cached decoded block belongs to the run entry it was decoded under, and a reader that finds a marker without a run entry returns `namespace_corrupt` instead of the marker. A reader that seeks to a key in a merge run, or probes its filter, replaces the sequence in that key with the marker.

The design keeps one property that every reader can be tested against. A merge run's rows, read through any reader, are the rows that the fold's derivation produces from the same deltas at the run's sequence and time. A test checks it by folding the same deltas as an ordinary commit record at the same sequence in a second store, and comparing the two namespaces through every reader: seeks, scans in both directions, filter probes, compaction, the change feed, diff, and grep.

A compaction that rewrites a merge run writes the real sequence and time into its output, because the output's `run_seq` is the window's position. A fork's first manifest copies the run entry.

### A merge's commit record as rows

A merge on the manifest path has one form of commit record. The `commits` row stores the commit's header and merge record, and the deltas are rows of a new family, `commit_deltas`. Each `commit_deltas` row stores one group and is keyed by the sequence and the group's `semantic_operation_index`. A replay commit stores its conflict report the same way, in `merge_conflicts`. Both families join the `commits` [family group](../specs/glossary.md#family-group). The ownership check, a receipt lookup, and a retention advance read the small header. The change feed, diff, grep, and the check of what main committed during the plan read the deltas in pages, and they resume inside a commit by seeking to the next group. An ordinary commit, and a merge on the WAL path, keeps its whole record in its `commits` row.

### Checking what main committed during the plan

The run is valid if no commit in `(P, H]` changed a row that the plan read or replaces, or a rule that the plan applied. The plan records, beside its segments:

- the "touched set", a sorted list of every inode whose rows the merge replaces or reads to classify, and every directory slot (parent and name) that it binds into or vacates, including the slot of a temporary name,
- the "path set", every directory on the path to a parent that the merge binds into or to an inode that it changes, which grows with the distinct directories on those paths, and
- the smallest deletion sequence among the deletions that the plan relies on being in main's trash (one it restores, or one that already hides an inode it would delete).

For the commits in an interval, the check reads the inodes and slots that each commit touched, and finds an intersection if:

1. a commit wrote any row of an inode in the touched set,
2. a binding change used a slot in the touched set (a name that main took after `P`),
3. a commit wrote a path set directory's own binding, tombstone, or access row (a change to the directory's children doesn't count, so a create under `/` doesn't intersect),
4. a commit wrote any row of an inode that has, among its ancestors in main at `H` (or, for an unbind, at its old parent), a directory that the merge deletes or moves, which is the conflict rule's subtree check applied to the commits after `P`, or
5. at the end of the interval, the range rule or the merge floor rule fails, or main's retention floor is at or above the smallest deletion sequence that the plan relies on.

Condition 5 covers a floor advance during the plan. Any process can advance main's floor while the plan runs, because a process writes a floor object without the writer epoch. For example, the plan restores a deletion at sequence 980, a process puts a floor object that raises main's floor to 990, a maintainer's fold records it, and a base compaction removes the rows under the expired deletion. The check finds 990 at or above 980, so LoonFS plans again and reports the restore as a conflict. The check runs against every basis that the publication builds on. (The rows that the merge's unbinds and revokes point at don't need a check of their own. They're current at `H` by conditions 1 to 3, and a base compaction keeps every current row except one hidden by an expired deletion, which condition 5 covers.)

Condition 5 and the merge floor rule compare with the floor that main's writer validates a WAL commit against, which is the manifest's floor raised by the floor objects in the tail that the check read. A reader takes its floor from its manifest (see [The floor that readers use](#the-floor-that-readers-use)), but from a floor object's WAL number on, the writer refuses to restore a deletion at or below that floor object's floor. If condition 5 compared with the manifest's floor alone, a merge whose second stage read a floor object with floor 990 in the tail would still restore 980. The merge's manifest folds that floor object, so it would be the first manifest to record floor 990, and it would also restore 980. The advance would have reported floor 990, and the writer would have refused restores of 980 from that floor object on, but the merge would bring the deletion back.

After a plan of several hours, `(P, H]` can contain millions of commits, most of them folded, so the check runs in two stages:

1. Without pausing anything, the process reads main's head `P'` and checks `(P, P']`, reading `commits` and `commit_deltas` rows and the tail like any reader. It repeats from the head that it checked until at most 256 commits are left to check, or the plan's budget ends. (256 is a choice, not a measurement.) This stage can run on a host that isn't main's writer.
2. The process folds main's tail with an ordinary fold, so that the fold under the pause covers only the WAL objects that arrive in between. It then pauses its own publication queue for main. If its writer session for main doesn't have the writer epoch, it first claims the epoch and writes its fence ([Writer ownership](../specs/format.md#61-writer-ownership)). It reads the WAL above the tip that its fold reached, or above its fence, including any floor object that another process put before this read, and checks the commits from the last head that stage 1 checked through `H`, which are at most 256 plus what arrived since.

An intervening merge on the WAL path is a WAL commit, and the check reads it as it reads any other commit. The check reads an intervening merge on the manifest path as it reads any folded commit: its header from the `commits` row, and its deltas from `commit_deltas` in pages, as the change feed reads a merge run's commit. A compaction can rewrite the merge run into a larger run before the check reads it, so the check never reads the merge run's own segments. The deltas list every inode and slot that the intervening merge changed, so conditions 1 to 3 test them against the touched set as they test an ordinary commit's deltas. Condition 4 walks the ancestors of each inode that the intervening merge changed, but only when this merge deletes or moves a directory. The `commit_deltas` rows that the check reads are above `P`, and a base compaction drops them only below the floor, which can't pass `P` during the plan, so they stay until the check has read them. Both checks run in the first stage, because no other merge can publish while this process's queue is paused and its session has the writer epoch.

### The publication

The plan runs in the process that received the request and has no writer epoch, so it doesn't fence main's writer for hours. The publication runs in that process's writer session for main, which claims the epoch only if it doesn't have it. The epoch keeps another host's writer from committing between the tip that the publication reads and its manifest put, and the pause keeps this process's own queue from doing so. (A floor object can still be written in that window, as [Floor objects](#floor-objects) describes.) The publication then runs in main's fold path, under the fold lock (see [Folding and compacting a namespace](maintenance-hosting.md#folding-and-compacting-a-namespace)).

The new manifest folds main's tail through the WAL tip, adds the "merge run" at `run_seq = H + 1`, which lists the merge's segments and the publication's segments for `commits`, `commit_receipts`, and `merges`, and sets `head_seq` to `H + 1`. If the tail under the pause has only fences and floor objects, as it does when no commit arrived after the fold in stage 2, the fold adds no run of its own ([Fold protocol](../specs/format.md#fold-protocol)), and the merge run is the run at the head. Otherwise the fold's run is at `H`. The merge is ordered after every commit acknowledged before the pause, it's never in the WAL tail, and no run is above the head.

The publication writes the header row, the receipt, and one merge index row per covered range, so nothing proportional to the merge happens during the pause. The pause lasts for the fold of a short tail, a check of at most 256 commits plus what arrived since, and one manifest put. It never waits for the compaction lock. A compaction unit keeps that lock for as long as the unit runs, so a publication that waited for it would stop main's commits for that long. A compaction on the same host, or any publisher on another host, can therefore win the manifest number, and the rules below handle that.

The publication keeps four rules that a fold doesn't:

- **The writer's epoch.** A fold rebuilds over any winning manifest, even another writer's claim. A merge publication publishes only while the basis's `writer_epoch` is the session's. Otherwise the session is fenced, and the publication doesn't put its manifest. That happens when a commit on another host claims main between the start of the pause and the put.
- **One put per pause.** If the put loses to another publisher's manifest (a compaction, a maintainer's fold, or another host's claim), or the session is fenced, the queue resumes at once. The publication goes back to the first stage of the check, over the winning manifest, for the commits that it hasn't checked, without planning again, because a claim or a compaction changes no row that the plan read. A lost or fenced publication doesn't count as a plan. An intersection is what makes a new plan. The publication repeats until the plan's budget ends, and then the merge returns `store_contention` with the cause `lost_race`. Each lost put costs main's writers one more short pause. A measurement on S3 saw a writer's manifest put lose every attempt it was allowed while compaction units of the same process were publishing (the lab record `analysis/box-campaign-20261125.md` of the lab repository), which is why a pause covers one put and not a series of retries.
- **No WAL put in between.** The queue stays paused from the read of the tip until the publication learns the put's outcome. A commit put that the queue sent before the pause can still be in flight if the session never learned its outcome. The session released its writer epoch just before it sent that put ([Failed and unknown outcomes](../specs/format.md#64-failed-and-unknown-outcomes)), so the pause claims the epoch and writes a fence first. The put in flight is then found by the fence's discovery and folded by the merge's manifest, or it collides, or it's written below the fence where no reader replays it (the argument in [Publication and group commit](../specs/format.md#63-publication-and-group-commit) for a session's own put whose outcome is unknown).
- **An unknown outcome.** The session releases its writer epoch just before the manifest put, as it does before a commit's WAL put, and after an unknown outcome it claims the namespace again before it publishes anything. The claim takes the next manifest number with put-if-absent ([Writer ownership](../specs/format.md#61-writer-ownership)). If that number contains the merge's manifest (the same publication ID), the claim collides and claims the number after it, and the merge committed. If the number is free, the claim takes it, and a delayed put of the merge's manifest can't be applied. The session then reads the receipt from its new basis, and a retry with the same commit ID returns the commit or plans again.

Every manifest put goes through one function. Under the requirement that [A window for replaced manifests](replaced-manifest-window.md#the-requirement-on-publications) proposes, that function refuses a candidate that lists a segment or an extension segment of its own namespace that the basis doesn't list and that its own publication didn't write. The function also refuses the put when the clock under which the publication wrote its segments is older than the compaction budget (`METADATA_COMPACTION_BUDGET_MS`, 12 hours). A merge's publication passes the function two things:

- the segments that it wrote, which are the merge run's segments from the plan, the publication's segments for `commits`, `commit_receipts`, and `merges`, and the segments of the fold of main's tail that the manifest includes, and
- the plan's clock, which starts before the plan writes its first segment.

The plan's budget of 6 hours is checked before every manifest put, so that clock is less than 6 hours old at the put, and the 12-hour check never refuses a merge that its budget admits. The age argument of that note is then true for a merge's segments with 6 hours in place of 12, so a merge's segment is less than 6 hours and 55 minutes old on a collection's clock while a kept manifest lists it (6 hours, plus 5 minutes of provider bound, 5 minutes of clock margin, and the 45-minute window). When a put loses and the publication builds again over the manifest that won the number, the new candidate lists the merge's segments again. The winner doesn't list them, because no other publication has them, but they're in the set that the publication passes, so the function accepts the candidate, as it accepts a fold that rebuilds over a winner with its own new run.

On the publishing host, the writer position and every cached view move to the merge's head only from the manifest that the put made durable, after the boundary check, never from the value that the publication planned to write.

### Budgets and collection

A namespace's [collection](../specs/glossary.md#collection) deletes an unlisted segment once it's 24 hours old (the [grace window](../specs/glossary.md#grace-window)). A compaction unit bounds this exposure with a 12-hour budget plus the completion bound. A merge's plan gets a budget too, checked before the manifest put, and it has to be shorter, because the fork's content has to stay rooted for the whole plan, and the pool's collection relies on this inequality ([Content roots](../specs/format.md#119-content-roots)):

```text
POOL_ROOTS_READ_BUDGET_MS + GC_SAFETY_MARGIN_MS
    + OPERATION_SNAPSHOT_TTL_MS + PROVIDER_PUBLICATION_REQUEST_BOUND_MS
    < GC_GRACE_WINDOW_MS
```

With a plan budget `B` in place of the 5-minute snapshot lifetime, the left side is 12 hours + 5 minutes + `B` + 5 minutes, so the inequality is true while `B` is shorter than 11 hours and 50 minutes, and a compaction's 12 hours and 25 minutes doesn't fit. This design sets `B` to 6 hours (a choice, not a measurement). The same terms also set `MAX_TAIL_COMMIT_AGE_MS`, which would fall to 5 hours and 50 minutes with `B` in place of the snapshot lifetime. The plan reads no fork tail, so that constant doesn't change.

### The request

A plan over millions of inodes could take minutes to hours (not measured), so it can't run inside one HTTP request. The merge route plans every merge on the WAL path first, inside the request, as [Merging a fork](merge.md#merging) describes. When that plan refuses the merge at one of the bounds in [Which merges take the manifest path](#which-merges-take-the-manifest-path), the route releases the attempt's reservation of the allowance and starts the manifest path's plan as a job, with the attempt's range, in the process that received the request, and waits for it for up to 10 seconds (a choice, not a measurement). If the merge commits within that time, the route returns the commit's header with a count of events. Otherwise it returns a response that says the merge is running. The same request sent again with the same commit ID returns the commit once its receipt exists, `merge_conflict` while the process still has that outcome, or the running response again while the process has the job. After a restart, the request plans on the WAL path again, which refuses the merge again, and the route starts a new job. A merge that commits within the wait returns its result to the first request.

A merge on the WAL path returns the same response, the commit's header with a count of events, so a client reads one response whichever path its merge took, and reads the merge's events from the change feed. (A merge on the manifest path can have millions of events, which don't fit in one response.) The plan runs as a compaction unit does, with a budget and no saved progress, so it fits [Maintenance hosting](maintenance-hosting.md).

Each plan on the manifest path reserves the plan memory bound from the merge allowance (see [Planning](#planning)). A plan doesn't wait for room. If the allowance has no room when the job starts, the request returns `server_busy`, and a retry with the same commit ID starts the job once the allowance has room.

### A rebase

A replay commit takes the same path as a merge of the same size. A replay commit within the WAL path's bounds is one WAL commit in the new fork, as [Merging a fork](merge.md#rebasing) describes. A larger one is one publication in the new fork, planned on the fork's whole unmerged range, with the same rule for skipping the conflicting part of an inode's change. Because no replay is split into pieces, a rebase doesn't report a conflict on a name that the fork passed through, doesn't apply a state that the fork passed through, and judges a directory's delete together with a skipped move of a file out of it. The new fork is private unless a resolver (the program or person that resolves the conflicts, as in [Merging a fork](merge.md#rebasing)) starts early, so the check usually finds no commits after `P`.

## A worked example

This section follows one merge on the manifest path, first with a commit to main that doesn't overlap it, and then with one that does. The fork changes three inodes, so that each step is short. A merge that small takes the WAL path, and a merge on the manifest path takes the same steps with tens of thousands of inodes or more in place of the three.

Main's manifest 39 has `folded_wal_no` 300 and a folded head of 1,000, and WAL objects 301 to 305 contain commits 1,001 to 1,010. Another host has main's writer epoch. The fork was forked at 950, and its commits change `/docs/a.txt` (inode `A`), create `/docs/b.txt` (inode `B`), and delete the directory `/tmp/old` (inode `C`).

1. The WAL path refuses the merge as too large, and the route starts the merge's job. No receipt exists, and main's merge index has no row for the fork, so the range starts at the fork point.
2. The process folds the fork and takes a 6-hour snapshot of the fork's manifest. It folds WAL objects 301 to 305 of main into manifest 40, with `folded_wal_no` 305 and head 1,010, and takes a 6-hour snapshot of manifest 40, so `P` = 1,010.
3. Step one classifies. `A`'s revision 3 on main was committed at 900, at or below the fork point, so it's the fork's own, and the planner produces a content group with revision 4. `B` doesn't exist on main and its slot is free, so the planner produces a create group (`B`'s create, binding, and revision 1). `C`'s binding is the fork's own and main's diff below `/tmp/old` is empty, so the planner produces a delete group (`C`'s unbind and tombstone). `B` and `C` have ordering entries. The touched set is `A`, `B`, `C` and their three slots, and the path set is `/`, `/docs`, and `/tmp`.
4. Step two finds no dependency between `B` and `C`, so their groups come first in inode order, then `A`'s. `B`'s group is deltas 0 to 2, `C`'s is 3 and 4, and `A`'s is 5, with operation indexes 0, 1, and 2. Step two derives the rows and writes them into small segments, one for each family that has a row.
5. A client commits 1,011, which creates `/src/main.rs` (inode `D`), in WAL object 306. The first stage finds no intersection, because `D` and its slot aren't in the touched set, the create doesn't change `/`'s own rows, `D`'s ancestors aren't below `/tmp/old`, and the floor and merge index haven't changed. Fewer than 256 commits are left to check, so the process folds WAL object 306 into manifest 41. It then claims main's writer epoch, which publishes manifest 42 with the next epoch, writes its fence at WAL object 307, and pauses its queue. It finds nothing above 307, so `H` = 1,011.
6. The process puts manifest 43, which folds the fence at 307 without a run, adds the merge run at 1,012, and sets the head to 1,012. `B`'s binding row is stored with the marker and decodes to the position `{1012, 1}`, which is `B`'s binding version.
7. The process resumes its queue, and its next commit, 1,013, is WAL object 308.

A reader with manifest 42 and the tail through 307 cached finds WAL object 308 starting two sequences above its head, runs discovery under the rule in [The sequence gap](#the-sequence-gap), and loads manifest 43.

If commit 1,011 had written a new revision of `/docs/a.txt` instead, the check would find `A` in the touched set, and LoonFS would plan again from 1,011. `A`'s current revision would then be foreign, so the plan would return `merge_conflict`, and collection would delete the first plan's segments after the grace window.

On a single server whose process already has main's writer epoch, a merge into a namespace whose tail is folded takes the same steps without the claim and the fence. The process pauses its queue, finds the tail empty, and puts one manifest that adds the merge run and no other run. (A session that sent a WAL put without learning its outcome has no epoch, so it claims and writes a fence first.)

## What changes in the format and the log protocol

This section states each rule that changes and why the change is safe. A merge on the WAL path is a WAL commit, as it is today, and none of these changes applies to it.

### The sequence gap

[Replaying the visible WAL](../specs/format.md#42-replaying-the-visible-wal) requires every data WAL object to continue the preceding head, and every fence and floor object to record it. After a merge publication, a reader on an older manifest finds the next WAL object above its head. That can be the writer's next data WAL object, which starts above the reader's head, or a fence or floor object that records the merge's head, because its writer's discovery found the merge's manifest. (Neither case needs a race. A reader whose view is cached on the manifest before the merge's finds that WAL object on its next probe.) Today, discovery treats such an object as invalid, reloads the current manifest, and starts again from it when it's newer, so discovery recovers. A warm probe of a cached view treats it as corruption, so one read returns `namespace_corrupt` before the runtime drops the view.

The new rule is that a WAL object whose head is above the replaying head (for a data WAL object, its prior head) means that a newer manifest published a merge. Discovery reloads the current manifest and reports corruption only if it's the same one, and a warm probe returns "needs discovery", as it does today for an object of another writer epoch. Every replay validates objects through the same check, so discovery, warm probes, a fork's read of its source's tail, the writer's discovery after a collision, a retention advance, and the pool collection's read of a tail all follow the rule. No reader may treat an object above its head as the end of the log. Main's writer is the one process that raises the head without a WAL object, at its epoch with its queue paused, and it folds through the tip it found. So the first data WAL object or fence above the new manifest's `folded_wal_no` continues or records the new head (a floor object can still record the older head, as the next section describes), and a gap above the current manifest's head is still corruption.

The change feed has no hole at a merge run's sequence. It reads the commits above the manifest's folded head from the tail and the commits at or below it from rows, and a merge run's commit is always at or below its manifest's head, with its deltas in `commit_deltas`.

### Floor objects

A merge's restore and a floor advance have to be ordered against each other, because a restore of a deletion that has already expired could bring back an inode whose rows a base compaction removed ([The expired-deletion invariant](../specs/format.md#the-expired-deletion-invariant)). A restore in a WAL commit, including a merge on the WAL path, is ordered against a [floor object](../specs/glossary.md#floor-object) by its WAL number. A restore in a merge run is in a manifest, and any process writes a floor object at `tip + 1` without the writer epoch ([Retention advance in the WAL](retention-advance-in-the-wal.md) describes who writes a floor object and how). So neither the epoch nor the pause keeps a floor object out of the window between the publication's read of the tip and its manifest put.

A floor object is written before, inside, or after that window:

- **Before.** A floor object put before the read of the tip is in main's tail at that tip. The second stage of the check reads it, condition 5 compares its floor with the deletions that the plan relies on, and the merge's manifest folds it and records its floor.
- **Inside.** A floor object whose writer's discovery found the tip that the publication read, and whose put comes after that read, is written at the next WAL number with head `H`. Its put can come before or after the merge's manifest put, because only its discovery has to come before the manifest put. The merge's manifest doesn't fold it, so it's in the tail of the merge's manifest with a head one below that manifest's head. Its check after the put finds it live, because its number is above the `folded_wal_no` of the merge's manifest.
- **After.** A floor object whose writer's discovery found the merge's manifest records the merge's head, and replay checks it like any other floor object.

Replay accepts a floor object whose recorded head is at or below the replaying head, applies its floor, and keeps the replaying head. Today replay requires the two heads to be equal, so a floor object written inside the window would make every replay from the merge's manifest fail, and no fold could fold it. Every head computation changes with the rule, because replay today sets the head from each WAL object. The rule drops a check that would catch a floor object written with a wrong head for another reason. No harm follows, because an advance's target is at or below the head that it was planned from, so an accepted floor never passes the replaying head. (The lab repository's model `verification/tla/merge_publication` checks floor objects that record the head of the manifest that their writer planned from, instead of the head that discovery found, and finds no counterexample within its bounds.)

A reader takes its retention floor from its manifest, and main's writer validates commits against the manifest's floor raised by the floor objects in its tail (see [The floor that readers use](#the-floor-that-readers-use)). So a floor object written inside the window doesn't change what any reader sees until a fold records its floor, and that fold is built on the merge's manifest. For example, suppose that the merge in [A worked example](#a-worked-example) also restores a deletion at 1,005, and that manifests 40 to 42 have floor 900:

1. The publication reads the tip, the fence at WAL object 307, with `H` = 1,011.
2. A process that advances main's floor to 1,008 runs discovery, which loads manifest 42 and replays WAL object 307.
3. The process puts floor object 308 with manifest 42's writer epoch, head 1,011, and floor 1,008. Its check after the put finds 308 live, and the advance reports floor 1,008. (This put can also come after step 4.)
4. The publication puts manifest 43, with `folded_wal_no` 307, head 1,012, and floor 900, which revokes deletion 1,005.
5. A reader with manifest 42 and the tail through 307 cached probes 308 and replays it, because the head that 308 records, 1,011, equals the reader's head. The reader still serves manifest 42's floor of 900, so it lists deletion 1,005 in the trash, as it did before 308 was written. Its next successor probe finds manifest 43, and the inode that deletion 1,005 hid is visible again.
6. A reader on manifest 43 replays 308, keeps head 1,012, and serves floor 900 with the inode restored.
7. The fold that covers 308 is built on manifest 43 or a later manifest, because each manifest is built on the one before it. It publishes manifest 44 with `folded_wal_no` 308, head 1,012, and floor 1,008. Deletion 1,005 is at or below that floor, but its latest event is the merge's revoke, so it hasn't expired. A reader on manifest 44 serves floor 1,008 with the inode restored, and a base compaction removes no row of the restored inode.

No reader sees deletion 1,005 expired, either before the merge's manifest or after it. Main's writer learns of 308 when its next put collides with it, and from then on it refuses to restore a deletion at or below 1,008. Between the floor object's put and the fold, the trash still lists any other deletion above 900 and at or below 1,008, and a restore of that deletion is refused, as after any floor object under the rule in [The floor that readers use](#the-floor-that-readers-use).

If a fold that covers 308 wins manifest number 43 before the merge's put, that fold is built on manifest 42 and records floor 1,008 while deletion 1,005 is still `set`, so a reader on it sees the deletion expired. The merge's put then loses, the publication goes back to the first stage of the check over the winning manifest, and condition 5 refuses the restore, so the deletion stays expired. A later merge whose plan reads main through a snapshot of one of main's manifests sees a deletion expired only in a manifest whose floor reaches the deletion while its latest event is `set`, and condition 5 and the writer's validation keep every later manifest from restoring that deletion.

(The lab repository's model `verification/tla/merge_publication` checks this design with a floor object put before, inside, and after the window, a floor put that's written late, a fold that wins the race against the merge's put, and a second merge whose plan reads a reader's view. Within its bounds, these runs find no manifest that restores a deletion that an earlier manifest has expired, and the runs with a fold, `MC_FloorAtFoldReadersFold` and `MC_FloorAtFoldTwoMerges`, find no reader that sees a deletion expired and later restored. Their witnesses show that in those runs a reader does see a deletion expired, a merge's manifest does restore it, and a fold records the floor of a floor object written inside the merge's window. With condition 5 compared with the manifest's floor alone, the run `MC_FloorAtFoldMergeChecksManifestFloor` finds a merge's manifest that restores a deletion after a floor object that expired it.)

### The floor that readers use

The ordering of floor objects above depends on a rule for the retention floor, and this design states the rule as a change that it depends on. A reader takes its floor from the manifest that its view is on. Main's writer validates a commit against the "validation floor", which is the manifest's floor raised by the floors of the floor objects in the writer's tail. The restore check, the merge floor rule, and condition 5 compare with the validation floor, and the trash listing, the change feed's lower bound, and every read compare with the reader's floor. A reader's floor changes only at a manifest, so a floor object written inside the publication's window doesn't change what any reader sees until a fold records its floor, and that fold is built on the merge's manifest. ([Alternatives considered](#alternatives-considered) describes the order that a reader whose floor includes its tail's floor objects would see.)

The rule has a cost. Between a floor object's put and the fold that records its floor, the trash lists a deletion that a restore refuses, because the listing compares with the reader's floor and the restore with the validation floor. In the same time, `GET /merges` can report a fork's next range that `POST /merges` refuses with `below_retention_floor`, because the preview compares the fork point with the reader's floor and the merge compares it with the validation floor. An advance folds the namespace right after it writes a floor object, so the difference lasts one fold, and until the namespace's next fold when the fold after the advance fails (estimated, not measured).

### Reading a store that contains a merge

A build can read, maintain, and commit to a store that contains a merge run by implementing a set of format parts on its own, without the manifest path's planner, the check of what main committed during the plan, the publication, or the API's job. The set is:

- the `commit_deltas` and `merge_conflicts` families, with their keys, their rows, their place in the `commits` family group, and their rule in a base compaction (rows below the floor are dropped, as for `commits`),
- the form of a merge run's `commits` row, which stores the header and the merge record while the deltas are in `commit_deltas`, and the paging over the deltas in the change feed, diff, and grep, which the check of what main committed during the plan also uses to read an intervening merge (the ownership check, a receipt lookup, and a retention advance's cutoff walk read the header),
- the merge run's manifest entry, which records the commit's sequence and time, and the markers: the replacement in the block decoder, the marker in a seek key and a filter probe, a cached block that belongs to its run entry, `namespace_corrupt` for a marker without a run entry, the real values in a compaction's output, and the run entry that a fork's first manifest copies,
- the gap rule and the floor object rule of replay (see [The sequence gap](#the-sequence-gap) and [Floor objects](#floor-objects)), in every place that replays a tail, and
- the reader's floor in [The floor that readers use](#the-floor-that-readers-use).

A merge on the WAL path needs no part of the set, because it's a WAL commit with the WAL's merge record, which doesn't change. A fold, a compaction, and a collection need nothing more. A fold built on a merge's manifest can find a floor object that records the older head at the start of its tail, which the floor object rule accepts. A compaction reads a merge run through its run entry. A namespace collection and a pool collection keep a merge run's segments because a manifest lists them, and they delete a plan's chunks and unpublished segments under the age rule for unlisted segments. A writer that commits after a merge finds the merge's manifest through discovery and continues from its head.

No part of the set depends on the manifest path's planner. A test can write a merge run from the deltas of any ordinary commit, with the fold's derivation and the markers, and check the property in [Reading a merge run](#reading-a-merge-run) against the same deltas folded as a commit record. The planner decides which deltas a merge run has and in what order, and the readers already check what they rely on in that order, because the change feed reports a group of any shape other than one event as corruption.

### The guarantees of the log protocol

[A summary of the log protocol](../specs/format.md#26-a-summary-of-the-log-protocol) lists eight guarantees. A merge on the WAL path is a WAL commit, so each guarantee is true for it by the argument that the spec makes today. The table describes a merge on the manifest path:

| Guarantee | Change | Reason |
| --- | --- | --- |
| 1. The visible log is unbroken above `folded_wal_no` | Changes: it continues the manifest's head, and a WAL object whose head is above the replaying head (for a data WAL object, its prior head) means a newer manifest | A merge run is committed by its manifest put, and the gap rule sends readers to that manifest. |
| 2. Every acknowledged commit is in the visible log or the current manifest | Changes: or in a merge run of it | The writer acknowledges a merge on the manifest path only after its put succeeds and the boundary check after it passes. |
| 3. Writer epochs never decrease, and a fence blocks older writers | Unchanged | The publication writes no WAL object, and a merge's manifest put loses at a number that a newer claim took, so a merge can't commit at an older epoch. |
| 4. Fresh discovery observes every acknowledged commit | Unchanged | Discovery loads the newest manifest, which lists the merge run. |
| 5. Cached views and writer positions never move backward | Unchanged | A view moves to the merge's manifest through discovery, or on the publishing host from the manifest that the put made durable, and replay keeps the replaying head when a floor object records a lower head. |
| 6. Pieces stay readable until folded | Unchanged | The publication folds main's tail as a fold does, and a merge run has no pieces. |
| 7. Identical retries don't commit twice | Unchanged, with a new argument | After an unknown outcome the session claims before it publishes, so a delayed put is the committed merge or can't be applied. The range rule stops a second process from publishing the same range under the same commit ID. |
| 8. Current and snapshot manifests keep their segments | Unchanged | The merge's segments are protected by their age until the publication, and the fork's by the plan's snapshot. The plan reads main through its snapshot of main, and the check reads main's later commits through its current manifest. |

### Two details of the commit record

A merge run's deltas need a `semantic_operation_index`, which the change feed, diff, and the activity counters read to group a commit's deltas into events. The change feed maps each group to one event and reports any other shape as corruption. So a merge run assigns one index per group, in the order of its deltas, and never one per inode, as the WAL path assigns one per operation. An inode that the merge moves and whose content it changes has two groups, a move and a content change.

A merge's fingerprint ([Merge commits](../specs/format.md#b5-merge-commits)) hashes the namespace, the actor, the fork, the merge's own range, and the message, and not the operations, so this design doesn't change it, and a merge has the same fingerprint on either path, because the job plans the range of the WAL path's attempt. A retry is identified by its commit ID and that fingerprint, as today, so a retry of a merge that changed paths finds the receipt of the merge that committed.

### Changes to the specs

The storage format gains the parts that a build needs to read and maintain a store that contains a merge run (see [Reading a store that contains a merge](#reading-a-store-that-contains-a-merge)). The WAL's merge record doesn't change, because a merge on the WAL path is still a WAL commit with that record.

- [Replaying the visible WAL](../specs/format.md#42-replaying-the-visible-wal) gains the gap rule for every WAL object whose head is above the replaying head and the rule for a floor object whose head is at or below it, and the log protocol summary changes guarantees 1 and 2.
- [Advancing the retention floor](../specs/format.md#101-advancing-the-retention-floor) says that a reader takes its floor from its manifest and that the writer validates against the manifest's floor raised by the floor objects in its tail, with the cost in [The floor that readers use](#the-floor-that-readers-use).
- [Manifests, runs, and segments](../specs/format.md#71-manifests-runs-and-segments) gains the merge run, whose entry records the commit's sequence and time.
- [Row families](../specs/format.md#19-row-families) gains the two new families and the markers. Every row of a merge run is still derived from one delta or commit record, so the section gains no exception.
- [Metadata rows and row keys](../specs/format.md#a6-metadata-rows-and-row-keys) gains a merge run's `commits` row, which stores the header and the merge record, and doesn't match any WAL commit record, and the compaction family groups put the two new families in the `commits` group.
- [Compaction windows](../specs/format.md#102-compaction-windows) lists the two new families in the `commits` group, and [Row retention during a base compaction](../specs/format.md#103-row-retention-during-a-base-compaction) drops their rows strictly below the floor, as it does for `commits`.

The rest of the changes belong to the manifest path's planner, the check, the publication, and the API:

- [Manifests, runs, and segments](../specs/format.md#71-manifests-runs-and-segments) gains the merge publication and its epoch rule among the basis checks for a manifest publication.
- [WAL records](../specs/format.md#a5-wal-records) keeps the merge record of a WAL commit record, the conflict report's count toward the WAL object's size, and the rule that a merge is alone in its WAL object, because a merge on the WAL path is still a WAL commit. It gains one sentence: a merge that doesn't fit within those bounds is published as a merge run instead.
- [The expired-deletion invariant](../specs/format.md#the-expired-deletion-invariant) covers a restore in a merge run as well as one in a WAL object. It states that no manifest restores a deletion that an earlier manifest has at or below its floor with its latest event `set`, because condition 5 refuses that restore, and the first manifest that records the floor of a floor object written inside the publication's window is built on the merge's manifest.
- [Merges](../specs/format.md#merges) gains the boundary between the two paths, the requirement that the two planners accept and refuse the same merges with the same result, and, for a merge run, the five conditions of the check in place of the writer's preconditions, with condition 5 and the merge floor rule compared with the validation floor, and the plan's snapshot of main at `P`. The writer's preconditions stay for a merge on the WAL path. [Content roots](../specs/format.md#119-content-roots) uses the plan's budget in its inequality.
- [Records and owners](../specs/format.md#81-records-and-owners) says that a plan on the manifest path takes temporary snapshots of the fork and of main that expire after the plan's budget instead of after 5 minutes.
- [Fixed logical bounds](../specs/format.md#c3-fixed-logical-bounds) says that `MAX_WAL_OBJECT_BYTES` and the merge allowance bound a merge on the WAL path and set the boundary to the manifest path, where the plan memory bound and the plan budget bound a merge.
- In the API, the merge and replay routes run a merge that the WAL path's bounds refuse as a job. The response of every merge becomes the commit's header with a count of events, in place of the `Commit`, and a merge on the manifest path can also return a running response. `merge_too_large` has the bounds `plan_budget` and `plan_memory` in place of `wal_object`, `merge_allowance`, and `touched_inodes`, because a merge that one of those three refuses takes the manifest path, and it loses `split_at_seq`. The route's description keeps the rule that a merge on the WAL path is the sole commit in its WAL object. A merge on either path returns `server_busy` when the allowance has no room for its reservation. The reference server keeps `max_merge_bytes` as the one allowance for merge memory and gains `max_merge_plan_bytes`, which each plan on the manifest path reserves from it, so the self-hosting guide's sizing formula doesn't change. The guide's advice to set a small allowance, such as 1 MiB, for callers that never merge also has to set a plan memory bound no larger than that allowance, because a server refuses to start with a larger bound, and a merge whose estimate is above the allowance takes the manifest path instead of returning `merge_too_large`.

In the design notes, [Merging a fork](merge.md) describes the WAL path's bounds as the boundary to the manifest path, and loses the split hint and the merges and replay commits in pieces, with the loop's states that follow a split hint. [Retention advance in the WAL](retention-advance-in-the-wal.md) states the floor that readers use and the validation floor, with the cost of the difference between them. Its statement that replay accepts a floor object only when the floor object's head equals the replaying head changes to the rule in [Floor objects](#floor-objects), which accepts a floor object whose head is at or below the replaying head and keeps the replaying head.

## Costs

This section lists what the design costs, each marked as measured, estimated, or not measured. A merge takes the manifest path only when the WAL path refuses it as too large, so apart from the second planner, the costs in this list are those of large merges. The figures in [What a small merge would cost on the manifest path](#what-a-small-merge-would-cost-on-the-manifest-path) describe what keeping the WAL path for every other merge avoids.

- **Two planners.** LoonFS keeps the WAL path's planner and the writer's merge path beside the manifest path's planner, with the differential test of [Two planners](#two-planners) and the change to the manifest path's temporary names that the requirement needs. A change to the conflict rule, the ordering, or the rights rules is made in both planners and checked by that test (not measured).
- **The change of path.** A merge on the manifest path first spends part of one plan on the WAL path, which stops at the first bound that the merge crosses: at the commit that takes the touched set past about 290,000 inodes, or when the estimate passes the allowance, so the WAL path's part of the plan keeps at most the allowance (512 MiB by default) in memory, and the route releases its reservation before the job reserves the plan memory bound. After a restart, a retry spends that part again (not measured).
- **The writer's pause.** Every merge on the manifest path pauses main's queue for one fold of a short tail, a check of at most 256 commits plus what arrived since, the publication's three segments, and one manifest put. Nothing proportional to the merge happens during the pause, so it's about 110 to 160 ms at any size of merge (estimated from the requests of a one-file merge in [What a small merge would cost on the manifest path](#what-a-small-merge-would-cost-on-the-manifest-path)), and longer when commits arrive during the pause (not measured). On the WAL path, a merge is alone in its batch, and the writer plans the whole merge again inside its queue. The lab measured a clean merge of 1,000 changes on S3 at 1.3 to 2.0 seconds and 1,007 to 1,273 store requests (the lab records `analysis/battery-20261118.md` and `analysis/box-campaign-20261125.md`), and main's other commits wait for the writer's share of that time. A merge at the WAL path's default bound, about 19,800 file creates, keeps the writer for longer (not measured).
- **The fold before the pause.** Folding main's tail before the pause costs one more manifest per merge when main's tail has commits. When commits also arrive between the two folds, it costs one more run, because the fold under the pause then adds a run of its own (estimated).
- **Lost puts.** Each manifest put that loses to a compaction or another publisher costs main's writers one more short pause, and the publication goes back to the first stage of the check for the commits that it hasn't checked. In the proxy in [What a small merge would cost on the manifest path](#what-a-small-merge-would-cost-on-the-manifest-path), a fold's manifest put lost 0.22 numbered creates for each manifest that it published at one publication a second and 0.86 at four a second, and each of the 22 folds that failed lost all 8 of its creates while compaction published 8 manifests (measured). A merge's publication doesn't stop after 8 losses, because it repeats until the plan's budget ends. At the same contention, a merge's publication would lose its number about 0.22 to 0.86 times for each manifest that it publishes, and each loss sends it back to the first stage of the check and pauses main's queue again, so main's queue would pause about 1.2 to 1.9 times for each merge (estimated from the proxy's folds, not measured for a merge).
- **Readers.** Every reader with a cached view on an older manifest runs discovery at each merge on the manifest path, as it does after each fold (estimated).
- **The fork's snapshot.** Every plan on the manifest path takes a temporary snapshot of the fork's manifest, as a merge on the WAL path does, which expires after the plan's budget instead of after 5 minutes. A snapshot's record stays, and keeps its manifest and every segment that the manifest lists, until `T` (24 hours) after its expiry ([Snapshot cleanup](../specs/format.md#117-snapshot-cleanup)). So a fork keeps the segments of each manifest that a merge read for about 30 hours after the plan starts, where the WAL path keeps them for about 24 (estimated).
- **Memory.** A merge's memory grows with its name changes (creates, moves, deletes, and restores) at about 300 bytes plus twice the name's length for each, about 330 MB per million creates with short names (estimated from the field sizes). The WAL path's allowance charges about 27 KB for each create. On top of that, a plan uses the 16 MiB buffer of step one, 32 MiB of puts in flight, 64 MiB of decoded input in the sorts, and about 32 MB per million touched inodes before the set spills (estimated). The plan memory bound (128 MiB by default) bounds the ordering entries and the other sets together, so a merge with more name changes than fit in it returns `merge_too_large` with `plan_memory`, and each plan reserves the bound from the merge allowance for as long as it runs (estimated to fit about 400,000 name changes with short names). The allowance stays the one budget for merge memory, 512 MiB by default.
- **Main's snapshot.** Every plan on the manifest path folds main and takes a temporary snapshot of the manifest that the fold published: one record put and the snapshot's verification reads (estimated). The snapshot keeps that manifest and every segment that it lists until garbage collection deletes the record, 24 hours after the snapshot expires, so about 30 hours after the plan starts (estimated from the plan's budget and the grace window). On a namespace that compacts often, compaction can replace every segment of that manifest in that time, so main stores up to one extra copy of its metadata at `P` for about 30 hours, and one more for each re-plan that takes a new snapshot after a compaction. With about 1 KB of rows per file (an assumption, not measured), that's about 1 GB for a namespace of a million files, which costs about $0.001 to store on S3 for 30 hours at $0.023 per GB-month (estimated). The snapshot protects main's own references, so it adds no term to the inequality in [Budgets and collection](#budgets-and-collection), and its lifetime is the same budget as the fork's snapshot.
- **The shared allowance.** At the defaults, four plans on the manifest path take the whole allowance for as long as they run, so a merge on the WAL path in the same process gets `server_busy` until one of them ends, and a fifth plan does too. A plan can run for its whole budget, so this can last up to 6 hours. With three plans running, the 128 MiB that's left admits a merge on the WAL path of up to about 4,950 file creates (estimated). An operator who sees `server_busy` for ordinary merges while large merges run raises `max_merge_bytes`, on a server sized for it, or lowers `max_merge_plan_bytes`, which lowers the number of name changes that a merge on the manifest path can have.
- **The check.** The first stage reads every commit after `P`, which grows with main's commit rate and the plan's length, and an intervening merge's `commit_deltas` rows (not measured).
- **Planning time.** Reads of the fork and of main for each changed inode (not measured, for one million or ten million inodes).
- **Storage.** The slot index, layouts, `trash`, and `commit_deltas` rows are written twice, and the groups of a merge that doesn't fit in step one's buffer are written once more as chunks (estimated). A merge with `N` bytes of rows that plans twice stores about `2N` for up to a day (estimated). The deltas family adds a copy of each delta, as the `commits` row does on the WAL path.
- **Fenced publications.** Where requests for main reach more than one host, a commit on another host between the publication's claim and its put fences the publication. The queue resumes, and the publication goes back to the first stage of the check and claims main again when it pauses. The plan itself has no epoch, so it isn't lost (not measured).

### What a small merge would cost on the manifest path

This part lists what a small merge would cost if it took the manifest path, which is what the WAL path avoids for every merge within its bounds.

- **A one-file merge.** On the WAL path, a merge of a few files is one WAL put, one snapshot record put, and its reads. The lab measured the merge of a resolved rebase fork at 163 to 197 ms and 8 store requests on S3 from the box, and a clean merge of a version control session's branch into a namespace of 10,000 files at 206 ms and 52 requests (the lab records `analysis/battery-20261118.md` and `analysis/battery-20261117-phases.md`). On the manifest path, a merge that creates one file, from a process that has main's writer epoch, with the fork folded and main's tail empty, sends these requests in order (estimated from the steps, not measured):
  1. The receipt, range, and floor reads and the successor probes of main and the fork, which run concurrently (about 2 round trips).
  2. The fork snapshot's record (1 put).
  3. The plan's reads of the fork's commits and the file's rows, and of main's slot and parent at `P` (about 2 round trips).
  4. The six segments of the plan (`inodes`, both binding families, `revisions`, `content_layouts`, and `commit_deltas`), concurrently (1 round trip).
  5. The first stage of the check, which probes main's head (1 round trip).
  6. Under the pause, the read of the WAL above the tip, the three segments of the publication (`commits`, `commit_receipts`, and `merges`) concurrently, the manifest put, and the boundary check after the put (4 round trips).

  That's 11 puts and about 11 round trips. The lab measured a round trip to S3 from the box at about 27 ms at the median and a commit of one WAL put at 21 to 29 ms (the lab record `analysis/battery-20261117-phases.md`), so this merge takes about 300 ms and pauses main's queue for about 110 ms (estimated). A fork with a tail adds its fold before step 2 (about seven segments, a manifest, and 3 round trips), a tail on main adds the fold before the pause (the same), and a process without the epoch adds the claim manifest and the fence to the pause (2 round trips). With all three, the merge sends about 29 puts in about 19 round trips, about 510 ms, and pauses main's queue for about 6 round trips, 160 ms (estimated). On the WAL path, the writer's share of a one-file merge is its planning and one WAL put, about one round trip.
- **Runs.** Each merge on the manifest path publishes one manifest and adds one merge run, which for a merge that creates one file has rows in five family groups (`inodes`, `bindings`, `revisions`, `content_layouts`, and `commits`, which includes `commit_deltas`). When main's tail has commits, the fold before the pause publishes one more manifest and adds a run of its own, in about five family groups for a tail of file writes, and the fold under the pause adds a run when a commit arrived after the fold before it. A tier compaction of four runs of a group removes three, and its output joins a later tier, so compaction publishes about 0.38 units for each run added to a group when the runs are about the same size and compaction runs as soon as a tier has four runs (estimated by applying the tier rules in [Compaction windows](../specs/format.md#102-compaction-windows) to a stream of such runs). A small merge would then lead to about 2.9 manifest publications in main when main's tail is empty and about 5.8 when it has commits (its manifest, the fold's manifest, and 1.9 or 3.8 compaction units, estimated). That's about 0.05 to 0.1 publications a second at one merge a minute, about 1.0 to 2.0 a second at the 30,000 merges a day (0.35 a second) of the version control use case that the lab models (the lab record `analysis/use-case-workloads-version-control-20261115.md`), and about 2.9 to 5.8 a second at one merge a second (all estimated).

  The lab measured a proxy for a stream of small merges on S3 (the lab record `analysis/small-publication-rate-20261126.md`). The proxy is one small commit that creates a 300-byte file, followed at once by an explicit fold, repeated at a steady rate, with compaction units running every 5 seconds in the same process, as the server's scheduler runs them for an open session by default. Each repetition publishes one fold manifest that adds one small run, with rows in seven families. That run has no `commit_deltas` or `merges` rows, and the proxy leaves out the rest of a merge's work before its publication: the fork snapshot's record, the plan's six segments, the check of main's head, the pause of main's queue, and a fold of main's or the fork's tail. It sends one WAL put, one content object put, and one fold where a one-file merge sends about 11 puts. Each rate ran once, for about 10 minutes, on a namespace of 10,000 files. A "numbered create" in the table is a manifest put at the next manifest number with put-if-absent, and it's lost when another publication took that number first.

  | | One a minute | One every 3 s | One a second | Four a second |
  | --- | ---: | ---: | ---: | ---: |
  | Runs at the start / at the end / most seen | 1 / 6 / 8 | 7 / 19 / 22 | 18 / 24 / 31 | 20 / 63 / 65 |
  | Manifests a second, from the loop's folds / from compaction | 0.02 / 0.02 | 0.33 / 0.46 | 1.00 / 0.94 | 3.96 / 3.58 |
  | Manifests for each small publication | 2.4 | 2.4 | 1.9 | 1.9 |
  | Numbered creates lost for each manifest, by the folds / by compaction | 0 / 0 | 0.02 / 0.02 | 0.22 / 0.08 | 0.86 / 0.51 |
  | Cold lookup of one file, at the start / at the end | 238 / 323 ms | 246 / 740 ms | 295 / 442 ms | 385 / 1,087 ms |
  | Cold listing of 100 entries, at the start / at the end | 84 / 141 ms | 92 / 163 ms | 93 / 124 ms | 83 / 141 ms |

  The run count stayed bounded at every rate, with no climb over the last two minutes of any rate, and compaction brought it back to 20 runs or fewer within 1.5 to 9 seconds after each rate. The proxy published about 1.9 to 2.4 manifests for each small publication, against the estimate of 2.9 for a merge into an empty tail, because compaction published 0.9 to 1.4 manifests for each fold manifest where the estimate is 1.9 units (why compaction needed fewer wasn't measured). At four a second, 22 of the 2,459 folds (0.9%) lost all 8 of the numbered creates that a fold is allowed and failed with `store_contention`, so the manifest chain stopped some publications before the run count grew. A cold lookup of one file cost up to about three times as much at the end of a rate as at its start, with the same number of requests in most readings, and each reading is one sample. A cold listing of 100 entries cost about the same throughout. By extrapolation from the losses (not measured), at about five to six small publications a second, each with the compaction that follows it, a fold would lose about as many numbered creates as it wins. The lab also saw a manifest put fail with `store_contention` while compaction units published about four manifests a second on a namespace of a million files (the lab record `analysis/box-campaign-20261125.md`).

  No write stop counts runs, so nothing makes merges wait when runs arrive faster than compaction removes them. A merge itself hasn't been measured, and neither has a namespace of a million files (where a compaction unit reads and writes more rows and takes longer than the 120 ms measured here, so compaction would fall behind at a lower rate), a rate above four a second, or more than one publisher besides compaction.
- **Small merges a second.** In one process, merges on the manifest path into one namespace are published one at a time, because each publication runs in main's fold path under the fold lock, and the fold of main's tail before the pause takes the same lock. A one-file merge would take about 300 ms from its request and pause main's queue for about 110 ms when main's tail is empty and the process has the epoch (estimated above). With a tail on main and no epoch, the merge would keep the fold lock for the fold before the pause (about 80 ms) and a pause of about 160 ms, about 240 ms in all. By that arithmetic, one namespace would take at most about 4 to 9 small merges a second, and at that rate main's queue would be paused almost all the time, so main's other commits wait (estimated). The plans run outside the lock, and the default allowance fits four plans at once, which allows about 8 to 13 merges a second even if each merge keeps its reservation for the whole 300 to 510 ms, so the allowance doesn't lower that figure. The manifest chain limits the rate sooner. The proxy's extrapolated limit is about five to six small publications a second, each with the compaction that follows it. A merge into an empty tail publishes one manifest, as one of the proxy's folds does, so it would reach that limit at about 5 to 6 merges a second. A merge into a tail with commits also publishes the fold's manifest before the pause, so it would reach the limit at about 3 (extrapolated from the proxy, not measured for a merge). On the WAL path, a small merge is one WAL commit, alone in its batch, and the writer publishes one batch with each WAL put. On S3 from the lab's host, one client that committed one file at a time committed 37.9 to 39.1 files a second (the lab record `analysis/battery-20261117-phases.md`). Those were commits of one file, not merges, but each needed one WAL put, as a small merge does on the WAL path, so the WAL path can commit up to about 39 small merges a second into one namespace, less the time that the writer takes to plan each merge again (estimated).

## Alternatives considered

- **Today's design, with its limits stated as product limits.** Every merge would take the WAL path. A small merge is one WAL put, the size limits are explicit errors with split hints, and each piece is a correct merge. But the writer's pause, the `commits` row, and the tail grow with the merge without any error, and a rebase in pieces depends on where the pieces fall.
- **A plan that moves its view of main.** The plan would take no snapshot of main. It would read main at `P` through main's current manifest, check its view as a cached view does at least once per [revalidation bound](../specs/glossary.md#revalidation-bound), and move its reads to each newer manifest that the check finds, relying on the rule in [A window for replaced manifests](replaced-manifest-window.md#choosing-the-window) that a process finds every segment of a manifest for less than 35 minutes after it checked that manifest. Because a base compaction over a manifest with a higher floor can remove rows that the plan reads below `P`, the plan would read main at one floor and plan again (or return `below_retention_floor`) when a newer manifest raised the floor. It would save the snapshot's record put and the up to one extra copy of main's metadata for about 30 hours that [Costs](#costs) estimates. It would cost new code in the planner's state readers (estimated at 150 to 300 lines), a rule about reading main at one floor, a re-plan when the floor rises, and a dependency on the window for replaced manifests, where a snapshot is a mechanism that LoonFS already has.
- **Every merge through the manifest.** Every merge would take the manifest path, so LoonFS would have one planner and no boundary between two paths. But each small merge would cost about 9 to 27 more puts and a few reads, one manifest, and one run (estimated in [What a small merge would cost on the manifest path](#what-a-small-merge-would-cost-on-the-manifest-path)). At a high merge rate, that includes the runs and manifests that compaction and the manifest numbers take, because a merge in a WAL commit adds no run and no manifest of its own, and a fold covers it with the commits around it. At one merge a second through the manifest, the merges, their folds, and the compaction of their runs are estimated at about 2.9 to 5.8 manifest publications a second. In the lab's proxy on a namespace of 10,000 files, one small publication a second led to about 1.9 manifests a second and up to 31 runs, and four a second led to about 7.5 manifests a second, up to 65 runs, cold lookups of up to 1,087 ms against 385 ms at the start, and 0.9% of the folds stopped by lost numbered creates (measured). One namespace would also take about 3 to 6 small merges a second through the manifest, against up to about 39 as WAL commits (estimated).
- **A WAL commit for a small merge.** The manifest path's planner would plan every merge, and a merge below a threshold would be published as one WAL commit, with main's writer running the check of what main committed during the plan and replacing the markers in the deltas before the WAL put. LoonFS would then have one planner. The WAL path's planner, its operation form, and the writer's planning of a merge's operations would go, and so would the requirement in [Two planners](#two-planners) and its differential test. It would take a threshold, the check and the markers in the writer, and a manifest path's planner fast enough for every small merge, built and measured before any large merge needs it. Against this design, it saves no request, because both publish a small merge through the log, and what it saves is the second planner.
- **The bound edge in place of the newest edge.** If a slot's state were the edge that's bound, whatever its position, a merge's name changes wouldn't need an order across inodes, and the temporary names would go. But the rule changes every reader of a slot for every commit. A consumer that applies a commit's events in order would see two files under one name for a moment. And the change removes the slot part of the ordering and nothing else, because a bind still has to follow the create of its parent directory, and a directory's delete still has to follow the moves out of it.
- **Ordering just the changes that another change depends on.** A create into a directory that the merge doesn't change, at a name that no other change of the merge touches, depends on nothing, so it could be streamed without an ordering entry, which would save memory. But finding the names that are reused needs a pass over every name change sorted by slot, and a mistake in what counts as independent corrupts a slot's state.
- **Checking by the newest row of each touched inode.** The check could look up the newest row of each inode and slot in the touched set instead of reading the commits after `P`, so its cost would follow the merge and not main's commits. But conditions 3 to 5 need the commits anyway, so it would be a second check beside the first.
- **Storing every commit's deltas as rows.** Every commit, not just a merge, would store its deltas in `commit_deltas`, so LoonFS would have one form of commit record. That costs a second row for every small commit.
- **The log as the commit point.** The merge's commit is a small WAL object that refers to the staged segments, so order, unknown outcomes, epochs, and floor objects follow today's rules with no protocol change, and a floor object can't race the merge. A reader that replays to that object stops there and reads main as of the commit before it, and the writer's next step is a fold that lists the segments. The merge isn't acknowledged until that fold, so reads don't wait, but the writer's own commits do, and after a crash between the two puts they wait for a maintainer's fold. It needs a new WAL record kind that refers to segments. And the merge is committed while no manifest lists its segments, so the namespace collection, which reads no WAL objects, would need a new root, or it would delete a committed merge's rows once they're a day old. That last point is why this design makes the manifest the commit point.
- **Floor objects that only the writer writes.** A floor object would be one item of a writer session's publication queue, put at the session's writer epoch, so none could be written while the queue is paused for a publication, and replay would keep the rule that a floor object records the replaying head. A process without a session would open one and claim the epoch before it advanced the floor. That's as safe for a merge (the lab repository's model `verification/tla/merge_publication` finds no counterexample for it within its bounds), but the host of each session would have to advance the floor on a timer, and a sweep would have to take over a namespace whose host hasn't advanced it after a delay. That needs two timing settings, a rule for when a fold is due, and an advance path in the `serve_only` and `disabled` schedulers. Maintenance would also fence a writer in several cases, for example when a sweep claims a namespace whose host is late by more than the delay, or when a retention job runs against another server's writer. When any process writes floor objects, the only process that interrupts a writer is another writer.
- **Readers that take the floor from their replayed view.** A reader would raise its floor with each floor object that it replays, as the writer does. A reader on the manifest before the merge's that replays a floor object written inside the publication's window would then see a deletion expire and come back, although [Expiring deletions and creating floor objects](../specs/format.md#expiring-deletions-and-creating-floor-objects) says that a restore of an expired deletion fails. For example, a reader with manifest 42 and the tail through 308 in [Floor objects](#floor-objects) would serve floor 1,008 and see deletion 1,005 expired, and after it loads manifest 43, it would see the deletion restored. Every merge on the manifest path would expose readers to this race. (The lab repository's model `verification/tla/merge_publication` finds this order.)
- **Making a floor object with an older head dead.** A floor object that records the head from before the merge would be dead. Either the merge's manifest reserves the next WAL number, so a floor object that races into `tip + 1` is dead by the existing rule, or replay skips a floor object whose head is below the replaying head, and its writer's check after the put retries. Both break the same way. The check after the floor object's put can run before the merge's manifest exists, so the advance reports a floor that the merge's manifest then drops (the lab repository's model `verification/tla/merge_publication` finds this order for the second form).
- **A commit across several WAL objects, closed by a marker.** Each part is still bounded by a WAL object, the tail and the fold still keep the whole merge in memory, and every reader needs a rule for an unclosed commit.
- **Listing the fork's own runs in main.** The fork's rows record the fork's sequences, which overlap main's above the fork point, and segments would need shared ownership across namespaces.
- **Stamping the sequence at publication.** The writer would rewrite the whole merge during its pause, which brings back the second limit.
- **Steps that the client drives.** Each step would continue the previous step's plan, so the server would need a durable record of the plan's progress.
- **An incremental re-plan.** Planning only the intersecting inodes again needs a way to remove the first plan's rows for them, because a second set of segments at the same sequence adds rows and hides none.
