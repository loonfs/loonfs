# Fork family content

This note explains where LoonFS stores content objects and upload records, and why every member of a [fork family](../specs/glossary.md#fork-family) writes them under one prefix. [File contents and ownership](../specs/format.md#15-file-contents-and-ownership) in the storage format defines the rule, [Content roots](../specs/format.md#119-content-roots) defines how the family's content is collected, and [Retirement](../specs/format.md#95-retirement) defines when it's deleted.

## The problem

A [content reference](../specs/glossary.md#content-reference) identifies a [chain](../specs/glossary.md#chain) by a random content ID, and a reader finds the chain's bytes by deriving object keys from the reference. Nothing in the reference says which namespace wrote the bytes, and a read doesn't need that information. A fork inherits its source's references and reads the same objects, and a fork's revisions and the source's revisions can refer to one object for as long as both namespaces exist.

So the question for the format is which prefix stores an object, because the prefix determines which garbage collection pass can delete the object, and which namespace's retirement deletes it. If each namespace stored the content it wrote under its own prefix, an object that two namespaces reference would be read by both, but only one namespace's collector would protect it. A fork pin makes that sharing safe in one direction, from a fork to its source. Every other case, such as a commit in one namespace that references content a related namespace wrote, would need a pin in that direction too, or a copy of the bytes under a new content ID. A copy writes the bytes again under a new content ID, so the same data is stored twice, and every reader that already had the first object misses its cache.

## The design

A "fork family" is a set of namespaces: one namespace that was created without a source, and every namespace forked from it, directly or through other forks. Each namespace in the set is a "member" of the family. The namespace that was created without a source is the "family root". Every manifest records the namespace's family root (`family_root_id`). A plain create records the namespace itself, and a fork copies the value from the pinned source manifest. The value can't change.

Every member of a family writes new content under the family root's prefix: the object of each upload, the objects a fold writes for inline pieces, and the extents of new chains. Upload session records are stored under the same prefix, and each one records the namespace that created the session. A content reference contains a content ID, a size, and a checksum. The reader's own manifest supplies the family root, so a reference identifies the same object in every member. A fork reads inherited content and its own content by one rule, and content is never copied between the members of a family. An import from another family copies the bytes under a new content ID in the destination's family, as every import between unrelated namespaces does.

Metadata stays with the namespace that wrote it. Manifests, WAL objects, segments, pins, and temporary objects are stored under each member's own prefix. A fork reads its inherited segments through its fork pin, and compaction output is written under the compacting namespace's prefix. The two rules follow one principle. Data keyed by content identity is stored per family and collected by reachability, and data keyed by namespace state is stored per namespace and protected by pins.

### One creator per chain

A chain's "creator" is the namespace whose commit started the chain, and only the creator appends to the chain in place. The chain's layout records the creator next to its extents. A copy or a restore of a chain that another member created includes the chain's layout in its WAL delta, so the layout row that replay writes from the delta records the same creator. The creator is a fact about the chain, like its extents, so the layout describes the whole chain. The delta and the row then include one record, and no rule has to tie the presence of one field to the presence of another. When any other member of the family appends to the chain, LoonFS starts a new chain whose layout lists the first chain's extents as [shared base extents](../specs/glossary.md#extent), followed by the appended bytes. The new chain's creator is the appending namespace, so that namespace's later appends extend the new chain in place.

Why does only the creator append to a chain in place? Every member writes under the same prefix. Two members that appended to one chain from the same length would write a span object at the same key with different bytes, and their layout rows would describe one content ID as two different byte sequences. The longest layout rule, which picks the newest row among the longest layouts of a chain, depends on every layout of a chain being a prefix of the longest one. One creator per chain keeps every layout a prefix of the longest one. The rule costs a content ID and a layout row for each other member that appends to a chain, and no bytes, because the new chain shares the first chain's extents.

For example, a namespace called `main` creates `/build.log` and appends to it three times, which extends one chain under the prefix of `main`. A fork of `main` called `sandbox` appends to the file. The fork isn't the chain's creator, so its append starts a new chain whose layout lists the first chain's extents and the appended bytes, under the same prefix. The next append in `sandbox` extends the fork's own chain. Later appends in `main` extend the first chain, and neither namespace writes a key that the other could write.

### Collection

The family root's garbage collection pass collects the family's content and upload records, with roots gathered from every member.

The pass finds the members by walking fork pins. The family root's fork pins identify its first-generation forks, and a fork of a fork pins the fork it was created from. So the pass lists the family root's pins, then the pins of each fork that listing found, and so on, until a listing finds no new member. A member's pin listing is also the listing that the pass needs for that member's reference roots, so the walk costs one pin listing for each member.

Why does the pass walk the fork pins instead of reading a list of members? A fork pin is stored under its source's prefix, and it's the only durable record of which namespaces were forked from a member. A list of members under the family root's prefix would be one more record that every fork installation and every retirement would have to keep in step with the pins.

The pass discovers the family root's current manifest and lists the family's upload sessions. It then loads each member's roots, in the order that the walk finds the members: the member's current manifest, its WAL tail, the manifests its pins keep, and the manifests whose successor is younger than the reclamation grace. Those are the same roots that a pass on a namespace without forks loads. The sessions are listed before any member's WAL tail is read, for the reason in [Content collection](content-collection.md#why-the-roots-are-enough). The layout scan visits each distinct segment once, and a fork's inherited segments are its source's, so the extra work for each member is a scan of its own runs. The pass then lists the family root's content prefix once for each content ID shard to find the candidates.

A member's content references count as roots until the member is retired. A deleted member's tombstone keeps its runs, and only retirement deletes the member's source pin. So until the member is retired, the walk finds the member, and the tombstone is one of the member's layout views. Retirement comes at least the retirement grace after the deletion. The pass has to read every member's roots within the retirement grace less the clock allowance, measured from the start of the pass (see [Clock and operation assumptions](../specs/format.md#114-clock-and-operation-assumptions)), or it skips the family's content sweep.

Why bound the pass by the retirement grace? A reference can move from one member to another while a pass runs. Suppose that after the pass has read the family root's roots, a commit in the family root refers to a chain that a fork wrote, and the fork is then deleted. The pass sees that reference only through the fork's tombstone. The commit came after the pass started, and the deletion came after the commit, so the fork can't be retired until the retirement grace, less the clock allowance between the hosts involved, has passed since the pass started. A pass that reads every member within the grace still finds the fork and its tombstone.

The pass skips a fork pin whose target has no manifest (an installation that hasn't finished, or one that failed). When the pass finds the pin, the target has no roots of its own, and the pin keeps the source manifest that the target reads through. A member whose manifest fails verification stops the family's content sweep, and other fork families are unaffected. A pass on a fork sweeps no content, because nothing is stored under its content prefix.

A fork's retirement releases its source pin and deletes nothing else. Content that the fork wrote and that no other member references becomes unreferenced, and the family root's pass collects it under the ordinary age rule.

The family root is the last member to be retired, because each fork pins its source, and a tombstone can't be retired while a pin is on it. Garbage collection still runs passes on a deleted namespace, so after the family root is deleted, its pass keeps collecting the family's content for as long as any fork exists. Once the last fork is retired, the family root can be retired. Its content prefix stores the whole family's content, so the retirement sweep deletes all of it.

Why doesn't another member take over the family's content when the family root is deleted? The deleted family root's pass keeps running while the family has other members, so nothing has to move. A takeover would need a durable record of which member collects the family's content, and a way for the members to agree on a change to that record.

## Costs

- The family root's pass loads one set of roots for each member, including each deleted member until it's retired. A family with many short-lived forks pays one manifest discovery, one pin listing, one manifest listing, and one WAL tail read for each of them on every pass, and a fork leaves the family once it's retired.
- The pass has to read every member's roots within the retirement grace less the clock allowance (`NAMESPACE_RETIREMENT_GRACE_WINDOW_MS - GC_SAFETY_MARGIN_MS`, about 58 minutes), or it skips the family's content sweep. A family whose members can't all be read in that time keeps its unreferenced content until a pass finishes in time.
- Storage is attributed to the family by prefix. A listing of the family root's content prefix measures the family's content, and a member's share isn't visible from object keys. Upload admission limits apply to each member, and nothing else limits a fork family's content.
- One member's garbage stays in the family root's prefix until the family root's next pass. A member whose manifest fails verification stops content reclamation for the whole family until the member is repaired or deleted.
- The shared base filter is sized from the sum of the members' current manifests' layout row counts, under the same byte cap as a single namespace's filter.

## Alternatives considered

- **Content stored under the namespace that writes it.** Each namespace could store its uploads and folded pieces under its own prefix, with a fork reading its source's objects through the fork pin. A reference would then identify an object in one namespace's prefix. Content that one member wrote could be used by another member only by copying the bytes under a new content ID, or by a pin from the reader onto the writer for as long as the reference exists. Such a pin would be a second kind of pin, and it would add a second direction of dependency to retirement.
- **Copying at retirement.** A member could reference another member's objects without a copy, under a pin in the reverse direction. When the writer is retired, the bytes could be copied into the reader's prefix, and the reader's layouts rewritten to point at the copies. That design needs pins in both directions and a publication in one namespace that another namespace's retirement triggers, and it still copies every shared byte eventually.
- **An owner namespace on every content reference.** Each reference could record the namespace whose prefix stores its bytes. Within a family that namespace is always the family root, which the manifest records, so the field would repeat one value in every reference and every extent. It would also make a reference into another family's prefix representable, and such a reference is never safe, because that family's collector doesn't read the reader's roots.
- **Any member extends a chain in place.** Two members that appended to one chain from the same length would write span objects at one key with different bytes, and a chain would stop being one sequence of bytes. Adding a unique component to span keys avoids the key collision but not the second problem, because the longest layout rule would then pick one member's bytes for a reference that the other member wrote.
- **Only the family root extends chains in place.** A fork would start a new chain on every append, and each new chain's layout would list every earlier extent as a shared base extent. Shared base extents are never merged and don't count toward the extent limit, so a file that a fork appended to 1,000 times would have 1,000 extents.
- **One content prefix for every namespace in a deployment.** Unrelated namespaces would share one collector and one content listing, and a namespace's retirement could delete nothing on its own. The family is the smallest set of namespaces that can share a reference, so it's the smallest collection domain that works.
