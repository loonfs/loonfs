# Grep across a pool

The grep extension indexes a namespace's file content so that `GET /grep` can find the files that a pattern can match without reading every file ([Content search index](content-search-index.md), [Grep extension format](../specs/format.md#appendix-d-grep-extension-format)). The index's runs are listed in the core manifest, and core keeps one property for every extension: an extension is opaque to core and durable through core. Core guarantees three things. It never decodes the members of an entry that the extension defines, or the rows of the extension's segments. An absent or unknown extension never blocks a read. An extension's segments are protected and collected exactly as metadata segments are.

A [fork](../specs/glossary.md#fork) inherits its source's index and can be searched as soon as it exists. The design has four parts:

- **Postings identify content, not revisions.** A posting identifies a content value (the bytes that a [content reference](../specs/glossary.md#content-reference) identifies), and a row family in the index maps a content value to the revisions in a namespace that reference the value. Content identity is the same in every member of a [pool](../specs/glossary.md#pool), so an index of content is valid in every member.
- **The index's runs are listed in the core manifest.** A fork then inherits its source's index the way it inherits metadata runs. The fork snapshot keeps the index's segments, and the core collector collects them under its segment rule. Grep has no manifests, hint, discovery, or collector of its own.
- **A fork's index starts at the fork point.** The fork's grep steps index the fork's own commits, and also the source's last few commits before the fork point if the source's index hadn't reached them. After a [merge](../specs/glossary.md#merge) into main, grep indexes only what the merge brought in.
- **The index is pruned.** A base-level reorganization drops the postings of a content value that no retained revision references.

[Content search index](content-search-index.md) describes the tokenizer, the eligibility rule, the planner, the three-tier reorganization, the bounded steps, and the lifecycle. In this note, "the index" means the grep index. "The watermark" means the sequence through which the index covers a namespace's commits (`built_through_seq`). "The source" means the namespace that a fork was forked from. A "grep step" is any step that changes the grep entry in the core manifest: a backfill step, a build step, or a reorganization step.

## The problem

Sandbox-per-task agent workloads fork a namespace of a hundred thousand files, make a few changes, merge, and retire the fork, hundreds of times an hour. If a fork started with no index, the fork couldn't be searched until a backfill read every eligible file. A backfill takes longer than the lifetime of most forks, so in practice grep couldn't search a fork at all. These workloads need to grep a sandbox the moment it exists.

An index whose postings identify `(inode_id, revision_no)` can't be shared with a fork, because after the fork point the fork and its source assign the same revision number to different content of the same inode. A shared index of revisions would attribute one namespace's content to the other.

An index with its own log would also need a second copy of core's log machinery: numbered manifests, a hint, discovery with a revalidation bound, a publication budget, and a collector with its own grace rules. That copy would cost every grep step a parallel publication, every query a HEAD for a successor, and every deployment a second collector to run. It would also stop a fork from inheriting the index, because the fork snapshot that protects a fork's inherited state protects only what the core manifest lists.

## Indexing content, not revisions

A "content value" is the bytes that a content reference identifies. A content value is identified by a content ID and a size, which together identify a prefix of a chain ([File contents and ownership](../specs/format.md#15-file-contents-and-ownership)). Two revisions that record the same reference have the same bytes, in any member of the pool, because the pool's content objects are stored once under the pool's prefix, and a reference identifies the same object in every member.

A posting identifies a content value, through a number that's local to the run that stores the posting. Each run stores a "value table", which lists every content value that has a `texts` row in the run (see below), each as a content ID and a size, ordered by content ID and then by size. The table lists an ineligible value too, even though the value has no postings, because a reorganization keeps a value's postings and its `texts` row exactly when the reorganization's output table lists the value. A value's "ordinal" is its index in that table. A posting batch stores the number of postings, the first ordinal, and the gap from each ordinal to the next, each as an unsigned LEB128 value. For example, if the values at ordinals 0 and 2 of a run's table contain the gram `abc`, the run's batch for `abc` lists the ordinals 0 and 2. A row stores one batch for one gram, and its key identifies the batch's first ordinal:

```text
gram-{gram_hex}-{first_ordinal:020}
value-{ordinal:020}
```

The first key is a gram row's key. Its ordinal is written at a fixed width, so a gram's batches sort by ordinal. The filter key, `gram-{gram_hex}`, is unchanged. The second key is the key of a row in the value table, and the row stores the value's content ID and size. Every value row has the filter key `value`, and value rows sort after every other family's rows, so a reader finds a run's value rows by key range instead of probing filters.

A query intersects the batches of a run by ordinal, maps the ordinals that survive to content values through the run's table, and combines the runs' results by content ID, so the query still walks the candidates in content order. A reorganization's output table lists the union of its input tables' values, except the values that a base-level reorganization drops, and the reorganization renumbers the postings of the values that it keeps. Each step of a reorganization starts by building one "translation list" for each input run, which maps each of the input's ordinals to an ordinal in the output's table, or to none for a dropped value. The step builds each list in one read of the input's table and the output's table, which are both cached, and it remaps each posting batch through the list, so the postings stay integers throughout. At every level, the reorganization's first step writes the whole table with its rows, so every output that a manifest lists can be read.

The index has a second row family, `texts`, with one row for each content value that a grep step has examined:

```text
text-{content_id_body}-{size_bytes:020}
```

The row records whether the value was eligible, and its filter key is `text-{content_id_body}`. A grep step consults `texts` before it reads content, so a value that any retained run of the index has examined (an inherited run or one of the namespace's own) isn't read or tokenized again while its row is retained. The query's tail scan consults `texts` too (see [Querying](#querying)). A reorganization rewrites `texts` rows as it rewrites postings, and two rows for the same value become one row.

The eligibility rule is unchanged, and it's a property of the bytes alone: the size cap and the text sample. A grep step that examines a content value gets the same answer in every namespace.

The index deduplicates a content value within a namespace. A value is indexed once, however many revisions of the namespace reference it: a file restored to an earlier revision, a file copied by reference, or a file merged into main under the fork's content ID. Byte-identical content under two content IDs is indexed twice, because content IDs are random, and nothing in the store records that two content IDs have the same bytes. An index of content by a digest of its bytes (a "digest index") would record that, and the store has no digest index.

Why do postings store ordinals instead of content IDs? Content IDs are random, so sixteen raw bytes for each posting don't compress. With content IDs in its postings, an index of a 100,000-file fixture measured 1.7 times the bytes of a revision-keyed index. With ordinals, the same fixture's postings take 0.63 bytes each on disk, against about 10.7 bytes in a revision-keyed index (see [Costs](#costs)). A gap under 128 takes one byte before compression, and the gaps of a sparser gram take up to three.

Why is an ordinal local to its run? If the index assigned each content value one number for the whole namespace, the numbers would collide across the members of a pool, because a fork and its source would allocate the same numbers to different values after the fork point, which is why an inode ID's low 64 bits are random. A run can't change once it's written, and a fork inherits a run with its value table, so an ordinal identifies the same value in every namespace that lists the run.

## The content-to-revisions index

A query that finds a content value needs the revisions that reference the value in the namespace that the query searches, and no core row family is keyed that way. The `revisions` family is keyed by inode, and `content_layouts` is keyed by content ID but stores extents, not inodes. So the index has a third row family, `content_revisions`, which is stored in the index's segments beside postings and `texts`, with one row for each file revision:

```text
content-revision-{content_id_body}-{size_bytes:020}-{inode_id_body}-{u64::MAX - revision_no:020}
```

The row records the sequence of the revision's commit (`committed_seq`). Its filter key is the content ID and size, so a lookup by content value reads one prefix, and within the prefix each inode's rows are next to each other, newest revision first.

The rows come from inputs that the index already reads. A backfill step lists every file and reads its current revision's content reference, so it writes a row for each file, including a deleted file. A build step takes the inode, the revision number, and the content reference from each `file_created` or `content_changed` event that it indexes, and it writes a row for each event, including an event whose value it skips because `texts` already records the value. So the family has a row for every revision committed since the index was enabled, and for every file that was current when the index was enabled, which covers every sequence that a cursor issued under this build of the index can refer to (see [Querying](#querying)). A restore commits a new revision, and the change feed reports that revision in a `content_changed` event, so the restored file gets a row too. A fork inherits the family with the rest of the index, and every inherited row describes a revision at or below the fork point, which is the same revision in both namespaces.

A base-level reorganization prunes the family. It drops a row whose `(inode_id, revision_no)` pair isn't in a Bloom filter over the namespace's revisions, which its first step builds from the same scan that builds its pruning filter (see [Pruning the index](#pruning-the-index)), so the family adds no scan of the revisions. The filter errs only toward keeping a row, and a query ignores a row whose revision isn't the inode's current revision in any case (see step 2 in [Querying](#querying)).

In the lab's 100,000-file fixture, the family's 100,000 rows take 6.29 MB of the index's segments.

Why is the family part of the grep extension and not part of core? Grep is the family's only reader, and grep needs rows only from the time the index is enabled, so the index writes them from the steps it already runs. As a core family, it would cost every deployment about a quarter more metadata bytes and one more segment for each fold, whether or not any namespace is indexed (see [Alternatives considered](#alternatives-considered)).

## Pruning the index

If every reorganization unioned its input batches, a namespace's index would keep a posting for every value that the namespace ever examined, including every value that a fork inherited, and only a disable would reset the index. So a base-level reorganization prunes the index.

A base-level reorganization drops a content value's postings and its `texts` row together when no revision in the namespace references the value. The reorganization's first step records the namespace's head sequence when the step starts (`filter_seq`) and the retention floor at that time in the reorganization's in-progress record (`reorganize`). The reorganization prunes against the revisions that the retention rule keeps at that floor, read from the namespace at `filter_seq`: every revision newer than the floor, plus each file's newest revision at or below the floor, including the revisions of deleted files. The read at `filter_seq` includes the WAL tail. A grep step indexes commits that are still in the tail, so a filter built from the manifest alone would drop a value that only an unfolded commit references. The watermark would already have passed that commit, so nothing would index the value again. A value that any retained revision references stays, so a restore to a retained revision finds the value's postings, and a value that no revision references leaves no row. The postings and the `texts` row are dropped together, because dropping the postings and keeping the `texts` row would make a later grep step skip the value when a merge or a restore brings the value back, and the value would be unsearchable.

The first step scans the namespace's revisions at `filter_seq` once, and it builds two Bloom filters from the retained revisions: one of their content values, and one of their `(inode_id, revision_no)` pairs, which prunes the `content_revisions` family (see [The content-to-revisions index](#the-content-to-revisions-index)). It also builds the output run's value table, which lists the input tables' values that the value filter contains. The step writes the revision filter as `filter` rows in the output run's first segment, beside the value table and its rows. The filter is split into 32 KiB chunks in the existing filter-block encoding, and each chunk is a row keyed `filter-{chunk:020}`. The value filter isn't stored, because once the output table is written, no step reads the value filter again. `reorganize` records only `filter_seq` and the floor. Core protects only the segments that `runs` lists, so a filter stored in the output run is kept by the same listing that keeps the table. Every later step reads the revision filter and the table back from the reorganization's outputs, instead of scanning the namespace again. Each step keeps a value's postings and `texts` row exactly when the output's table lists the value, and drops each `content_revisions` row whose pair isn't in the revision filter. If the retention floor passes `filter_seq` before the reorganization finishes, the reorganization is abandoned, and a reorganization that hasn't published a step is abandoned without a publication. The reorganization costs one scan of the namespace's revisions and the revision filter's rows (43 rows and 582 KB on the lab's 100,000-file fixture). The scan doesn't share a read with core's base compactions, because a base compaction and a reorganization run at different times.

Why does the first step build the filters and the output table for every later step? The filters depend only on `filter_seq` and the recorded floor, so when the first step builds them once, every step uses the same filters, and a later step doesn't need a scan. Filters built again from the rows that a later step found could differ, because the step can read a different manifest, and a Bloom filter's false positives depend on what the filter contains. If each step built its own filters and table, one step could keep a value's postings while another dropped the value's `texts` row, and a grep step would skip that value when it came back. Every step reads the revision filter and the table that the first step wrote, so every step keeps and drops the same values and rows.

A merge can bring a value back while a reorganization runs. A restore can't, because a writer refuses to restore a revision that the floor pruned, and the floor that it validates against is never below the floor that the filters used ([Advancing the retention floor](../specs/format.md#101-advancing-the-retention-floor)). Suppose a base-level reorganization builds its filter and finds that no revision references a value. A merge then commits a file with that value, and a build step finds the value's `texts` row, skips the value, and advances the watermark past the merge. If the reorganization then published its output, it would drop the value's postings and `texts` row, and the file would exist but grep would never find it, with no indexing work left to do.

So before the last step of a base-level reorganization publishes, the step runs a "re-reference check". It reads the change feed from `filter_seq` to the head, and it checks whether a `file_created` or `content_changed` event refers to a value that an input run's table lists and the output's table doesn't. If the check finds such a value, the reorganization is abandoned and its outputs are left to the collector. The inputs stay listed, so the value stays searchable, and the next reorganization builds a new filter that keeps the value. The check costs a scan of the change feed over the reorganization's own duration, and it abandons a reorganization only in the rare case where a value comes back while the reorganization runs.

A build step needs no check of its own. If a build step skipped a value because `texts` recorded it, and the step's publication then lost to the reorganization that dropped the value, the step publishes nothing, because the reorganization changed the grep entry. The next step plans from the winning manifest, which no longer records the value, so that step reads and indexes the value (see the Publication rule in [The index in the core manifest](#the-index-in-the-core-manifest)).

A fork's first base-level reorganization rewrites the whole inherited base into fork-owned output, as a fork's first base compaction rewrites its inherited metadata base. Until then, the fork's reads use the inherited segments, which the fork snapshot keeps.

## The index in the core manifest

The core manifest has an `extensions` field, a JSON object that maps each extension's name to that extension's entry. An entry is a JSON object too, because a manifest is a JSON payload. Core parses two members of an entry, `version` and `runs`, and it writes the other members back unchanged, as JSON values that it doesn't interpret. For grep, the entry has these fields:

| Field | Meaning |
| --- | --- |
| `version` | The grep format's version, which is 1. |
| `status` | The lifecycle state and its position fields: `disabled`, `backfilling` with its snapshot and cursor, or `active` with the `captured_seq` of the backfill that built the index, the watermark, and `next_event_index`. |
| `reorganize` | The in-progress reorganization, if any. A reorganization into the base level also records `filter_seq` and the retention floor. |
| `runs` | The index's runs, each with its run number, its level, and its segment descriptors. A descriptor has the segment's owner, row count, key range, block handles, and inline filter, in the same representation as a metadata segment descriptor. |

Core handles the entry like this:

- **Publication.** Every core publication other than a tombstone copies the entry forward unchanged: a fold, a compaction, a compactor's claim, a retention window change, and a writer's claim. A tombstone copies the entry with its `runs` emptied (see Collection below). A grep step's result is a change to the grep entry. The runs that the change writes have provisional numbers until the change is published, and the publication assigns their numbers from the `next_run_no` of the manifest that it's published over, as a compaction assigns its run's number. Grep publishes its changes in core manifests of its own, as compaction does, paced by the server's maintenance interval (`maintenance_interval_ms`, five seconds by default). The steps that a namespace runs within one maintenance interval pend in memory and publish once, and a sweep publishes a namespace's pending change when the namespace's index step ends. Each step starts from the pending entry, not the manifest's, because a step that started from the manifest's entry would index the previous step's range again, since that step's `texts` rows aren't published yet. So a crash loses at most the steps of one interval, and their segments are left to the collector. Grep's publication is a maintainer publication under the format's publication rules ([Publishing a manifest](../specs/format.md#72-publishing-a-manifest)), made under the current compactor epoch and without a claim, and its manifest changes only the grep entry and `next_run_no`. The last step of a base-level reorganization runs the re-reference check before it publishes (see [Pruning the index](#pruning-the-index)), and the reorganization is abandoned if the check finds a value that came back, or if the retention floor has passed `filter_seq`. Grep's publication can lose the numbered put, or a put whose outcome is unknown can find another payload at its number. If the winning manifest's grep entry is the one that the change built on, as it is after a fold, a compaction, a claim, or a retention window change, the change is still valid, so it's published over the winner with its new runs numbered from the winner's `next_run_no`. If the entry changed, another process planned a change from a different state, so nothing is published, and the pending steps' segments are left to the collector. The next step loads the winning manifest and plans from its state, so a build step indexes the same range again, and a reorganization whose publication lost is planned again by its next step. Redoing the work costs one tick's steps, and it needs no second mechanism. A fold that loses its put to a grep publication keeps the WAL tail it read, because the two manifests differ only in their number, `next_run_no`, and `extensions`. `extensions` is in the format's list of fields that a fold can ignore.
- **Forks.** A fork's first manifest copies its source's `extensions` entry from the snapshot's manifest, as it copies the source's runs, without reading the entry. An `active` entry is then the source's index as of the snapshot's manifest, and the fork's own commits are the index's unindexed tail. A `backfilling` entry is inherited with its runs, and the fork's first grep step finds a snapshot whose owner is the source and restarts the backfill in the fork. The restarted backfill keeps the inherited runs, takes a snapshot of the fork's own head, and sets the cursor to the beginning. That walk is cheap, because each value that the inherited runs examined costs a `texts` lookup rather than a read. An inherited `reorganize` is the source's, with source-owned outputs, so the fork's first grep step clears it, and the fork's own reorganizations start from the inherited runs. The fork then reorganizes inputs whose outputs it also inherited, which is harmless, because a reorganization unions its inputs and duplicate rows become one row. A `disabled` entry stays disabled. A rebootstrap of an active index keeps its runs the same way, because content-keyed postings stay valid.
- **Snapshots.** A snapshot keeps every segment that its manifest lists, so the fork snapshot protects a fork's inherited index segments from the source's collector until the fork is retired, and a snapshot keeps the index that was current when the snapshot was taken.
- **Collection.** Core's segment rule applies to extension segments as it applies to metadata segments, so a segment is collected once neither the current manifest nor a manifest that a snapshot keeps lists it and the segment is more than 24 hours old. The collector lists each extension's segment prefix as it lists `segments/`. Disabling the index empties the entry's `runs`, and so does a namespace's tombstone, so a deleted namespace's segments become unlisted objects that later collections delete once they're more than 24 hours old. Fork snapshots keep the segments of their manifests whatever the tombstone lists.
- **Validation.** Core validates that each run's number is below the manifest's `next_run_no` and that no other run in the manifest, metadata or extension, has the same number. Core also validates that the entry's segment IDs are unique and that each descriptor has block handles. Core never decodes a row.

A segment's key is `namespaces/{owner}/extensions/grep/segments/{segment_id}.sst`, where the owner is the member that ran the step. A fork's manifest lists segments owned by its source and segments it wrote itself, as it does for metadata runs. Grep has no hint or manifest sequence of its own, so a query sends no successor HEAD, and grep has no discovery, publication retry rules, or collector of its own.

A query reads the index from the read view it already has, and the index is as current as the view's manifest. The unindexed tail is the namespace's commits after the watermark, read from the change feed. A fold can fold commits that grep hasn't indexed, and a grep step can index commits that are still in the WAL tail, so the watermark and the manifest's folded position are independent. Garbage collection keeps every WAL object above the current manifest's `folded_wal_no`, so both positions are readable from any view of the manifest. A query can still read at a sequence below the index's watermark: a page after the first reads at its cursor's head sequence, and an eventual read within its staleness window can be below a watermark that the server's scheduler just advanced. Step 2 in [Querying](#querying) covers both cases. The query also takes no new read view when the index is ahead of the query's view, because step 2's cut covers that case too.

Why are extension runs listed in the core manifest? An inherited index needs three mechanisms (copying at fork time, protection by snapshots, and collection by reachability), and the core manifest provides all three for metadata runs. If grep had its own copies of those mechanisms, a fork couldn't inherit the index. Core never decodes an extension's rows, but the core manifest lists their segments.

## Building the index

Enabling the index publishes a `backfilling` entry with a user snapshot on the namespace head. Each backfill step lists files from the snapshot in inode order, reads each current revision's content reference, writes a `content_revisions` row for the revision, skips a value that `texts` already records, tokenizes the rest, and records new delta segments and the cursor in the pending entry, which grep publishes in a core manifest once for each maintenance interval. The final step records `active` at the captured sequence, and grep deletes the snapshot after it publishes that entry.

A build step on an active index reads the change feed from its cursor. For each `file_created` or `content_changed` event, the step takes the event's content reference, writes a `content_revisions` row for the revision, and skips the value if `texts` records it. Otherwise, the step reads the content, checks eligibility, tokenizes the content, and writes postings and a `texts` row. Moves, deletes, and restores publish no content and need no postings. The cursor advances in the same publication as the segments. A build step plans its content budget from the sizes that the events record, before it looks up `texts`, so it can stop early on values that `texts` already records. Consulting `texts` costs a grep step one filter probe for each segment and a block read on a hit.

A fork's first grep step starts from the inherited watermark. When the source's index was current at the fork point, that step indexes the fork's own commits and nothing else. No grep step runs in a fork that's never written to, and in a fork where a thousand files are written, grep steps read at most a thousand files.

The inherited watermark can be below the fork point, because the source's index lags its head, and a step's change can wait up to the five-second maintenance interval before it's published. The fork can't read that gap from its own change feed, because the fork's retention floor is the fork point. So the step reads the gap from the source through the fork snapshot, as a [rebase](merge.md#rebasing) reads its source through the snapshot. The gap is the source's commits above the watermark and at or below the fork point, and the `commits` rows of the snapshot's manifest keep those commits until the fork is retired. The snapshot's manifest keeps commits from the source's retention floor at snapshot time, so the gap is readable when the watermark is at or above that floor, which is true unless the floor passed the watermark before the fork was created. Otherwise, the fork's index is backfilled from scratch, which `texts` makes cheap. In practice the gap is a few seconds of the source's commits, because the server's scheduler indexes a namespace with an open writer session within seconds of each commit.

A merge into main appears in main's change feed as the merge's events, whose content references are the fork's. Main's `texts` rows don't record those values, because the fork's segments aren't listed in main's manifest, so grep indexes the merged content in main, at the cost of reading what the merge brought in. A rebase's new fork inherits main's grep index at the head that the new fork was created from, and grep indexes the replayed content in the new fork the same way.

Reorganization keeps its shape: three levels, bounded steps, a recorded input set, and inputs and outputs that stay visible until the final step. A fork's reorganization rewrites inherited runs together with the fork's own runs into fork-owned output. The inherited inputs stay where they are, kept for the source by the source's manifest, and for the fork by the fork snapshot until the fork is retired.

## Querying

A query plans its grams and intersects posting batches, and the candidates are content values. For each candidate value, the query:

1. Reads the index's `content_revisions` prefix for the value, which yields the `(inode_id, revision_no)` pairs that reference the value, grouped by inode, with each inode's newest pair first.
2. Keeps each inode's newest pair whose `committed_seq` is at or below the query's "cut", and checks in the `revisions` family that the pair is the inode's current revision at the sequence the query reads at (the "read sequence"). The cut is the read sequence, or, when `allow_stale` applies because the unindexed tail is larger than one query scans, the lesser of the read sequence and the watermark, as the next paragraphs describe.
3. Checks visibility, scope, and the subject's rights on each inode that passed.
4. Reads and verifies the value's bytes once, through a revision read of the first file that passed, and reports the matches for each file that passed. (A read of content by its reference alone requires an administrator, so the query reads through a file that the subject can read.)

Two candidate budgets bound a page. The examined-candidates budget (4,096 files) counts files, so a prefix read stops when the budget is reached, inside a value's prefix if that's where the budget runs out. The cursor then records that value and the inode the page finished at, and the next page's prefix read resumes after that inode. The verified-candidates budget counts content values, because the query reads each value's bytes once, however many files reference the value. Why don't both budgets count files? If the verified-candidates budget counted files, a page whose candidates were many files with one value, all of them false positives, would spend the budget on that one value and return no matches, only a cursor. The prefix read costs one row for each retained revision that references the value, and the retention floor bounds that number.

When `allow_stale` lowers the cut, the query still reads at the head, so visibility and current revisions are the head's. The query treats the commits above the watermark as unscanned. Step 2 keeps only pairs whose `committed_seq` is at or below the lesser of the watermark and the read sequence, and it leaves out the commit at the watermark when the index covers that commit only in part (`next_event_index` above zero). A file whose current revision is newer than the cut is left out, as a stale result allows. Reading at the watermark instead would show files deleted after the watermark, and a caller who opted into index staleness didn't opt into that.

Then the query reads the unindexed tail (the files with a revision committed after the watermark) within the tail budget, under three rules. First, for each tail file, the query consults `texts` for the file's current content value. A value with a `texts` row is either ineligible, in which case the file is skipped, or indexed, in which case the posting intersection already produced the value as a candidate, so the query reads only the tail values that have no row. Second, in a fork whose watermark is below the fork point, the tail begins in the source, read through the fork snapshot as a grep step reads the gap, and continues in the fork's own change feed. Third, a tail file is sorted into the page's order by its current content value. `index_lagging`, `allow_stale`, and `rebootstrap_required` keep their meanings over the whole tail.

Candidates arrive in content order, so a page's matches are ordered by content value, then inode, then byte offset. The cursor records the content value, the inode, and the position inside the file at which the page finished, with the head sequence and the request's fingerprint. The cursor also records the sequence that the active index's backfill captured (`captured_seq`), and an active entry keeps that sequence to identify the index's build. A page served by an index whose `captured_seq` differs from the cursor's returns `invalid_request`, the error for a cursor that isn't valid, and the client starts the search again. A rebuild after a rebootstrap, or after grep is disabled and enabled again, can capture a sequence above the cursor's head sequence, and the rebuilt index's `content_revisions` rows don't cover the older sequence that the next page would read at. A rebuild that captures the same sequence has rows for the same sequences, so a cursor issued before the rebuild stays valid. The API promises that candidates the cursor has passed aren't revisited, even if later commits changed them. In content order, a file whose content changes between pages would move to a different place in the order. So each page after the first reads the namespace at the cursor's head sequence, as the diff route reads at a sequence between the floor and the head ([`GET /diff`](../specs/api.md#612-get-diff)), and step 2 above keeps the candidate set the same on every page. A later page checks the subject's rights at the head, and it serves a file that changed after the cursor's sequence only to a subject with the `history` right, as a snapshot read does. The index that a later page uses can have a watermark above that sequence, which step 2's cut also covers. When the retention floor passes the cursor's head sequence between pages, the next page returns `rebootstrap_required`, as a tail that falls below the floor does. A client that needs inode order sorts a page.

Everything that depends on the namespace's current state still comes from the namespace: a path-prefix scope, the subject's rights, and whether a revision is a candidate's current revision. The index records which revisions referenced a value, and the query checks each of those revisions against the namespace.

## Lifecycle and maintenance

The lifecycle has the three states that [Index lifecycle](content-search-index.md#index-lifecycle) describes, and the state is read from the core manifest's entry. The index has no run counter of its own, so the status route reports no run number. The server's maintenance scheduler runs the index steps as [Maintenance hosting](maintenance-hosting.md) describes, so a namespace with an open writer session is indexed within seconds of a commit. The CLI's `maintenance index enable` runs the same bounded steps. A one-shot CLI command has no later maintenance interval to publish its pending change, so it publishes the change when the command ends.

Grep's publications are paced by the maintenance interval. The steps that a namespace runs within one five-second interval publish as one manifest, and a run of steps publishes what's pending when it ends. Without pacing, a run of sixteen steps would publish sixteen manifests, and that many manifests trigger two of core's rules. A writer whose position walk finds more than eight new manifests drops its position and rediscovers it with a tail replay, and every cached reader's successor probe finds a successor and runs discovery. Pacing keeps grep to at most one manifest every five seconds, and it bounds what a crash loses to the steps of one interval. The backfill case is what sets the interval, because with a five-second interval, a backfill becomes searchable as it goes, rather than when the backfill ends. A graceful shutdown publishes the pending change, rather than leaving its segments to the collector.

The core collector collects the index's segments and counts them in a `gc` result's `deleted.extension_segments`, so a deployment runs one collector.

## Costs

The lab measured the content-keyed index against a revision-keyed index (the first item in [Alternatives considered](#alternatives-considered)) on a fixture of 100,000 files. The query rows are the lab's `selective`, `rare`, and `common` grep queries, with a warm or a cold cache.

| Measure | Revision-keyed index | Content-keyed index |
| --- | --- | --- |
| Build, total | 144.3 s | 76.8 s |
| Build steps | 43.7 s | 43.7 s |
| Reorganizations | 100.3 s | 33 s |
| Segment bytes | 2,047,625,559 | About 131.5 MB |
| Bytes for each posting on disk | About 10.7 | 0.63 |
| Warm `selective` query | 0.25 ms | 0.25 ms |
| Cold `selective` query | 12.5 ms | 10.7 ms |
| Warm `rare` query | 55 ms | 64 ms |
| Warm `common` query | 86 ms | 80 ms |
| Cold `common` query | 195 ms | 676 ms |

The build takes about half as long, and the whole difference is in the reorganizations. A reorganization step remaps postings through its translation lists, instead of mapping each posting to a content value and searching the output table for it. The index is about sixteen times smaller. Its 131.5 MB consist of 190.8 million postings in 119.4 MB, 100,000 `content_revisions` rows in 6.29 MB, 100,000 `texts` rows in 2.77 MB, 100,000 value rows in 2.44 MB, and 43 `filter` rows in 582 KB. Of the cold `common` query's 676 ms, core spends 453 ms resolving the query's stat batch one inode at a time.

- **Postings.** Each posting is an LEB128 gap between ordinals, and each run stores a value table with one row for each value that has a `texts` row in the run. The index also stores one `texts` row for each content value that a grep step examined.
- **The `content_revisions` family.** The index stores one row for each retained file revision, and the fixture's 100,000 rows take 6.29 MB. A base-level reorganization prunes the family with a filter from the scan that it already makes. A deployment without grep doesn't pay for the family.
- **Core manifests.** Grep's segment descriptors join the manifest, roughly doubling the descriptor count for a namespace whose index has as many segments as its metadata, and every reader loads them whether or not it greps. So the manifest cache's 32 MiB default fits about half as many of these namespaces, as the [block cache](block-cache.md) note describes. The format's example manifest is 193 KiB of JSON and 36 KiB compressed, against a 512 MiB limit.
- **Publications.** Grep publishes one core manifest for each maintenance interval with grep work, plus one at the end of a run of steps. When a publication loses its put to a manifest that copied the grep entry, the change is published over that manifest. When another process changed the entry, the change publishes nothing, and the next step plans from the manifest that won.
- **Grep steps.** Before each content read, a grep step makes one `texts` filter probe for each segment, and a block read on a hit.
- **Pruning.** A base-level reorganization scans the namespace's revisions once, at `filter_seq` in its first step, and builds two filters, one keyed by content value and one keyed by `(inode_id, revision_no)`. It writes the revision filter as `filter` rows in its output's first segment, and later steps read those rows back, and core's base compactions don't share the scan. The last step also reads the change feed for the reorganization's duration. A fork's first base-level reorganization rewrites the inherited base into fork-owned output.
- **Queries.** A query makes one `content_revisions` prefix read for each candidate value, and one current-revision check for each inode that the prefix read yields. For a warm namespace, the segment cache serves those checks.
- **Forks.** Creating a fork has no grep cost. The inherited index is a copy of descriptors in the fork's first manifest, and closing the source's lag below the fork point reads a few seconds of the source's commits through the snapshot.
- **Merges.** Grep reads and tokenizes the merged content in main once, a cost in proportion to the merge.

## Alternatives considered

- **A revision-keyed index for each namespace, with its own log.** Each posting identifies `(inode_id, revision_no)`, the index's objects are stored under the namespace's own prefix, and the index has its own numbered manifests, hint, discovery, and collector. A fork starts with no index and builds one from scratch, which takes longer than the lifetime of a sandbox, and identical content in two namespaces is indexed twice. On the lab's fixture, a revision-keyed index takes about sixteen times the bytes of the content-keyed index (see [Costs](#costs)).
- **Copy the grep manifest at fork time, with a grep collector for each pool.** Fork creation would call into each extension, the grep collector would walk the pool's members as the pool's collection does, and grep would keep its parallel log. Listing the runs in the core manifest provides the same inheritance through machinery that exists.
- **Store grep segments under the pool's prefix, like content.** This isn't needed, because segments listed in a manifest are kept by the snapshots that keep the manifest, so per-owner segments are inherited and protected the way metadata segments are, and the pool's collection doesn't need to find them.
- **Dense content numbers across the namespace, delta-encoded.** They collide across the members of a pool. Numbers local to a run don't, because each run stores its own value table.
- **Content IDs in postings.** Sixteen random bytes for each posting don't compress, and an index of a 100,000-file fixture measured 1.7 times the bytes of a revision-keyed index.
- **Postings keyed by digest.** They would deduplicate byte-identical content under different IDs, which content IDs can't. They need a digest index first, and the `texts` family is where they plug in.
- **A core `content_revisions` family.** Core would compute the family's rows from each `append_file_revision` delta in a fold or a replay of the WAL tail, store them in a family group of its own, and prune them in a base compaction against a filter over the basis's revisions. The family would then have rows from before the index was enabled, which nothing needs, and it could serve a use without grep. In exchange, every deployment would store about a quarter more metadata bytes (5.5 MB against 21.4 MB for all other families in a namespace of 100,000 files with one revision each), and every fold would write one more segment.
- **List a fork's grep runs in main's manifest at merge time, to avoid re-indexing.** Main's manifest would list fork-owned segments, and main would need a snapshot on the fork, which is the reverse snapshot that the design in [Pools](pools.md#alternatives-considered) avoids. Re-indexing the merged content costs a read of what was merged.
- **Keep the grep manifest sequence and add a pointer to it from the core manifest.** Inheritance through the snapshot would then protect the pointer and not the segments, so the grep collector would still need to find every member.
- **Keep inode order in query results.** The query would have to collect every candidate before it could return the first page, because candidates arrive in content order from the posting batches. Reading each page at the cursor's head sequence keeps the promise not to revisit a candidate that the cursor has passed, in content order instead.
- **Keep every posting.** A namespace's index would keep a posting for every value that the namespace or its source ever examined, and the indexes of a pool's members would grow without bound. Pruning against the retained revisions costs one scan and the revision filter's rows for each base-level reorganization.
- **Build steps that ignore `texts` while a base-level reorganization is in progress.** A build step would read and tokenize every value that a commit in the reorganization's window writes, so a value that came back would be indexed again whatever the reorganization dropped. But the step would re-read every value that's already indexed, and for a large merge that's most of the merged content. The re-reference check costs a scan of the change feed over the same window, and it abandons a reorganization only when a value actually came back.
- **A build step skips a value only when its `texts` row is in a run that isn't an input of an in-progress base-level reorganization.** This one-line rule closes the race within one process. But a build step in another process can index a commit above the reorganization's `filter_seq` while its view still has a manifest from before the reorganization published its in-progress record (`reorganize`), because a view's WAL tail advances without its manifest. That step skips a value that the reorganization is about to drop. The window is a few seconds and the loss is silent, so the design keeps the re-reference check at the reorganization's final publication.
- **Publish one core manifest for each grep step.** Sixteen manifests in one run of steps would make every writer drop its position and every cached reader run discovery again, for work that core's readers don't otherwise see. Publishing the steps of each maintenance interval once keeps grep to at most one manifest every five seconds.
- **Batch a run's steps into one publication.** Batching would keep a run of steps to one manifest, but a crash would lose every step of the run. Pacing by the maintenance interval bounds the loss to the steps of one interval.
- **Include a step's change in the namespace's next fold or compaction.** A fold or a compaction in the same process would include the pending change in the manifest it publishes, so grep would add no manifest where a fold happens anyway. The price is a hook into the fold's publication path, and a fold or compaction that has to reconcile the pending change with a basis whose grep entry can differ from the one the step started from. Keeping grep's publications separate avoids that hook and that reconciliation.
- **One runs object for each extension, listed in the manifest.** The manifest would list one immutable object that stores the extension's segment descriptors, kept by reachability like a segment, and the collector would follow that one pointer to find the extension's live segments. Inheritance through snapshots and collection by the core collector would work as in this design, at one extra GET for each manifest in a collection, and the manifest cache would fit as many namespaces as it fits without an index. Listing the descriptors in the manifest is simpler, and its cost is the larger manifest that [Costs](#costs) describes.
