# A window for replaced manifests

This note proposes two rules that keep a replaced manifest readable for a while after it's replaced. A [collection](../specs/glossary.md#collection) would keep every manifest that a newer manifest replaced less than 45 minutes ago (a "kept manifest"), and it would load the oldest kept manifest to keep the segments that it lists, the WAL objects above its `folded_wal_no`, and the content objects that its layouts and its WAL tail refer to. A requirement on every manifest publication makes that one manifest enough. The requirement says that a manifest lists no segment of its own namespace that its basis doesn't list, other than segments that its own publication wrote. A [writer position](../specs/glossary.md#writer-position) whose last check is at least the [revalidation bound](../specs/glossary.md#revalidation-bound) old (20 minutes) would be checked before it's used as the basis of a publication. Together, the two rules mean that a process that checked its manifest recently finds the segments, WAL objects, and file bytes it needs, so the code that runs a read or a publication again after it finds a segment missing can be deleted. Nothing in this note is implemented yet, and the [format spec](../specs/format.md) describes today's rule.

## The problem

This section describes what a collection keeps today, and an example in which a process loses a segment and a file's bytes a second after it checked its manifest.

### What a collection keeps today

A namespace's collection keeps the current manifest (or the tombstone), the manifests that snapshots keep, and every segment that those manifests list. It keeps every manifest numbered above the newest one it found, and in an active namespace, every data WAL object above the current manifest's `folded_wal_no` (see [Reference roots](../specs/format.md#112-reference-roots)). A manifest below the newest one isn't a root unless a snapshot keeps it, however recently it was replaced.

Everything else is a candidate. A segment that no root lists is deleted once its provider age is at least the [grace window](../specs/glossary.md#grace-window) `T` (24 hours), and so is a data WAL object at or below the current manifest's `folded_wal_no`. In a deleted namespace, every data WAL object is deleted once it's `T` old (see [Candidate and age rules](../specs/format.md#113-candidate-and-age-rules)). The age is measured from when the object was written, not from when the last manifest that listed it was replaced. So a segment that's older than `T` when a compaction drops it is deleted by the next collection, however recently the compaction published.

Content objects follow the same pattern. A [pool](../specs/glossary.md#pool)'s collection keeps a content object while the extent filter of a `content_layouts` segment in a member's current manifest or snapshot manifest matches the object's name, or while the member's unfolded WAL tail or an upload session refers to the object's chain (see [Content roots](../specs/format.md#119-content-roots)). It deletes any other content object once the object is `T` old. So a span object that's older than `T` when a compaction drops the last layout row in the current manifest that lists it is deleted by the next collection of the pool.

Segments younger than `T` are safe for `T` whatever happens, and most compaction output is young. The objects at risk are segments that were older than `T` when a manifest stopped listing them (the inputs of a compaction of old runs), content objects of the same age that a fold merged into a new span object (a span object or an upload's whole object that an old layout listed), and WAL objects that stayed unfolded for more than `T`. A maintained namespace folds its tail once the tail's newest commit is 15 minutes old, so an unfolded tail that old needs a namespace that nothing maintained for a day, for example while its maintaining server was down.

### An example that loses a segment, a span object, and a WAL object

For example, the namespace `main` has a manifest boundary of 38:

1. Manifest 40 has been current for two days, and its `folded_wal_no` is 300. It lists `S`, a `content_layouts` segment written three days ago. One of `S`'s rows is the layout of `/logs/app.log`, which lists span object `A`, also written three days ago. WAL objects 301 to 305 were written 30 hours ago, while the server that maintains `main` was down, so nothing has folded them. One of them appends as many bytes to `/logs/app.log` as `A` contains.
2. At 10:00:00, a reader process checks manifest 40. The HEAD of manifest 41 finds nothing, and the boundary is still 38. A read of `/logs/app.log` starts from that view.
3. At 10:00:01, the maintaining server starts again, and its first sweep runs `main`'s metadata step. The step folds the tail into manifest 41 (`folded_wal_no` 305). For `/logs/app.log`, the fold's doubling rule merges `A` with the appended bytes into a new span object `B`, and writes a new layout row that lists `B` in a new segment. A compaction unit then publishes manifest 42, which rewrites `S` and drops the replaced layout row, so no layout in manifest 42 lists `A` (see [Extent assembly and the doubling rule](../specs/format.md#extent-assembly-and-the-doubling-rule)).
4. At 10:00:02, the same sweep collects `main`. The collection finds manifest 42 as the newest. No root lists `S`, which is three days old, so the collection deletes it. WAL objects 301 to 305 are at or below 305 and 30 hours old, so the collection deletes them too. The sweep then collects `main`'s pool. No extent filter of manifest 42's layout segments matches `A`, which is three days old, so the pool's collection deletes it.
5. At 10:00:03, the read loads the layout row from `S` and finds `S` missing. If `S` were still there, the read would find `A` missing instead. A process that evicted its copy of the tail and replays WAL objects 301 to 305 finds them missing too.

Today, the load that finds `S` missing runs a discovery to learn whether manifest 40 was replaced. It was, so an ordinary read runs again from manifest 42, up to eight attempts in all, and then returns `store_contention`. A read view returns `store_contention` at once. A fold, a compaction unit, a commit batch, and a retention advance each have a branch of their own for the same error (see [Replaying the visible WAL](../specs/format.md#42-replaying-the-visible-wal)). A missing content object isn't checked against a replaced manifest at all, so a read that finds `A` missing returns `namespace_corrupt`.

A writer position is exposed for longer. A publish doesn't check the position's manifest (see [Read freshness](read-freshness.md#one-view-per-process)), and a check doesn't run because of the position's age. Other processes publish manifests at the session's writer epoch (the maintaining server's compactions, a grep index publication, a snapshot's fold on another host), and the writer learns of them at its next check or its next manifest put. A writer that makes one small commit a minute reaches the 256-object fold threshold after about four hours, and its newest commit is never 15 minutes old, so the idle fold doesn't run either. Its commits validate against the rows of a manifest that may have been replaced hours ago, so no window short enough to be cheap would cover the position without a check.

## The design

This section describes the collection rule, the requirement on publications that lets a collection load one kept manifest, the gate on an aged writer position, how the window's length follows from the existing bounds, and what happens to work that no bound covers.

### The collection rule

A namespace's collection also keeps every manifest above the [manifest boundary](../specs/glossary.md#manifest-boundary) whose next listed manifest is younger than the replaced-manifest window, `REPLACED_MANIFEST_WINDOW_MS` (45 minutes), by provider timestamp. These are the kept manifests. The "next listed manifest" is the next higher number in the collection's listing of the manifests above the boundary, and the collection compares its timestamp with the same clock reading that its age rule uses. The collection keeps every manifest numbered at or above the oldest kept manifest. It loads the oldest kept manifest, besides the current manifest and the snapshot manifests that it already loads, and keeps the segments that the oldest kept manifest lists. It doesn't load the kept manifests between the oldest and the current one. And it keeps every data WAL object above the oldest kept manifest's `folded_wal_no`, in place of the current manifest's.

If the listing returns a manifest above the boundary without a provider timestamp, the collection can't choose the kept manifests, so it stops without deleting anything, as it does today when it can't read its current manifest (see [One complete collection](../specs/format.md#111-one-complete-collection)). The pool's collection treats that member's roots as unreadable, which stops its content deletion for the pass, as any unreadable member does. The format requires a listing to return each object's modification time (see [Required operations](../specs/format.md#31-required-operations)), so a provider that meets the format never causes this.

Why is the oldest kept manifest enough? Every manifest is built over the manifest one number below it, and the requirement in [The requirement on publications](#the-requirement-on-publications) means that a manifest lists no segment of its own namespace that its basis doesn't list, other than segments that its own publication wrote. So if a kept manifest lists a segment that the oldest kept manifest doesn't, some manifest `j` above the oldest kept one first listed that segment, and `j`'s publication wrote it. The segment's age then follows in three steps:

1. The oldest kept manifest's successor is less than 45 minutes old on the collection's clock, because that's why the oldest kept manifest is kept.
2. Manifest `j` is that successor or a later manifest. The provider's timestamps follow the order of the manifest puts, within the clock margin (as the paragraph below on the unbroken run of manifests explains), so `j`'s timestamp is at most the margin earlier than the successor's.
3. The publication of `j` wrote the segment at most the compaction budget before its put started, and the provider applied the put within its request bound, so the segment is at most the compaction budget plus the provider bound older than `j`'s timestamp.

The collection reads the segment's age and the successor's age on the same clock reading, so the difference between its clock and the provider's doesn't enter. The segment's age on the collection's clock is less than:

| Term | Value |
| --- | ---: |
| `METADATA_COMPACTION_BUDGET_MS`, the longest that a publication's write clock can run before its put | 12 h |
| `PROVIDER_PUBLICATION_REQUEST_BOUND_MS`, from the start of `j`'s put to its timestamp | 5 min |
| `GC_SAFETY_MARGIN_MS`, how much earlier `j`'s timestamp can be than the oldest kept manifest's successor's | 5 min |
| `REPLACED_MANIFEST_WINDOW_MS`, the successor's age | 45 min |
| Total | 12 h 55 min |

The total is below `T` (24 hours), so the age rule that every unlisted segment already follows keeps the segment. The format states the relation as a requirement on the constants. (The gap between a segment's write and its manifest's put, in which a collection can find the segment before any manifest lists it, is a different case. The relation of the compaction budget to `T` covers it through the age rule, as today.)

The argument is about segments of the manifest's own namespace, and forks are the two cases where that matters. A fork's manifest 1 has no basis, and it lists its source's segments, which can be any age. Those segments are stored under the source's prefix, which the fork's collection doesn't list, so the fork's collection never deletes them, and the source's snapshot of the fork point keeps them on the source. A fork's manifest 2 folds the source's tail, so its layouts can list content objects that neither manifest 1 nor the fork's own tail refers to. The fork point snapshot keeps manifest 2, so manifest 2 is a root of its own, and the collections load it with the other snapshot manifests.

The rule defines what a namespace's roots are, and that set is the same for the namespace's own collection and for its pool's collection. So when the pool's collection reads a member's roots, it chooses the member's kept manifests the same way, reads the extent filters of the layout segments of the oldest kept manifest as well as those of the current manifest and the snapshot manifests, and reads the member's WAL tail from the oldest kept manifest's `folded_wal_no` instead of the current manifest's. The pool's collection reads its clock before it reads any member, and it compares a member's listed timestamps with a reading of that clock taken when it starts reading that member (the start time plus the monotonic time elapsed since). A member that the collection reads hours after it started then keeps the manifests replaced within the window before that read, not every manifest replaced since the collection started. The argument in [Choosing the window](#choosing-the-window) is still true with the member's reading, because the pool's collection sends no delete before it has read every member. The age rule for content objects still uses the reading from the start, and an age measured against an earlier reading is smaller, so that rule keeps at least what it would keep with the member's reading.

The pool's collection reads that tail by one rule. It reads the WAL numbers in order from the oldest kept manifest's `folded_wal_no` upward. Above the current manifest's `folded_wal_no`, the first missing number ends the tail, and a number missing below a present one is corruption, as today. At or below the current manifest's `folded_wal_no`, a missing number means that the collection can't read the member's roots whole, so it deletes no content in that pass, as it does for any member whose roots it can't read. A read that took a missing number as the end of the tail would stop reading there. It would miss the commits above the current manifest's `folded_wal_no` and delete content that a reader of the current manifest needs.

Why does the oldest kept manifest's layout view cover the content of the kept manifests after it? A manifest's layout rows list no content object that neither a layout row of its basis nor a WAL object between its basis's `folded_wal_no` and its own refers to, other than objects that its own publication wrote. A manifest 1 has no basis, so the requirement doesn't apply to it, and a fork's manifest 2 is the exception described above. A new object that a fold writes is at most the publication budget plus the provider bound older than its manifest's put, so its age keeps it, as for a segment. So by the same induction as for segments, every content object that a kept manifest's layouts list is listed by the oldest kept manifest's layouts, referred to by a WAL object in the tail that the pool's collection reads, or young enough that its age keeps it.

A fold whose put loses to a compaction, a retention window change, or an extension publication at the same head reuses the layouts that it computed from its first basis, and those layouts stay within the requirement. A retention window change and an extension publication copy every layout row. A compaction keeps the longest, newest layout row of every chain, which is the row that a read of the chain uses, and a base compaction drops a chain only when no revision row in its basis refers to the chain. A chain that the tail appends to is referred to by the file's newest revision, and a chain that the tail restores from is referred to by a revision that the floor keeps for the restore (see [Advancing the retention floor](../specs/format.md#101-advancing-the-retention-floor)). A file hidden by an expired deletion can't be changed or restored by any commit, so the tail refers to none of its chains.

The induction is why a missing WAL number stops the pool's content deletion instead of being skipped. Suppose a WAL object bound an upload's whole object `c`, and both stayed unfolded for 30 hours. A fold publishes manifest `j`, whose layout lists `c`. A later fold merges `c` into a new span object, and a compaction drops `j`'s row. The pool's collection then chooses `j - 1` as the member's oldest kept manifest. Just before it reads the WAL, a namespace collection whose clock is later no longer keeps `j - 1`, and it deletes the WAL object, which is at or below `j`'s `folded_wal_no` and older than `T`. If the pool's collection skipped that number, neither the oldest kept manifest's layouts nor the current manifest's nor the tail would refer to `c`, and it would delete `c` while a process that checked `j` a minute earlier still needs it.

In the example above, `main`'s boundary is 38, and the collection that starts at 10:00:02 lists manifests 39 to 42. Manifest 40 was published two days ago, and manifests 41 and 42 at 10:00:01. Manifest 39's next listed manifest, 40, is two days old, so manifest 39 isn't kept. Manifest 40's next listed manifest, 41, is a second old, so manifest 40 is the oldest kept manifest, and manifest 41 is kept too. Manifest 42 is the newest. The collection loads manifests 40 and 42. It keeps the segments that they list, which include `S`, and the WAL objects above 300, manifest 40's `folded_wal_no`. A segment that manifest 41 lists and neither 40 nor 42 does was written by the fold at 10:00:01, so its age keeps it. The pool's collection reads the extent filters of manifest 40's layout segments, which match `A`, and reads WAL objects 301 to 305, which the namespace's collection kept. So `S`, `A`, and WAL objects 301 to 305 stay, and the read of `/logs/app.log` from manifest 40 finds them. A collection that starts at 10:45:01 or later no longer keeps manifest 40.

The layout view of the oldest kept manifest is needed for a layout row whose chain no kept tail refers to. For example, a read through manifest 40 of an older revision of a file, whose rows a base compaction drops after a retention advance passes the commit that replaced it (see [Row retention during a base compaction](../specs/format.md#103-row-retention-during-a-base-compaction)), needs that revision's span objects. They can be older than `T`, and no tail refers to their chain, so only the extent filters of manifest 40's layout segments keep them.

The rule applies to a deleted namespace too, until retirement, and so does the WAL floor. A deletion folds the tail before it publishes the tombstone, so the manifests that the deletion's fold and the tombstone replaced are kept for the window, and a process that checked one of them just before the deletion replays the WAL objects above that manifest's `folded_wal_no`. The pool's collection reads the tail from the oldest kept manifest's `folded_wal_no` for a deleted member too, although today it reads no tail of a deleted member. Today a deleted namespace keeps no data WAL object, so without the floor, the deletion of a namespace whose tail was older than `T` would lose that tail for such a process. A retired namespace has no roots, as today.

Why does the rule consider only manifests above the boundary? Every manifest at or below the boundary is dead, and a put that the provider applies late, into a number that a collection emptied, is at or below the boundary (see [The manifest boundary](manifest-boundary.md#publishing-a-manifest)). Counting such a manifest wouldn't make anything safer. It would keep the late put's garbage for the window.

Why does the rule keep one unbroken run of manifests? Above the boundary, each manifest was put by a publisher that had loaded its predecessor, so the provider's timestamps follow the order of the puts: a manifest's timestamp isn't earlier than any lower manifest's by more than the clock margin. So if one manifest's successor is younger than the window, every later manifest's successor is younger than the window plus the margin, and the kept manifests are the newest manifest and the manifests just below it, down to the oldest kept manifest. Keeping every manifest by number from the oldest kept one also keeps a later manifest whose successor's timestamp is up to the margin earlier, and the age argument above includes the margin for the same reason. The oldest kept manifest's `folded_wal_no` is also the lowest of the kept manifests', because a successor's `folded_wal_no` is never lower than its predecessor's.

Why move the WAL floor? A process replays the WAL objects above its own manifest's `folded_wal_no`, not the current manifest's. Without the floor, the example above keeps `S` and still loses WAL objects 301 to 305. The pool's tail root moves for the same reason. The tail of a kept manifest can refer to content objects that the fold then merged into a new span object, such as an extent that the commit's validation wrote, so the layouts of the manifests after it don't have to list those objects.

A collection lists the manifests twice today. To find the newest manifest, it lists the manifests above the boundary and keeps the highest number. Later, its sweep lists the whole manifest prefix and checks each manifest as the listing streams, deleting the old ones in batches. The kept manifests have to be chosen before that sweep starts, so the rule uses the first listing. That listing already returns each manifest's provider timestamp, and the rule needs the find step to return the listed numbers and timestamps instead of the highest number alone. The collection then loads the oldest kept manifest while it loads the snapshot manifests, adds its key and segments to its live set, and computes the WAL floor, so the sweep keeps them like any other root. The rule adds no listing. The pool's collection finds each member's newest manifest with the same listing.

Another collection can delete the oldest kept manifest between the listing and the load, if that collection's clock is later and it no longer keeps the manifest. Today the find step lists again when the newest manifest that it chose is missing at its load, and the same rule covers the oldest kept manifest. A collection raises the boundary before it deletes manifests, so the new listing starts above every deleted manifest, and the collection chooses the kept manifests from it against the same clock reading. Its oldest kept manifest is then the lowest kept manifest that still exists. Every process that checked the deleted manifest is outside its guarantee by the deleting collection's clock, so the segments, WAL objects, and content that only the deleted manifest needed can go.

### The requirement on publications

The collection rule depends on a property of every publisher, so the format states the property as a requirement, and one function in the core crate enforces it. Every manifest put goes through that function, which has the basis and the candidate in memory and already checks the candidate's fields against the basis's.

Each publication passes the function the segments that it wrote and the clock under which it wrote them, and a publication that writes nothing passes an empty set. The function refuses a candidate that lists a segment or an extension segment of its own namespace that's neither in the basis nor in that set. It also refuses the put when that clock is older than the compaction budget, which is the check that bounds a new segment's age in the argument above. A fold and a grep index step write under their publication clock, and a compaction writes under the clock that it starts before it reads its inputs. The check sends no store request, and it's linear in the number of segments. It covers a segment added to a run that the basis already lists, which a grep reorganization does, and which a check by run number would miss. Every publisher already passes the check: a fold writes one new run and rebuilds over a winner from the winner's runs, a compaction is abandoned when its inputs moved, a grep index step adds the segments that it wrote, and the other publishers copy their basis's runs or a subset of them.

The function returns the same budget error for the write clock as for the publication clock. A compaction checks its 12-hour budget in its own code before its put, and it ends as abandoned when the budget is used up. With the shared check, the compaction's own check can go, but one handler has to stay. The compaction maps a contention error from a race it lost on every attempt to an abandoned unit, and the budget error is a different error, so the compaction maps the budget error to an abandoned unit too. The maintenance loop then handles it as it handles a lost race today.

The manifest doesn't contain the layout rows, so the shared function can't check the requirement for content. The requirement is kept where layout rows are built. A fold's content writer is the one place that builds a new layout row that isn't a copy. It takes the chain's earlier extents from the layout rows of its basis and its tail, and adds the one object that it writes. A compaction copies rows, and a fold copies the layout rows that the tail's commits contain.

### The gate on an aged writer position

Before a writer position is used as the basis of a publication, LoonFS checks the position if its last check is at least `READ_REVALIDATION_BOUND_MS` (20 minutes) old. The check is the session's existing check: a HEAD of the next manifest and a conditional read of the boundary, after which the position stays, moves onto the newest manifest of its writer epoch, or is dropped, as it does for a read (see [Read freshness](read-freshness.md#the-writers-session-and-its-position)).

Today the position reaches a publication without a check from the commit engine (a commit's validation and the session's folds), from a fold that starts from the position, from a namespace deletion, and from a fork of the namespace's head. (The runtime passes the position to the fork's read of the head as it is. The fork's temporary snapshot is verified after it's written, so a fork from a replaced manifest reads the head again, but the reads before that verification use the unchecked position.) A compaction unit and a retention advance already check the position before they plan, whatever its age, so the gate doesn't change them.

The gate is one accessor, not a rule at each call site. The position's basis and the publisher's position accessor become private to the core crate, and the one way to get a publication basis out of a position is a method that takes a maximum age and runs the check when the position is older. A new caller then can't skip the gate. The age is that of the position's merged check (a check of an earlier manifest counts, as in [Read freshness](read-freshness.md#what-a-read-promises)), and a WAL put doesn't count as a check, because a put confirms the WAL tip and nothing about the manifest.

### Choosing the window

In this section, a "holder" is any work that reads a manifest's rows after checking the manifest: a read, a [read view](../specs/glossary.md#read-view), a writer position, a fold, a commit's validation, or a compaction unit. A check of manifest `m` at time `c` (a successor probe that found no newer manifest, followed by a boundary read that found `m` above the boundary) shows that the provider hadn't made manifest `m + 1` visible at `c`. The collection compares `m + 1`'s provider timestamp with its own clock. The window has to cover four terms:

| Term | Value | Why |
| --- | ---: | --- |
| `READ_REVALIDATION_BOUND_MS` | 20 min | The oldest check that a holder may start work from. An `eventual` read checks its view once the check is that old, and the gate does the same for a publication. |
| `METADATA_PUBLICATION_BUDGET_MS` | 15 min | How long a publication reads rows after it starts. Its reads come before its put, and the put checks the budget. |
| `PROVIDER_PUBLICATION_REQUEST_BOUND_MS` | 5 min | How much earlier than its visibility `m + 1`'s timestamp can be. A provider applies a request within this bound of the client starting it, and the timestamp of a single put is taken when the request arrives, not when it completes (inferred from provider behavior, not measured). |
| `GC_SAFETY_MARGIN_MS` | 5 min | The difference between the collector's clock and the provider's (see [Clock and operation assumptions](../specs/format.md#114-clock-and-operation-assumptions)). |

The sum is 45 minutes, which is `READ_REVALIDATION_BOUND_MS + PUBLICATION_COMPLETION_BOUND_MS`, because the completion bound is the last three terms. The window is far below `T`.

The guarantee follows in three steps:

1. The holder's successor probe, sent after `c`, found no `m + 1`, so the provider made `m + 1` visible after `c`, and `m + 1`'s timestamp is no earlier than `c` minus the provider bound.
2. A collection deletes a segment that `m` lists only if `m` isn't kept at the collection's start, because the collection keeps every segment that a kept manifest lists, by loading the oldest kept manifest or by the segment's age. So the collection's next listed manifest after `m` is at least 45 minutes old by the collection's clock. That manifest is `m + 1` or a later, younger one.
3. With the clocks within the margin, the collection's start is at least `c` + 45 - 5 - 5 minutes, and the collection takes its clock before it sends any delete.

The same steps apply to the pool's collection, with the clock reading that it takes when it starts reading a member, because it sends no delete before it has read every member. So a holder finds every segment that `m` lists, every WAL object above `m`'s `folded_wal_no`, and every content object that `m`'s layouts or that tail refer to, at any time less than 35 minutes after its check. A collection that starts exactly 35 minutes after the check can delete them, so the spec should say "less than", not "at most".

A read starts from a check that's less than 20 minutes old, so it finds every segment it needs, and every byte of the files it reads, for at least 15 minutes after it starts, unless its process pauses for longer than the clock margin. A publication from a gated basis reads its rows before its put and within the publication budget, so it finds its basis. The contract for users is that a read or a read view works for at least 15 minutes after it starts, and work that needs a view for longer takes a snapshot.

A commit's validation has no stated budget, and this design doesn't add one. In practice it finishes within the provider's deadlines, well inside 15 minutes (inferred, not measured). A commit that finds a segment missing anyway, after a pause, fails once with `store_contention`, and the client sends it again with the same commit ID.

### Work with no bound

Three kinds of work outlast what the window covers:

- **A long read or a read view that a caller keeps.** A read that runs longer than 15 minutes from a 20-minute-old check, or a read view kept longer than that, can find a segment missing. The read fails once with an error, and the caller captures a new view or takes a snapshot.
- **A compaction unit.** A unit can run for up to 12 hours (`METADATA_COMPACTION_BUDGET_MS`). Folds keep every run, so the unit's inputs can be dropped only by another compactor's publication. After the deletions described below, the unit fails (today it's abandoned), and no window shorter than `T` would cover it.
- **A process paused past the margin.** Any holder can lose a segment or a content object after a pause longer than the window allows. The check that classifies a missing segment finds that the manifest was replaced, and the holder fails once. A read that finds a content object missing runs the same check on the manifest that the layout came from, so it fails the same way instead of returning `namespace_corrupt`.

In each case, the next use repairs itself. A holder that finds a segment or a content object missing has a check at least 35 minutes old, which is older than the revalidation bound, so its next use runs a check: the gate for a writer position, and the existing age rule and the strong read for a cached view. No error path needs to move or drop anything.

## What LoonFS can delete afterwards

Once both rules are in, no process needs to recover from a collected segment. The in-read retry can go: the loop that runs an ordinary read again after a replaced manifest, with the extra pin and the wrappers that grep, snapshot reads, and the retention advance put around it. An ordinary read that finds its manifest replaced then returns `store_contention` once, as it does today after eight attempts. The check that classifies a missing segment gains one case, so that a namespace whose current manifest is a tombstone returns `namespace_deleted` at once, as the retry's second run returns today, and it also runs for a content object that a read finds missing. After the gate, the publication side can go too: the commit engine's drop of a replaced basis, the case that publishes a commit again after a replaced basis, the fold's extra attempt after a replaced manifest, and the compaction unit's branch that abandons the unit after a replaced manifest. A unit whose inputs another compactor dropped then fails, with a log line and a backoff, instead of reporting that it was abandoned.

The check that classifies a missing segment stays, with both of its kinds, because a snapshot read needs it to tell `snapshot_not_found` from `namespace_corrupt`. So do the check that a manifest is still current, the position check's three outcomes, the runtime's single place that drops a namespace's view, and the error carve-outs that report a commit's basis and not the operation.

Why can't the in-read retry go before the collection rule? Without the rule, a read from a writer position accepts a check up to 20 minutes old and isn't checked again after another process's compaction. Where another process compacts the namespace and collects it hourly, roughly one in three compactions that drop old segments would show the error to reads that touch those segments (estimated from a 20-minute check age against a 60-minute collection interval). A reader process checks its view about once a second, so its exposure is roughly one in 3,600 such compactions (estimated the same way). No metric records read retries today.

The deletions are modest in size. About 150 to 190 lines go outside tests, and the two rules add about 90 to 150, so the net is between about 0 and 100 lines removed (estimated from the current code). The larger change is in kind, because no read, commit, fold, or compaction unit has a branch for a replaced manifest, and the check before a holder's next use repairs every holder.

## Costs

This section lists what the two rules cost in requests, memory, and storage. The measured collection figures are from namespace and pool collections on S3 (each run twice, with the same results), on a namespace of a million files with no writes running during the collections, recorded in `analysis/box-campaign-20261125.md` in the lab repository (part 4).

Today a namespace collection on that namespace sent 36 requests and read about 600 KB in about one second, and its 3 manifest GETs read 589 KB of that. A pool collection sent 730 requests and read 1.18 MB in 1.76 seconds, and 710 of those requests read the extent filters of layout segments, about 650 bytes each. That pool has 1,212 content objects, so the pool figures measure reading the members' filters, not checking a million content objects.

A collection sends no new listing, because the listing above the boundary already returns the timestamps that the rule needs. It loads one more manifest, the oldest kept one, through the segment cache, whatever the number of kept manifests. A process caches each manifest that it publishes, so the writer's host, which also collects its namespace once an hour by default, usually finds the oldest kept manifest in its cache. A sweep on another host loads it from the store (estimated, not measured).

| Namespace | Extra manifest loads per collection | Extra bytes read |
| --- | ---: | --- |
| Idle | 0 | 0 |
| Any namespace that published within 45 minutes | 1 GET on a cache miss, none on a hit | One manifest. On the measured namespace, the manifests published within one window had a median stored size of 257 KB, and the current manifest was 463 KB stored and 3.6 MB decoded (measured). |
| The largest manifest the format allows (512 MiB decoded) | 1 | Up to 512 MiB decoded, the same as one snapshot manifest load today |

The measured namespace published 760 manifests within one 45-minute window, 728 of them in three minutes while the lab ran compaction samples, and those manifests take 194 MB stored (measured). A collection that loaded every kept manifest would have read those 194 MB, against 589 KB today. Loading the oldest kept manifest reads one of them.

For each member, the pool's collection now loads the oldest kept manifest (through the same cache), reads the extent filter of each `content_layouts` segment that the oldest kept manifest lists and the current manifest doesn't, and reads each WAL number between the oldest kept manifest's `folded_wal_no` and the current manifest's once. The extra filters are those of the layout segments that compactions dropped within the window, tens to hundreds per member on a steady writer (estimated), at about 650 bytes each (measured on the namespace above).

The extra WAL reads are the largest cost that the design adds. A probe has measured the store's side of them, and no run has measured a collection that sends them. The pool's collection sends one GET for each WAL object that the member's folds covered in about the 45 minutes before the member's read, because the oldest kept manifest's successor is less than 45 minutes old and every later manifest is younger. A fold is due once the tail has 256 WAL objects or 8 MiB of WAL bytes, and the fold covers the whole tail that it finds. So a fold of a writer that commits steadily covers about 256 WAL objects, and more when commits arrive while the previous fold runs. The design bounds the count only through the window's length, so the count grows with the rate at which the member writes WAL objects. A namespace's writer publishes one batch of commits at a time, with one WAL put for each batch, so that rate is at most about one WAL object for each round trip of a put. The table below estimates the extra reads of one pool collection for one member. The times are extrapolated from that probe, described below the table, at the concurrency that the pool's collection reads with today: 16 members at once, with 16 WAL GETs in flight for each member. The charge assumes the list price of $0.0004 per 1,000 GET requests.

| Member | Extra WAL GETs | Time | Charge |
| --- | ---: | ---: | ---: |
| A writer that commits as fast as one namespace can, about 39 WAL objects a second | About 105,000 | About 155 s | About $0.042 |
| A writer that folds 1.5 times a minute, 256 WAL objects per fold | About 17,000 (68 folds) | About 25 s | About $0.007 |
| A quiet member that committed a few times and was folded within the window | One for each folded WAL object, a few | One round trip | Under $0.00001 |
| A member that published no manifest within the window | 0 | 0 | 0 |

The two write rates are measured, the times are extrapolated from the probe below, and the rest of each row is an estimate. On S3 from the lab's host, one client that committed one file at a time wrote 39.1 files a second, with one WAL object for each commit (`analysis/battery-20261117-phases.md`), which is about one round trip of a put for each WAL object. The build of the million-file namespace above folded 11 times in 7 minutes 18 seconds (part 2 of the record above). That record doesn't say how many WAL objects each fold covered, so 256 for each fold is an assumption. If those folds were due at 8 MiB of WAL bytes, or were started by the dataset builder's pacing, they covered fewer WAL objects, and the second row is lower. If they started late and covered more, up to the write stop of 1,024 WAL objects, the second row is up to four times higher and still below the first.

The probe measured how long the store takes to return that many small objects, and nothing else (the lab record `analysis/pool-tail-read-probe-20261126.md`). It ran once, on the lab's S3-colocated host, and read back 46,080 objects of 32 KiB, the size of a WAL object in a fold of 256 objects that's due at 8 MiB, with plain GETs of whole objects. With 16 GETs in flight, the read took 68.0 seconds, 677 GETs a second, and a GET took 23.3 ms at the median and 34.8 ms at the 99th percentile. The same number of 1 KiB objects took 67.9 seconds at the same concurrency, so at 16 in flight the read is bound by round trips, not by bytes. At 677 GETs a second, the first row's 105,000 GETs take about 155 seconds and the second row's 17,000 about 25 seconds (extrapolated from the probe).

More GETs in flight for each member would shorten the read about in proportion, for the same number of GETs and the same charge. With 64 in flight, the probe read the 46,080 objects in 18.7 seconds (2,462 GETs a second), and with 256 in flight in 4.5 seconds (10,144 a second), so the first row would take about 43 seconds at 64 in flight and about 10 seconds at 256 (extrapolated). The median GET stayed at 23 to 24 ms, but the 99th percentile rose from 35 ms at 16 in flight to 70 ms at 64 and 61 ms at 256. The pool's collection reads 16 members at once, so 64 GETs in flight for each member would mean up to 1,024 in flight from one process, which the probe didn't measure.

The probe didn't decode the objects or take content IDs from them, so the collection's CPU time is unmeasured, and at 10,000 objects a second the decoding could be the limit. It didn't run a collection, so it doesn't show how many GETs a collection sends or what else the collection reads beside the WAL objects. It read from one prefix with sequential keys, and S3 scales request rates per prefix, so members under their own namespace prefixes, or a store under load from other clients, could see different rates. No GET returned a throttling error or any other error. The provider client retries a throttled request before the caller sees it, though, and the slowest GETs (247 to 257 ms, about ten times the median) are the size of one retry, so the probe can't tell whether the provider throttled behind those retries. Each read ran once, so the store's variance from hour to hour isn't in these figures.

A pool with many members adds the sum of its members' rows. For example, a pool of 1,000 members, of which 10 write like the first row and the rest are quiet, adds about 1.06 million GETs to each pass, about $0.42. The pool's collection reads up to 16 members at once, so when the ten busy members are read at the same time, their ranges are read side by side, and the pass takes about 2.6 minutes longer. With 100 busy members, a pass adds about 10.5 million GETs, about $4.20, and about 16 minutes, because no more than 16 of them are read at once (all estimated). The pool's collection runs once a day by default, so these are the figures for a day.

Today the pool's collection reads only each member's unfolded tail, which the write stop limits to 1,024 WAL objects. The pass on the million-file namespace above sent 730 requests in 1.76 seconds, and one of them was a WAL GET (measured, with no writes running). One member that writes like the first row would add about 140 times that pass's requests, and about 90 times its time (estimated).

The WAL bytes in a member's range depend on what its commits write. A fold is due at 8 MiB of WAL bytes, so a member whose folds start at that trigger has about 8 MiB in its range for each fold, about 1.4 GiB for a member that folds that way four times a minute (estimated from the fold trigger). A fold covers the whole tail that it finds, so a fold that starts late covers more, up to the write stop of 64 MiB. The pool's collection needs only the content IDs that each WAL object refers to, so it takes those IDs from each object as the object arrives and keeps none of the objects.

The smallest bound on these reads would be a limit on the WAL numbers that one member's range may cover, with a member whose range is longer treated as unreadable. The pool's collection would then delete no content in any pass while one member writes faster than the limit allows, so the limit would have to be above the busiest member's range, about 105,000 WAL objects at the rate of the first row, which the rate of WAL puts already bounds. A shorter window reduces the reads in proportion, but the window can't be shorter than the four terms in [Choosing the window](#choosing-the-window). So the design accepts a cost that grows with the members' write rates, up to about 2.6 minutes and 4 cents for each member in each daily pass at the rates above.

A missing WAL number in that range stops the pool's content deletion for one pass. It needs a WAL object at least `T` old inside the range, so a tail that stayed unfolded for about a day, and then a namespace collection whose clock is later than the reading at which the pool's collection chose the member's kept manifests. The pool's collection runs once a day by default. The next pass isn't affected by the same event, because its clock is later than that namespace collection's, so its oldest kept manifest is at least as new, and the deleted numbers are below the range that it reads.

A layout segment that the oldest kept manifest lists can also be deleted before the pool's collection loads its extent filter, which stops content deletion for the pass in the same way. The pool's collection loads the extent filters only after it has read every member, and a filter that it can't load skips content deletion and reports `content_deletion_unreadable_member` (see [Content roots](../specs/format.md#119-content-roots)). This needs a layout segment at least `T` old that a compaction dropped within the window before the member's read, and a pool read that outlasts the rest of that window, so that a namespace collection no longer keeps the oldest kept manifest when it runs. Today the same exposure exists for the current manifest's layout segments: a compaction drops an old layout segment after the member's read, and a namespace collection deletes it before the pool loads its filter. With the window, a namespace collection deletes such a segment only once the compaction's manifest is 45 minutes old, so the period in which a drop can stop the pass moves 45 minutes earlier and keeps its length. The design makes the stop about as likely as today's rule does (estimated, not measured).

The cost of either collection on a namespace of a million files with writes running hasn't been measured.

The added memory is small. The live set stores each segment key once, so the oldest kept manifest adds the segments that compactions dropped within the window: compaction inputs, tens to hundreds of keys (estimated). The pool's collection adds the extent filters of the layout segments among them, at 20 bits per extent name, and the content IDs of the longer tail, but not its WAL objects. The oldest kept manifest is decoded whole while it's loaded, as a snapshot manifest is.

Storage grows for segments that were older than `T` when a manifest stopped listing them. Today such a segment is deleted by the first collection after the drop, 0 to 60 minutes later with hourly collections. With the rule, it's deleted 45 to 105 minutes later, so about 45 minutes longer. In the heaviest case, where base compaction rewrites all live metadata once a day, the extra stored bytes average about 3% of live metadata (45 minutes out of 24 hours), with a peak of one extra copy of live metadata for 45 minutes after a full rewrite, a peak that already lasts up to an hour today (estimated). The kept manifests add little storage, because a manifest is deleted by the same age rule as a segment, so a manifest younger than `T` is already stored today. That includes the 194 MB of manifests measured above. The extra manifest object is the oldest kept manifest when it's older than `T`, because every later kept manifest was published no earlier than the oldest kept manifest's successor, which is less than 45 minutes old. Content objects grow the same way: a span object or an upload's whole object that was older than `T` when a fold merged it into a new span object, and a compaction dropped the last layout row that listed it, stays longer too, and so does the content of an older revision whose rows a base compaction dropped. Pool collections run once a day, so the object stays a day longer when the next pool collection falls inside the window, and as long as today otherwise, about 45 minutes longer on average (estimated). The retention floor covers a revision that was current in a reader's view, because a retention advance passes a commit only once it's `T` old, so the revision that the commit replaced keeps its content for `T` after the replacement. The floor doesn't cover an older revision read through a kept manifest after a base compaction drops it, or a replaced layout of the same revision, and the rule covers both.

The check on publications costs one set of the basis's segment keys and one pass over the candidate's, on a manifest that the publication already encodes, and no store request.

The gate runs at most once per active session every 20 minutes, on one commit's path. When no other process has published since the position's last check, it costs one HEAD and one conditional boundary read. When another process has published, it costs the HEAD, a read of each newer manifest (up to nine, after which the position is dropped), and the boundary read. An idle session sends nothing, because the scheduled metadata step reads the position without publishing.

## Changes to the specs

In the storage format, [One complete collection](../specs/format.md#111-one-complete-collection) changes the steps that establish roots: the find step returns the numbers and timestamps that its listing found, the collection loads the oldest kept manifest with the snapshot manifests and lists again when that manifest is missing at its load, and it records the oldest kept manifest's `folded_wal_no` in place of the newest manifest's. The same section gains the stop when the listing returns a manifest above the boundary without a timestamp, its paragraph that says the collection protects every WAL number above `folded_wal_no` refers to the oldest kept manifest's, and its rule that every age check uses one clock reading from the start gains the exception for the pool's reading for each member, which chooses that member's kept manifests. [Reference roots](../specs/format.md#112-reference-roots) gains the rule's row and the load of the oldest kept manifest, its row for the folded boundary protects every WAL number above the oldest kept manifest's `folded_wal_no` in an active or a deleted namespace, and it loses the paragraph that says a replaced manifest isn't a root. [Basis, collision, and boundary checks for every manifest publication](../specs/format.md#basis-collision-and-boundary-checks-for-every-manifest-publication) gains the requirement for segments: a manifest MUST NOT list a segment or an extension segment of its own namespace that its basis doesn't list, unless its own publication wrote that segment under a clock that the publication checks against `METADATA_COMPACTION_BUDGET_MS` before its put. [Content roots](../specs/format.md#119-content-roots) gains the requirement for content: a manifest's layout rows MUST NOT list a content object that neither a layout row of its basis nor a WAL object above its basis's `folded_wal_no` and at or below its own refers to, unless its own publication wrote that object. Manifest 1, which has no basis, and a fork's manifest 2 are the exceptions. Its roots table changes the layout view to include the oldest kept manifest, and its WAL tail row loses the exception that a tombstone has no tail, because a deleted member's kept manifests have tails. The row describes the read from the oldest kept manifest's `folded_wal_no`: above the current manifest's `folded_wal_no`, the first missing number ends the tail, and at or below it, a missing number makes the member's roots unreadable. Its section on discovering members says that the collection chooses a member's kept manifests against its clock reading when it starts reading that member, and that a member whose listing returns a manifest without a timestamp is unreadable. Step 3 of its collection steps reads the oldest kept manifest's layout segments, and the member's tail from the oldest kept manifest's `folded_wal_no`. [Candidate and age rules](../specs/format.md#113-candidate-and-age-rules) changes its example to include a manifest that's kept because its next listed manifest is younger than the window, and it changes two rows of its table. The row for data WAL objects in an active namespace refers to the oldest kept manifest's `folded_wal_no` in place of the current manifest's. The row for data WAL objects in a deleted or retired namespace becomes two rows. In a deleted namespace, a data WAL object is deleted once it's at or below the oldest kept manifest's `folded_wal_no` and its provider age is at least `T`, so the objects above that number stay until retirement. In a retired namespace, every data WAL object is deleted once its provider age is at least `T`, as today. [Clock and operation assumptions](../specs/format.md#114-clock-and-operation-assumptions) says that the safety margin also bounds how much earlier a manifest's provider timestamp can be than the timestamp of a lower manifest above the boundary, which the choice of kept manifests relies on. [Publication during collection](../specs/format.md#115-publication-during-collection) keeps its sentence that metadata segments have no equivalent check, and says why none is needed: a collection keeps every segment that a kept manifest lists, because the oldest kept manifest lists it or because the requirement on publications keeps it young enough for the age rule, so a process finds every segment that its manifest lists for less than 35 minutes after it checks that manifest. [A summary of the log protocol](../specs/format.md#26-a-summary-of-the-log-protocol) changes guarantee 8 and drops the parenthesis in guarantee 5 that exempts publications from the revalidation bound. [Replaying the visible WAL](../specs/format.md#42-replaying-the-visible-wal) loses the retry once the retry is deleted. Its paragraph on a process that keeps only a manifest reference says that a publication from a writer position whose last check is at least `READ_REVALIDATION_BOUND_MS` old checks the position first, and its paragraph on the check after a missing segment says that the check also runs for a missing content object, and that a namespace whose current manifest is a tombstone returns `namespace_deleted`. [Publication and collection timing](../specs/format.md#c1-publication-and-collection-timing) gains the constant, its relationship, and the requirement `METADATA_COMPACTION_BUDGET_MS + PROVIDER_PUBLICATION_REQUEST_BOUND_MS + GC_SAFETY_MARGIN_MS + REPLACED_MANIFEST_WINDOW_MS <= GC_GRACE_WINDOW_MS`, and loses "Doesn't bound publication bases or writer positions". [Read freshness](read-freshness.md), the API spec's paragraph on reads on a replaced manifest (see [Standard error contract](../specs/api.md#3-standard-error-contract)), and the sentences in [SDK shape](../specs/api.md#4-sdk-shape) and [Snapshots](../specs/api.md#snapshots) that say `Namespace::read_at_snapshot` runs again after a replaced manifest change when the retry goes. The [glossary](../specs/glossary.md) gains "kept manifest" and the replaced-manifest window, and its entries for the writer position and the revalidation bound say that a position whose last check is at least the bound old is checked before a publication uses it. The byte format and the wire don't change.

## Alternatives considered

Load every kept manifest. A collection would load each kept manifest to learn its segments, and the pool's collection would read the extent filters of all their layout segments, so the argument about where a segment first appeared isn't needed. The loads grow with the number of publications in the window. On the namespace measured above, they would be 760 manifests and 194 MB stored, against 589 KB today. It also doesn't remove the requirement on publications. If a publisher listed a segment that its basis had dropped, a collection that ran before the manifest that lists the segment again existed would delete it in this form too, and so would a pool's collection with a content object that a fold lists from outside its basis and tail. Both forms need the requirement, so the form that loads one extra manifest is the design.

Load every kept manifest of a member when the pool's collection finds a WAL number missing in that member's range. The pool's collection would then delete content in that pass instead of skipping it. But a missing number needs a tail that stayed unfolded for about a day, so this path would almost never run, and it would add loading every kept manifest as a second path, with its own cost and its own tests. Skipping one pass of content deletion delays deletion by a day in a case that's already rare.

Remember, in the collector, when it first found a segment unreferenced. A collector would keep, between collections, the time it first found each segment unreferenced, and delete the segment one window after that. It's safe, and it uses the collector's own monotonic clock instead of provider timestamps. But the memory doesn't survive a restart, so a host that restarts more often than its collection interval forgets every first sighting before it can act on one. A namespace collected by a daily sweep on a server restarted daily would keep every dropped segment. Making the time durable would add scheduling state, a new mechanism.

Keep the window for metadata only, and let a read through a replaced manifest lose file bytes. The pool's collection would then stay as it is, but a read that can find a span object missing within the window needs a recovery path of its own, and removing those paths is the reason for the window.

Keep today's rule. Every holder then has to handle a segment that was deleted a second after its check, and every operation that reads a manifest's rows keeps its own recovery path.
